# 地形ワイヤーフレームと稜線データの試作

現在の方針・比較結果・最新の全国生成サイズは [調査メモ](RESEARCH.md) にまとめる。新しい調査結果が得られたら、このメモも更新する。以下は実行手順と過去の試作記録を含む。

Issue #90 の実装方式を検討するため、小地域の実 DEM をワイヤーフレームで表示する。尾根・鞍部・斜面を連続した格子で確認できる。以前の尾根抽出は線の切れ目が残ったため、比較用として残し、地形ワイヤーフレームを既定の表示にした。Android / iOS の製品機能はまだ追加していない。

## 実行

Python 3.10 以上を使い、リポジトリのルートで実行する。

```sh
python -m venv build/terrain-venv
# Windows は build/terrain-venv/Scripts/activate、macOS / Linux は以下を使う
. build/terrain-venv/bin/activate
python -m pip install -r tools/terrain/requirements.txt

# 八ヶ岳の例。経度・緯度で指定するので、ほかの地域でも試せる
python tools/terrain/ridges.py --bbox 138.34 35.95 138.39 36.01 --output build/terrain-yatsugatake

# 保存した DEM だけで再生成する。未保存のタイルは通信せずエラーにする
python tools/terrain/ridges.py --bbox 138.34 35.95 138.39 36.01 --offline --output build/terrain-yatsugatake-offline

# 枝の量を比較する
python tools/terrain/ridges.py --bbox 138.34 35.95 138.39 36.01 --offline --min-cells 25 --output build/terrain-yatsugatake-dense

# 通信なしのテスト
python -m unittest discover -s tools/terrain -p 'test_*.py' -v

# 必要なときだけ標準地図も取得し、主稜線と鞍部を目視で照合する
python tools/terrain/reference.py build/terrain-yatsugatake
# 保存済みの標準地図だけで比較画像を再生成する
python tools/terrain/reference.py build/terrain-yatsugatake --offline

# DEM を間引かずに陰影を確認する。従来版とは別の場所に保存する
python tools/terrain/ridges.py --bbox 138.34 35.95 138.39 36.01 --offline --mesh-step 1 --output build/terrain-yatsugatake-full-resolution
```

生成した `build/terrain-yatsugatake/preview.html` を WebGL 2 に対応したブラウザーで開く。ファイルにデータを埋め込んでいるため、サーバーや通信は不要。陰影付きの地形ワイヤーフレームを既定で表示し、回転・傾き・拡大、格子の間隔、対角線、隠れ判定を切り替えられる。標高は誇張しない。抽出した尾根だけの比較表示にも切り替えられる。

陰影は三角形の斜面の向きから計算し、淡い色の地形面に重ねる。格子はその上に残す。「地形に陰影をつける」を外すと、面を塗らないワイヤーフレームに戻る。光の方角と陰影の強さを変えられ、光の高さは 45° に固定した。方角は北が 0°、東が 90°で、既定は北西の 315°。光源は地形に対して固定し、表示の回転には追従させない。山がほかの斜面へ落とす影は計算していない。

「表示」で「陰影のみ（格子なし）」を選ぶと、格子や尾根の線を描かず、陰影付きの地形面だけを表示する。光の向き、陰影の強さ、回転・傾き・拡大はそのまま調整できる。このモードでは陰影を有効に固定し、細かい地形メッシュ（当地で約 31 m）を自動で使う。対角線と線の隠れ判定の操作は無効にする。ワイヤーフレームへ戻すと、元の陰影のオン・オフと格子の間隔に戻る。

「滑らかな陰影」は既定でオン。隣り合う三角形の法線を面積で重み付けして共有頂点に足し、面の内側では補間した法線で明暗を計算する。これにより三角形ごとの明暗の段差を抑える。地形の座標や標高は変えず、欠損をまたぐ面も追加しない。オフにすると従来の三角形ごとの陰影と比較できる。地形の外形そのものはメッシュの細かさに依存する。

ワイヤーフレームは隣接する区画で同じ頂点と辺を共有する。最小長による線の選別を行わないため、その選別で尾根が切れることはない。格子の間隔は当地で約 31・62・124・247 m の 4 段階（元の格子の間隔で変わる）。既定は約 124 m。同じ間隔の面で隠れ判定し、細かい地形の面が粗い格子の線を隠してしまうのを防ぐ。細かい地形を調べるときは格子の間隔を小さくする。

八ヶ岳の生成結果では、4 段階すべてで格子が一続きになっていること、同じ辺を重ねて描いていないことをブラウザー上の接続検査で確認した。標準の間隔では 2,090 頂点・6,085 辺。隠れ判定・対角線・回転・傾き・拡大・比較表示の切り替えも、外部通信なしで確認した。Python の 18 テストでは、頂点の間に欠損がある区画に面を作らないことも確かめた。

`reference.py` は同じ範囲の標準地図を直列に取得し、両方式の候補を赤線で重ねた `reference.html` を作る。標準地図は標高タイルとは別に保存し、URL・容量・SHA-256 を `reference-sources.json` に残す。こちらも生成後は通信なしで開ける。

プレビューは地域全体を見下ろす透視投影である。真上から見ても、標高が高くカメラに近い地点ほど大きく投影される。回転・傾きは地域の中心を基準とし、拡大はカメラを動かさず画角を変える。地形の範囲からカメラの距離と描画する奥行きの範囲を決め、回転しても地形がカメラの後ろへ入らないようにする。現在地からの見え方、#89 の操作、山頂アイコン・山名との重なり、端末の描画速度を検証するものではない。画面の時間表示は描画命令を送るまでの時間で、GPU の処理時間やフレームレートではない。

投影のテストには Node.js と、`require('playwright')` で読み込める Playwright が必要。Windows ではインストール済みの Edge、ほかの OS では Playwright の Chromium を使う。`TERRAIN_BROWSER_CHANNEL` でブラウザーを指定できる。

```sh
node tools/terrain/test_projection.cjs build/terrain-yatsugatake/preview.html
```

このテストはプレビューの実際の頂点シェーダーを GPU で動かし、真上からの標高による拡大、中心位置、前後の描画境界を確かめる。回転・傾き・拡大も操作し、`perspective-top.png` と `perspective.png` を生成先に保存する。

## 入力と処理

元データは国土地理院の DEM10B PNG 標高タイル、ズーム 14 に固定した。異なる解像度の DEM を混ぜる処理はまだない。PNG の値の分解能 0.01 m と、元の標高の精度は区別する。

- [標高タイルの仕様](https://maps.gsi.go.jp/development/demtile.html)
- [地理院タイル一覧（提供範囲・ズーム・元データ）](https://maps.gsi.go.jp/development/ichiran.html#dem)

取得は直列に行い、PNG を `build/terrain-cache/` に保存する。HTTP 429 と一部のサーバーエラー、接続エラーは最大 3 回まで試す。404 や不正な PNG は失敗として扱う。再実行では保存済みの PNG を使う。更新を確かめたいときは別の `--cache` を指定し、結果の元データの SHA-256 を比べる。

解析する範囲には周囲 1 タイルを足す。周辺を含む取得枚数が 64 枚を超える指定は、通信前に拒否する。表示範囲がすべて欠損なら失敗する。欠損を標高 0 m に置き換えず、線の補間や隠れ判定用のメッシュでも穴をまたがない。

まず 3 × 3 の平均で 2 回平滑化し、次の 2 方式を比較する。線の標高は平滑化前の DEM から補間する。

| 方式 | 処理 | 主な制約 |
|---|---|---|
| `watershed` | D8 の最急降下先から流域を分け、異なる流域の画素境界を線にする | 平坦面・局所的なくぼみ・処理領域の端で流域の分け方が変わる。境界のすべてが見た目の尾根になるとは限らない |
| `inverse-flow` | 標高を反転した D8 の流路から、一定数以上のセルが集まる経路を線にする | 山頂で多数の線が集まりやすい。二峰を鞍部経由でつなぐことは保証しない |

`--min-cells` は流域境界では両側の流域の最小セル数、反転流路では集まるセル数であり、同じ意味の密度指標ではない。単純な D8 の比較実装で、GRASS GIS の `r.watershed` を使ったものではない。くぼみの処理、平坦面の排水、複数方向への流れ、地形の曲がり方による選別は未実装である。

線を分岐・端点で分けてから簡略化する。`--min-length` はその区間の最小長（既定 100 m）。簡略化の許容誤差は水平 10 m、標高 2 m。端点・分岐点は残し、鞍部などの標高変化も標高誤差の制限に含める。ただし、小さな枝を落とすと接続が減る。

## 出力

| ファイル | 内容 |
|---|---|
| `watershed.geojson` / `.geojson.gz` | 流域境界の標高付き折れ線。座標は経度・緯度・標高 m の順 |
| `inverse-flow.geojson` / `.geojson.gz` | 反転流路の標高付き折れ線 |
| `terrain.npz` | 表示範囲の元解像度の標高格子（float32、欠損は NaN）と JSON のメタデータ。Python での比較用 |
| `report.json` / `.json.gz` | パラメーター、元 PNG の URL・容量・SHA-256、各方式の線数・頂点数・容量・生成時間、標高格子の情報 |
| `preview.html` | 外部通信のない比較用画面 |

形式の版は試作用の 1。配信仕様や MBTiles の格納方式は決定していない。標高格子のメタデータには、左上の世界ピクセル座標、ズーム、配列の形、標高の出典を含める。NPZ は `numpy.load(path, allow_pickle=False)` で読み、使い終わったら閉じる。

タイル境界をまたぐ抽出は、結合した DEM で行う。切り出しの交点を固定する処理と、その交点が隣接領域で一致するテストを入れた。ただし、異なる範囲を独立に解析したときの流域境界の一致は保証しない。全国配信では解析区画・余白・接続点の決め方を別途検証する必要がある。

HTML には元の標高を 32 ビット浮動小数の配列として gzip 圧縮し、Base64 で埋め込む。ブラウザーで展開して頂点・三角形・法線を生成するため、通信せずに開ける。gzip の展開にはブラウザーの `DecompressionStream` を使う。表示メッシュは既定で 4 画素ごとに間引く（`--mesh-step`）。ワイヤーフレームの格子の間隔は、このメッシュからさらに間引いて切り替える。抽出した尾根の比較表示では、線は簡略化した折れ線なので、地表のメッシュと一致せず、一部が隠れる場合がある。プレビューでは小さな奥行きの補正を入れているが、製品での補正量は未決定。精度を調べるときは `--mesh-step 1` の結果とも比べる。表示範囲の外にある地形による遮蔽は扱わない。

## 八ヶ岳での初回確認（2026 年 10 月 12 日）

範囲は東経 138.34〜138.39°、北緯 35.95〜36.01°。南北約 6.7 km、東西約 4.5 km。表示範囲の格子は 583 × 864、欠損 0、標高タイルの画素間隔は当地で約 7.73 m。元データは DEM10B であり、画素間隔を元データの分解能と同一視しない。

周囲を含めた入力は 30 タイル、PNG 合計 3,132,973 バイト。既定のパラメーターで次の出力になった。gzip の容量は単一地域の実測で、全国分の容量の見積もりではない。

| 方式 | 区間数 | 頂点数 | gzip の容量 |
|---|---:|---:|---:|
| 流域境界（最小セル数 100） | 36 | 684 | 10,975 バイト |
| 反転流路（最小セル数 100） | 977 | 5,299 | 70,683 バイト |
| 反転流路（最小セル数 25） | 2,888 | 13,821 | 171,124 バイト |

元解像度の標高格子（NPZ）は 1,419,273 バイト。流域境界は最小セル数を 25 にしても今回の区間数・頂点数が変わらず、反転流路の枝は増えた。プレビューでは流域境界の大きな線のつながりを確認できたが、反転流路は山頂付近に多数の線が集中した。セル数の閾値だけで枝尾根の見やすさを制御するのは難しい。

合成した二峰と鞍部の地形では、流域境界が二峰の間で切れず、標高付きの線が鞍部まで下がることをテストした。実地形では地理院の標準地図に重ね、赤岳・横岳・硫黄岳の主稜線におおむね沿う候補を確認した。一方、流域境界にも直角に折れる不自然な線が残り、反転流路は特に山頂周辺に集中した。地形図との照合は目視のみで、尾根・鞍部の位置誤差は数値で測っていない。現段階ではどちらも採用方式としない。

保存した DEM を使うオフライン再生成で、両方式の GeoJSON / gzip、NPZ、HTML が初回とバイト単位で一致した。Windows の Edge のヘッドレス実行で方式切り替え・回転・傾き・拡大・最小長・隠れ判定を操作し、JavaScript と WebGL のエラーがないこと、隠れ判定で線の表示が変わることを確認した。Android / iOS の実機性能と、山名を重ねたときの読みやすさは未確認。

## 間引きなしの表示確認

`--mesh-step 1` の生成結果では、当地の約 7.73 m 間隔の格子をそのまま使った。陰影のみの表示は 503,712 頂点・1,004,532 三角形。滑らかな陰影の計算もこのメッシュで行う。元データは同じ DEM10B であり、元データ自体の測定精度が上がるわけではない。

標高からブラウザーでメッシュを生成する方式に変更し、高精細版の HTML は 2,275,703 バイトになった（頂点と三角形を埋め込んだ旧形式は 54,664,496 バイト）。標高の間隔と三角形数は変わらない。展開後の描画用メモリは必要なため、HTML の縮小率がそのまま実行時メモリの削減率になるわけではない。生成先の `preview.html` を開き、「陰影のみ（格子なし）」に切り替える。Windows の Edge のヘッドレス実行で、透視投影のテストと光源・回転・傾き・拡大の操作が通り、JavaScript と WebGL のエラーがないことを確認した。スマートフォンでの性能は未確認。

## 出典と配布前の確認

[国土地理院コンテンツ利用規約](https://www.gsi.go.jp/kikakuchousei/kikakuchousei40182.html)に沿って、出力データと画面に出典と加工した旨を記載した。元データの URL と SHA-256 は生成時のレポートに残す。規約には測量成果の利用手続についての記載もあるため、#49 では対象の DEM と加工・配布の形について確認する。この試作で、稜線データの再配布に必要な手続が完了したとは扱わない。

生成物は `build/` に置き、リポジトリや公開サイトには追加しない。製品化に進む前に、地形図との位置誤差の測定、不自然な線の除去、枝の重要度による選別、タイル接続、隠れ判定の精度、配信形式と更新方法を決める。Android / iOS には同じデータと判定用の見本を用意し、山頂・稜線の投影を #89 と共通にする。

### 地形が落とす影

「地形が落とす影」で、山や尾根が日光を遮る影を切り替える。「光の高さ」は 5〜80°で調整でき、既定値は 30°。低い光では影が長くなる。光の向きは既存の操作で変えられる。

光源から見た地形の奥行きを最大 2048 × 2048 の深度テクスチャに保存し、描画時に比較する。影の境界は周辺 9 点を比較してぼかす。影の計算には表示用に間引く前のメッシュを使い、光の向き・高さが変わったときだけ更新する。カメラの回転・傾き・拡大では再利用する。追加の標高データや通信は不要だが、GPU の処理と保存領域は増える。

読み込んだ範囲の外にある地形の影は描かない。影の解像度と、面が自分自身を影にしないための補正により、細い影の欠落や境界のずれが生じる場合がある。影のオン・オフによる描画画素の変化、光の操作による再計算、カメラ操作時の再利用、WebGL エラーがないことを Edge のブラウザーテストで確認した。スマートフォンでの性能は未確認。

## 全国の標高 PNG を取得する

山名データの取得とは独立して、国土地理院の標高タイルを取得する。次のコマンドを同じ条件で実行すると、取得済みの結果を飛ばして再開する。

```sh
python tools/terrain/fetch_national.py
```

対象は東経 122〜154°・北緯 20〜46°、ズーム 14 の標高 PNG。日本を含む矩形を確認するため、海上や日本以外の地点も問い合わせ対象になる。配信されていないタイルは 404 として記録し、地形を補わない。日本国内の行政境界で切り抜く処理は含まない。

元の PNG は `build/terrain-cache/14/{x}/{y}.png` に変更せず保存する。試作用の取得済み PNG も再利用でき、プレビューは同じキャッシュを `--offline` で読める。URL・確認日時・状態・ファイルの大きさ・SHA-256 は `build/terrain-national/tiles.sqlite3`、進捗は `progress.json` に保存する。既存キャッシュを初めて登録した日時は元の取得日時ではなく確認日時になる。生成やダウンロード後も元データを削除しない。

既定は同時接続 4、全接続で毎秒 8 回まで。通信障害・429・一時的なサーバー障害は待って再試行し、403 や不正な PNG は停止する。停止した通信を 404 として記録しない。長時間かかるため、PC を起動してネットワークにつないでおく必要がある。安全に中断するときは `build/terrain-national/STOP` を作る。処理中の行を保存して停止するので、再開前に STOP を取り除く。

バックアップは取得を停止してから、PNG の保存先と取得記録のフォルダを一緒にコピーする。公開・配信用のファイル生成は別の工程であり、この処理では行わない。

取得先または取得記録の保存先のドライブで空き容量が 10 GB 未満になると、新しい取得を始めず停止する。進捗の状態は `disk_space_low` になる。空き容量を確保したあと、同じコマンドで再開できる。

取得順は中部、本州中央、東北、北海道、中国・四国・近畿、九州、南西諸島、伊豆・小笠原諸島を含む範囲を優先する。矩形の重複は飛ばし、最後に残りの範囲を確認するため、優先範囲外の離島を取得対象から除外しない。問い合わせ総数は変わらない。既存の取得記録は順序変更後も再利用する。進捗の `currentRegion` は処理中の地域、`checkedTiles` は確認済み、`savedTiles` は保存済み PNG、`missingTiles` は 404 の件数を表す。

## 公式ダウンロードツールへの切り替え

タイルのダウンロードには [国土地理院の tdlmn](https://github.com/gsi-cyberjapan/tdlmn) を使う方針に変更し、独自の全国取得処理は停止した。取得済み PNG と SQLite は削除していない。

手元では公式ツールを `build/tdlmn/`、Ruby を `build/rubyinstaller-4.0.7-1-x64/` に展開した。`build/tdlmn/src/program.ini` は `TILE_ID = dem_png`、`ZOOM_LEVEL = 14` に設定済み。保存先の `build/tdlmn-tiles/dem_png` は、従来の `build/terrain-cache` を指す Windows のジャンクションなので、元 PNG を移動・複製せずに使える。設定とダウンロードしたツール本体は Git の管理対象外。

公式ソースにある古い例外名 `TimeoutError` は、外付けの `tdlmn_compat.rb` で現在の `Timeout::Error` に対応させる。公式ツールのソースは変更しない。リポジトリのルートから PowerShell で次を実行する。

```powershell
Push-Location build/tdlmn/src
try {
  & ../../rubyinstaller-4.0.7-1-x64/bin/ruby.exe -r ../../../tools/terrain/tdlmn_compat.rb tdlmn.rb -m -dt -diff
} finally {
  Pop-Location
}
```

確認時点では標高 PNG 用の `mokuroku.csv.gz` が 404 のため、全国のダウンロードは進められていない。公式ツールは目録または更新一覧と MD5 を必要とし、一覧なしでタイルの存在を調べる機能はない。全国取得の再開には標高用の有効な一覧が必要。独自処理の空き容量による停止機能は tdlmn には引き継がれないため、実際の連続取得を再開する際に別途設ける。

### std 目録の座標を使って標高を取得する

標高用目録の代わりに、公式の `std/mokuroku.csv.gz` を保存し、日本を含む指定範囲のズーム 14 の座標を候補として使う方式を追加した。標準地図と標高の提供範囲は異なるため、候補内でも標高が 404 になることがある。標準地図の目録にない標高タイルの網羅は保証しない。

```sh
python tools/terrain/download_dem_with_tdlmn.py
```

元目録は `build/terrain-national/std-mokuroku.csv.gz`、目録の出典情報と SHA-256 は `std-mokuroku-source.json` に保存する。標準地図の日時・サイズ・MD5 を標高画像のものとして転用しない。候補一覧は標高用の正式な目録ではなく、座標だけを引き継いだ独自の入力一覧。

公式 tdlmn の作業コピーに補助処理を適用し、MD5 が不明な候補は PNG の CRC、256 × 256 RGB の寸法・形式、圧縮データの展開を検査する。取得後の標高 PNG の SHA-256 と取得日時は `build/tdlmn/src/dem-downloads.jsonl` に保存する。これは配信元の MD5 との一致検証とは異なる。既存の正常な PNG は再利用する。公式ソースのコミットと適用した変更は `build/terrain-national/tdlmn-source.json` に記録する。

同時接続は 4、問い合わせ前に各接続で 0.5 秒待つ。起動した Ruby プロセスを監視し、空き容量が 10 GB 未満になったら停止する。進捗は `tdlmn-progress.json`、公式ツールの実行ログは `tdlmn-output.log`。独自の矩形走査の `progress.json` とは別の記録になる。公式ツールの終了コードだけでは全候補の保存成功を表さないため、終了後もログの NG 件数を確認する。

### 404 の保存と再開

標高タイルが 404 を返したときも、URL・確認日時・使用した元目録の SHA-256 を `dem-downloads.jsonl` に保存し、その都度ディスクに書き出す。同じ目録で再開するときは記録済みの 404 を候補から除外する。目録の SHA-256 が変わった場合は再確認する。429 や一時的なサーバー障害は待って再試行し、404 として保存しない。致命的な HTTP エラーでは処理全体を停止する。途中で書き込みが切れた記録は未確認として扱う。

進捗の `candidateTiles` は全候補数、`skippedMissingTiles` は記録済み 404 の除外数、`queuedCandidates` は今回公式ツールへ渡した候補数を表す。対応前の公式ツールの404ログには座標が残っていないため、過去の404は復元せず、変更後に確認した結果から保存する。

## 容量を減らした標高データ

```sh
python tools/terrain/compact_dem.py --step 5 --codec xz --workers 8
```

元の PNG を残し、標高を 5 m単位に丸めたデータを `build/terrain-compact/14/{x}/{y}.ymd` に作る。横方向の間引きはせず、標高の丸めによる誤差は最大約 2.5 m。欠損位置をビット列で分けて保存し、海抜 0 mには置き換えない。隣接点から予測した二次元差分を xz で圧縮する。`--step 1` なら最大約 0.5 mの誤差に抑えられるが容量は増える。

YMD1 のヘッダーはリトルエンディアンの `<4sHHfiBB`（識別子、行数、列数、標高の単位、基準値、フラグ、圧縮形式）。差分は符号付き 16 ビットで、値が収まらないときは 32 ビットにする。フラグのビット 0 が 32 ビット、ビット 1 が欠損マスクあり。圧縮形式は 0 が gzip、1 が xz。展開後は差分の配列と、必要な場合は行優先・下位ビットからの欠損マスクが続く。差分は縦・横の累積和で戻し、基準値を足して標高の単位を掛ける。

全タイルで復元し、最大誤差と欠損位置の一致を検査する。タイル別のサイズ・SHA-256・誤差は `tiles.jsonl`、全体のサイズ・最大誤差・二乗平均平方根誤差は `manifest.json` に記録する。これは元の標高データの精度ではなく、追加した圧縮による誤差。xz の展開には専用の処理が必要で、ブラウザーの `DecompressionStream` だけでは展開できない。

生成が完了して `manifest.json` ができた後に地域選択サーバーを起動すると、圧縮データを優先して読む。サーバー側で展開し、ブラウザーには従来の形式で渡す。表示には標高の丸め単位と最大誤差を明記する。Android / iOS の展開処理は未実装。

全国 109,506 タイルの生成結果は、タイル本体 878,138,288 バイト。元 PNG は 9,280,731,082 バイトで、約 90.5% 小さくなった。全タイルの復元検証で標高の最大誤差は 2.5 m、RMSE は約 1.414 m、欠損位置はすべて一致した。配布用の `build/dem10b-compact.zip` は圧縮済みタイルを再圧縮せずまとめ、一覧と manifest は ZIP 内で圧縮する。ZIP の大きさと SHA-256 は `build/dem10b-compact.json` を参照する。

## 複数縮尺を持つ SQLite

```sh
python tools/terrain/lod_database.py
```

ズーム 14 の圧縮標高をそのまま SQLite に格納し、ズーム 13〜4 の概略データを順に生成する。元データは DEM10B のみ。概略レベルは隣接 2 × 2 点の標高あり部分を平均し、すべて欠損のときは欠損を維持する。平均化した格子の中心位置も投影に反映する。海岸などの欠損と地形の境界は概略化される。細部版の標高丸めによる最大 2.5 mの誤差上限は、低縮尺の概略データには適用しない。

出力は `build/terrain-lod.sqlite3` と配布用の `build/terrain-lod.sqlite3.gz`。SQLite の `tiles` に `z`・`x`・`y`・圧縮標高を保存し、座標の索引で必要なタイルだけを読む。`metadata` に形式の識別子・版・レベル一覧・加工方法を保存する。最細部の xz を再圧縮せず、概略レベルは展開速度を考えて gzip で保存する。生成途中は別名のファイルを使い、完了後に差し替える。

地域選択サーバーは完成した SQLite がある場合に優先して使う。全国・広域の表示範囲に合わせて縮尺を選び、全国表示でズーム 14 のタイルを大量に展開しない。ポリゴン版ではホイールや「拡大」スライダーによる拡大・縮小に合わせ、読み込む縮尺も自動で切り替える。単独 HTML の表示にはサーバーからの自動読み込みはない。

全国表示は地形分布を確認する概略表示であり、地球の曲率を含めた全球の立体描画ではない。地域別 SQLite への分割、共通 manifest v6 による公開、Android / iOS への組み込みは別の工程。この試作では全国を 1 本の SQLite にまとめて動作を確かめる。

生成した全国 SQLite は 1,510,574,080 バイト、配布用 gzip は 1,490,014,950 バイト。ズーム 4〜14 の 11 段階を収録した。全国の初期表示はズーム 4 の 4 タイル、206,989 標高点、13,428 三角形。Windows のヘッドレス Edge で表示初期化まで約 324 ms だった。富士山ではズーム 14、1,182,722 三角形へ切り替わることを確認した。この時間は当該 PC の参考値で、スマートフォンの性能や GPU の描画完了時間ではない。

## ポリゴンで容量と描画量を抑える

```sh
python tools/terrain/polygon_dem.py
# 中断後、同じ元データ・生成条件で再開
python tools/terrain/polygon_dem.py --resume
```

10 インチ程度の画面での表示を念頭に、格子をすべて描く方式から、地形の変化に合わせた適応ポリゴンへ変換する。ズームは 4〜14 の 11 段階を収録する。画面の大きさだけで必要な精度は決まらないため、細部のレベルを残して表示比較できるようにする。

各正方形を中心からの 4 三角形で近似し、入力の標高点とのずれが大きい場合だけ 4 分割する。隣の区画に頂点がある場合は同じ辺へ頂点を追加し、タイル外周では元の全標高点を共有する。同じレベルで読み込んだタイル間の隙間と標高不一致を防ぐ。欠損を含む区画は細かく分割し、欠損をまたぐ面を作らない。

座標や三角形の接続番号を直接保存すると大きくなるため、YMP2 は分割木を 2 ビット単位で記録し、決められた順番の頂点の標高差だけを xz 圧縮する。頂点座標と三角形の接続は読み込み時に復元する。最細部の入力格子点に対するずれの上限は 20 m。元の DEM の精度と、標高を 5 m単位に丸めた追加誤差は別。低縮尺の平均化による誤差も別に扱う。入力格子点の最大誤差・欠損保持・境界の一致は単体テストで確認し、全タイルで保存前後の頂点と接続が一致することを検証する。

出力は `build/terrain-mesh.sqlite3` と `.sqlite3.gz`。完成後に地域選択サーバーを起動するとポリゴン版を優先する。格子版と元 PNG は比較用に残す。表示範囲はタイル単位で少し広がる。全国概略の地球曲率、地域別配布、Android / iOS 実機での見え方と速度は別途確認する。

ポリゴンの誤差・欠損・境界・保存と復元は `python -m unittest discover -s tools/terrain -p 'test_*.py'` で確認する。地域選択サーバーの起動後、`node tools/terrain/test_polygon_viewer.cjs http://127.0.0.1:61434/` で富士山・八ヶ岳・大山・全国の切り替え、頂点と接続番号、ワイヤーフレームと陰影、WebGL のエラーを検査する。ブラウザー検査には Playwright と Edge が必要。

レベル 13 追加前の全国分の生成結果は 6 段階、計 118,248 タイル。SQLite は 295,688,192 バイト、配布用 gzip は 279,545,814 バイトで、格子版の複数縮尺 gzip から約 81.2% 減った。最細部 109,506 タイルのポリゴン本体は 232,725,206 バイト。SQLite の整合性と、gzip 展開後の SHA-256 の一致を確認した。各縮尺から計 84 タイルを抽出し、別の三角形補間処理でも入力格子点の誤差上限と欠損位置を埋めないことを確認した。

完成した全国版を Windows の Edge で表示したとき、富士山は 63,304、八ヶ岳は 112,490、大山は 120,768、全国概略は 5,402 三角形だった。陰影のみ・ワイヤーフレームの切り替えで WebGL エラーは発生しなかった。これは PC 上での確認であり、10 インチ以下の実機での表示品質と速度は未確認。

## 水域・登山道と徒歩道・都道府県境の試作

検証用プレビューに、地形・水域・登山道と徒歩道・都道府県境の表示切り替えを追加した。地形を消して水域だけ表示できる。地形による遮蔽は表示とは別に切り替え、設定はブラウザー内に保存する。全画面では操作用の凡例と出典を残して描画する。

マウスの左ドラッグで表示位置を移動し、ホイールで拡大・縮小する。右ドラッグまたは Shift＋左ドラッグでは、横方向で方角、縦方向で傾きを変える。ダブルクリックか「視点を戻す」で、位置・拡大率・方角・傾きを初期状態へ戻す。サーバー版のポリゴン表示は、移動先と拡大率に応じて保存済みの全国データを読み直す。単独 HTML 版では読み込み済みの範囲を動かす。操作と描画の変化は `node tools/terrain/test_mouse_viewer.cjs` で実際のマウス入力を使って確認する。

自動切り替えでは `/terrain-data` から必要範囲の JSON を gzip で受け取り、同じ描画面の地形と追加レイヤーを差し替える。位置・方角・傾き・表示設定を維持し、中心の標高には緩やかに追従する。細かな操作は 240 ms まとめ、縮尺の境目では 15% の余裕を設ける。読み込みは同時に 1 件に絞る。画面四隅の視線と地面の交点から必要な範囲を求め、余裕を加えて先読みする。初期表示でも範囲が足りなければ読み足す。地平線より上の視線は有限の先読み距離に抑える。取得中に移動しても、応答が現在の画面を覆い、レベル・表示モード・投影条件が合う場合は表示する。条件が変わって使えなくなった応答は捨て、最新の範囲を読み直す。直近 2 件をキャッシュし、置き換えた GPU バッファーは解放する。保存データがない範囲や読み込みの失敗では、現在の地形を残して画面に知らせる。

`node tools/terrain/test_lod_viewer.cjs` は全国のレベル 4 から 8・14 への拡大と全国への復帰、移動先の読み込み、遅い応答の破棄、失敗時の表示維持、同じ描画面と方角・傾きの保持を確認する。元データの各縮尺を切り替えるため、平均化された山の形が細部へ変わる差は残る。

追加データの取得範囲は富士山・富士五湖・駿河湾周辺（東経 138.45〜139.00 度、北緯 35.00〜35.64 度）。全国の追加レイヤーと Android / iOS アプリへの組み込みは未実施。取得範囲外や広域の概略表示では、追加レイヤーが表示されない理由を画面に出す。

元データは [国土地理院最適化ベクトルタイルの PMTiles 版](https://github.com/gsi-cyberjapan/optimal_bvmap)。必要な範囲を HTTP Range で取得し、受信した範囲データを保存する。ヘッダー・ETag・更新日時で取得元を記録し、配信元が更新された場合は別のキャッシュへ取得する。従来の更新が止まった個別 PBF 配信は使わない。

Windows での準備と起動例：

```powershell
python -m venv --system-site-packages build/terrain-venv
build/terrain-venv/Scripts/python -m pip install -r tools/terrain/requirements-overlays.txt
build/terrain-venv/Scripts/python tools/terrain/vector_layers.py
build/terrain-venv/Scripts/python tools/terrain/region_server.py
```

元の地形処理で使う NumPy も必要。追加レイヤーは `build/terrain-vectors.sqlite3` に保存する。この試作では全国の地形 SQLite を書き換えず、別ファイルから読み込む。取得後の表示では外部サービスへ通信しない。地域選択の「富士山・富士五湖（追加レイヤー）」、または `http://127.0.0.1:61434/terrain?lat=35.40&lon=138.73&size=30&fullscreen=1` で確認できる。

水域の面は `WA`、河川中心線は `RvrCL`、徒歩道は `RdCL` の `vt_code=2721`、都道府県境は `AdmBdry` の `vt_code=1211` を抽出する。徒歩道には登山道以外の道も含まれる。北海道へ広げる場合、1211 には振興局界も含まれるため、道県境だけに絞る追加処理が必要。[公式の分類表](https://maps.gsi.go.jp/help/pdf/vector/optbv_featurecodes.xlsx)を参照する。

`WA` の「河川・湖池」だけでは湖と断定しない。水域周辺だけズーム 16 の湖池水涯線を追加取得し、閉じた面を識別する。海は海抜 0 m、識別できた湖は岸の地形から推定した一定の標高で表示する。湖・海の内部の地形を切り抜き、岸を水面標高に合わせる。島は残す。識別できない水域と河川は地形に沿った面として表示する。推定値は実測水位ではなく、標高や岸の形の差が表示に影響する。

線の標高は表示中の三角形そのものから補間し、地形のない部分では線を切る。徒歩道は橙色、県境は紫色の破線、水域と河川は水色にする。近距離の線も一定間隔で補間するため、急な地形で細い線が一部隠れることがある。

生成した追加レイヤーの SQLite は 24,023,040 バイト。全国分の容量ではない。単体テストは仮想環境から `python -m unittest discover -s tools/terrain -p 'test_*.py'`、保存した富士山 HTML の描画検査は `node tools/terrain/test_overlay_viewer.cjs` で実行する。描画検査では全レイヤー・水域のみ・地形のみ・全非表示、遮蔽、全画面、外部通信なしを確認する。

## 格子状の形を避ける不規則メッシュの比較

四分割した正方形と中心からの扇形は、陰影を滑らかにしても幾何形状として残る。通常の表示では隣接点の法線を 3 回平均して陰影のばらつきを抑え、影の判定も三角形の奥行きに合わせて補正した。座標や接続は変えないため、四分割の形自体を解消する処理ではない。

別の地域試作として、入力格子との誤差が大きい場所へ点を追加し、Delaunay 分割で不規則な三角形を作る `irregular_dem.py` を追加した。タイル境界も同じ標高列から誤差に応じた点を選び、両側で同じ点を共有する。欠損をまたぐ面は取り除く。この方法では海岸で隙間が増える場合があり、全国への採用前に追加検証が必要。

```powershell
build/terrain-venv/Scripts/python -m pip install -r tools/terrain/requirements-tin.txt
build/terrain-venv/Scripts/python tools/terrain/irregular_dem.py --tolerance 25
```

不規則メッシュを含む単体テスト一式にも、この追加の依存ライブラリが必要。出力は `build/terrain-tin.sqlite3` と `build/terrain-tin.html`。全国の SQLite は変更しない。地域選択サーバーの `/tin-preview?fullscreen=1` から富士山・富士五湖周辺の比較試作を表示できる。比較試作はレベル 12 のみで、自動縮尺切り替えは使わない。

富士山周辺の 25 タイルでは、四分割版の 168,046 頂点・310,442 三角形から、不規則版の 56,006 頂点・108,846 三角形へ減った。タイル本体の合計は 137,315 バイトから 120,955 バイトになった。不規則版の入力格子点に対する差は最大 25 m を条件としており、比較した四分割版の条件は最大 50 m。元の DEM の誤差と概略格子への平均化の誤差は別。全国のサイズをこの比率だけから推定しない。

実験形式 YMP3 は座標と標高の差分を xz 圧縮し、三角形の接続を読み込み時に再構成する。欠損部分の面を除くマスクと接続の SHA-256 を保存し、生成時と接続が違う場合は読み込みを拒否する。現在の復元検証は同じ SciPy 環境での確認であり、Android / iOS での再構成と配布形式の採用は未確定。誤差上限・共有境界・欠損・保存と復元を単体テストで、法線の平面保持とばらつき低減を `node tools/terrain/test_normal_shading.cjs` で確認する。

傾きが 45 度以上のときは、視点からの奥行きに応じて複数のデータレベルを同時に読み込む。手前は細かく、奥は粗くし、方角を変えたときも読み直す。異なるレベルの境界は下向きの裾で隙間をふさぐ。これはプレビュー用の方式で、境界の標高を連続に補間する処理はまだ入れていない。全国のポリゴン SQLite を使い、不規則 TIN の固定縮尺の比較画面には適用しない。

水平に近い視点ではカメラ周辺を追加で一段細かくする。追加する範囲は表示幅の 10% 以内、最大 4 km とし、全国を高精細に読み込むことを避ける。傾きは 90 度の水平まで指定できる。自己影の補正には地形の簡略化誤差を使い、影の境界は重み付きの 25 点で平均する。境界の補正によって小さな地形が落とす影は薄くなる場合がある。

「山頂名」で、アプリと同じ配布山頂データの山名を表示できる。緯度・経度・標高を地形と同じ式で投影し、重なる名前は近い山を優先して間引く。標高のない山頂は表示しない。山頂データは `build/terrain-peaks.json.gz` に保存する。「地形による遮蔽」がオンのときは、カメラと山頂の間に地形の面が交差する山頂名を除外する。地形を区画に分けて視線が通る区画だけ調べる。簡略化した地形と山頂標高のずれによる誤判定を抑えるため、地形の簡略化誤差（最低 5 m）を許容する。読み込み範囲外の地形による遮蔽は判定しない。山頂データの出典は © OpenStreetMap contributors（ODbL）。

レベル 13 は入力格子に対する誤差上限 35 m で生成する。既存のレベルを作り直さず追加するときは、次のように別ファイルへ生成・統合し、検証後にプレビューの DB を差し替える。統合はタイルとレベル別の誤差情報を保持し、SQLite の整合性と gzip 展開後の SHA-256 を確認する。

```sh
python tools/terrain/polygon_dem.py --levels 13 --output build/terrain-mesh-level13.sqlite3 --workers 8
python tools/terrain/merge_mesh_levels.py --base build/terrain-mesh.sqlite3 --addition build/terrain-mesh-level13.sqlite3 --output build/terrain-mesh-with13.sqlite3
```

レベル 13 を全国 28,854 タイル追加した結果、7 段階の合計は 147,102 タイル。レベル 13 の圧縮済みタイル本体は 90,713,870 バイト。統合した SQLite は 390,987,776 バイト、配布用 gzip は 370,995,558 バイトで、追加前から 91,449,744 バイト増えた。既存の全タイルが変わっていないことと、SQLite の整合性、gzip 展開後の SHA-256 の一致を確認した。槍ヶ岳周辺 3 タイルの独立した三角形補間による標高誤差は最大 20 m だった。

## 元の海域ポリゴンから作る海岸線

レベル 4・6・8・9・10・11 の輪郭は、国土地理院の元ベクトルタイルの海域ポリゴンから生成する。DEM の標高あり・なしの境界や、粗い格子の外周の平滑化は輪郭に使わない。レベル 12・13・14 の地形は既存データを保持する。

`coastline_source.py` は、DEM のレベル 10 がある全国 733 タイルに対応する国土地理院最適化ベクトルタイルを保存する。海域の `WA`（分類コード 5100〜5199）を除いた陸域を取り出す。湖や河川は海域として除外しない。PMTiles の更新情報を記録し、異なる更新時点のデータを混ぜない。海域と海岸線の分類は [国土地理院の分類表](https://maps.gsi.go.jp/help/pdf/vector/optbv_featurecodes.xlsx)、元データの配信と利用条件は [公式リポジトリ](https://github.com/gsi-cyberjapan/optimal_bvmap)を参照する。

```sh
python tools/terrain/coastline_source.py
python tools/terrain/coast_mesh.py
```

`coast_mesh.py` はタイル間の微小な座標差を 1 cm の精度でそろえて結合し、島と海の穴の包含関係を保ちながら輪郭を簡略化する。Visvalingam–Whyatt 法の許容値はレベル 4 が 250 m、6 が 100 m、8 が 40 m、9 が 20 m、10 が 10 m、11 が 5 m。この値は除く三角形の面積の平方根に相当する指標で、輪郭の最大位置誤差ではない。

既存の地形の面を海岸線で切り、海岸付近で新たに陸地となる部分へ面を足す。内陸の DEM 欠損は埋めない。内部の標高は各レベルの元の面から補間する。海岸線と、DEM がない追加の沿岸の陸地は海抜 0 m とするため、海岸付近の高さは近似となる。タイル境界の高さは同じ標高列から補間する。海岸線を採用しても、標高の細かさは選択した地形レベルのまま。

生成先は `build/terrain-coast-mesh.sqlite3` とその gzip。YMP4 は小数の XY 座標・5 m 刻みの標高・三角形の接続を xz 圧縮して保存する。内部の地形は既存の YMP2 を残す。地形データの schemaVersion は 2、encoding は YMP2+YMP4。配布 manifest は変更していない。現在はローカルプレビューの実装で、Android / iOS の読み込みは未実装。

以前の `precompute_outlines.py` と `terrain-outlines.sqlite3` は、DEM の外周を後から平滑化する比較試作用。元データのサイズ・更新日時が一致しないキャッシュは使用しない。海岸線から作り直した地形にはこの差分を使わず、表示時に輪郭の平滑化や面の作成も行わない。

山頂名の遮蔽は近い表示候補 300 件以内を対象にし、名前同士の重なりを除いたあとに判定する。

全国の低レベル 628 タイルを海岸線に沿って再生成した。共有境界の 219,397 頂点を検査し、海岸線がタイル境界に重なる 2 箇所は両側を海抜 0 m にそろえた。レベル 12・13・14 のタイル本体は変更していない。生成した全国地形は SQLite が 410,753,024 バイト、gzip が 390,773,529 バイト。追加前の gzip から 19,777,971 バイト増えた。SQLite の整合性、全ての海岸メッシュの有限値・面のつぶれ・頂点番号、gzip 展開後の SHA-256 の一致を確認した。旧データは `build/terrain-mesh-before-vector-coast.sqlite3` に退避し、新データを `build/terrain-mesh.sqlite3` へ反映した。東京湾のレベル 4・8 と、湾内・湾口・横浜・千葉・羽田の陸海判定を確認した。

## レベル 9・11 の追加

レベル 9・11 は、元の各レベルの標高格子から別ファイルへ生成し、海岸線を組み込んでから統合する。入力格子に対する標高の簡略化誤差上限は 9 が 225 m、11 が 100 m。元 DEM の誤差、概略格子への平均化、海岸付近の処理の誤差は別。統合では既存のレベルと出典を保持し、海岸線の取得時点が異なるデータは混ぜない。距離別の切り替えは番号を 2 ずつ動かす方式から、存在する隣のレベルを使う方式に変更した。

## 全国の河川・徒歩道・県境

`national_lines.py` は、国土地理院最適化ベクトルタイルの PMTiles 索引から、存在するレベル 14 の全国タイルを列挙する。DEM の取得範囲だけで絞らず、離島を含む配信元の全タイルを対象にする。連続した約 8 MB の範囲をまとめて取得し、不要な建物などのレイヤーを除いて保存する。元データの取得と段階への変換は、完了済みの処理を飛ばして再開できる。取得元の更新時点や生成設定が変わった場合は、途中の出力と混ぜず停止する。

```powershell
build/terrain-venv/Scripts/python.exe tools/terrain/national_lines.py
# 元データの取得だけ、または保存済み元データからの変換だけを行う
build/terrain-venv/Scripts/python.exe tools/terrain/national_lines.py --stage acquire
build/terrain-venv/Scripts/python.exe tools/terrain/national_lines.py --stage generate
build/terrain-venv/Scripts/python.exe tools/terrain/verify_national_lines.py
```

出力は `build/terrain-national-lines.sqlite3` と配布用 gzip。取得元の範囲キャッシュ・抽出済み元データ・進捗・ログは `build/terrain-national-lines/` に保存する。既存の地域限定データは残す。全国の水域の面は今回の対象に含めず、取得済みの富士山周辺の水域と組み合わせて表示する。アプリ本体への組み込みやデータの公開はまだ行っていない。

### SQLite の中継とブラウザー内での復元

動的ビューワのサーバーは、HTML・JavaScript の配信と、SQLite の検索・中継だけを行う。表示範囲と地形レベルの選択、圧縮データの展開、座標変換、タイルの接続、レベル境界の裾、水面と湖岸の生成、河川・徒歩道・県境の標高補間は、ブラウザーの Web Worker で行う。サーバーは BLOB の圧縮・展開・再構成を行わず、SQLite に保存されている値をそのまま返す。全国データの再生成は不要。

ブラウザーは地形を先に表示し、追加レイヤーを後から反映する。地形と追加レイヤーは別の Worker を使い、水域の計算中にも移動先の地形を取得・復元できる。表示地域が変わると、計算中の古い追加レイヤーを中断する。復元済みの地形を追加レイヤーの Worker に渡すため、その地形を再びサーバーから取得する必要はない。地形の復元キャッシュは概算 64 MiB、組み立て済みの地域は 2 件まで保持する。これはブラウザー全体のメモリ上限ではない。

| URL | 返す内容 |
|---|---|
| `/sqlite/metadata` | 地形・全国の線・地域限定の水域・有効な輪郭差分の付随情報 |
| `/sqlite/overview?level=4` | 指定したレベルの全国の BLOB すべて（4〜8 を指定可能） |
| `/sqlite/mesh?tiles=z,x,y;…` | 指定したタイルの `YMP2` / `YMP4` BLOB。最大 256 タイル |
| `/sqlite/outline?tiles=z,x,y;…` | 元データと一致する輪郭差分の gzip BLOB |
| `/sqlite/lines?level=…&west=…&south=…&east=…&north=…` | 指定範囲とレベルに重なる線の `YVL1-gzip` BLOB |
| `/sqlite/water?west=…&south=…&east=…&north=…` | 指定範囲に重なる水域・水涯線の gzip GeoJSON BLOB |
| `/sqlite/normals` | 全国背景の陰影マップ（gzip RG8 の元 BLOB） |
| `/sqlite-peaks` | 保存済みの山頂名ファイル |

BLOB の応答は `YSQ1`、little-endian uint32 の JSON ヘッダー長、行の付随情報と BLOB 長を示す UTF-8 JSON、元の BLOB を順に並べた形式。BLOB を base64 や描画用配列に変換しない。旧 `/terrain-data` API は HTTP 410 を返す。静的 HTML を生成する既存の Python 処理は比較・検証用に残しているが、動的ビューワのリクエストからは呼ばない。

XZ の展開には `xz-decompress` 0.2.3、ポリゴンの交差・差分には `polygon-clipping` 0.15.7、三角形分割には `earcut` 3.2.4 を使う。スクリプトと XZ 展開用 WebAssembly は `vendor/` に同梱し、実行時に CDN へ接続しない。ライセンスの表示と本文も同じ場所に置く。参照先は [xz-decompress](https://github.com/httptoolkit/xz-decompress)、[polygon-clipping](https://github.com/mfogel/polygon-clipping)、[earcut](https://github.com/mapbox/earcut)。

右下の「表示データ」は、現在の地形・線・水域で参照した圧縮 BLOB の合計と、描画用配列のバイト数を示す。「累計取得」は目録や山頂名も含む取得完了済みの応答本文の合計で、キャッシュから再表示した分は加算しない。取得中は SQLite の応答待ち、受信量、ブラウザー内の処理内容と経過時間を更新する。描画用配列の値には法線・ワイヤーフレーム・キャッシュなどを含めず、ブラウザーや GPU の総メモリ使用量を示すものではない。

全国背景はレベル 4 の地形とノーマルマップを合わせて 830,382 バイト。地域の詳細地形・追加レイヤーはその後に取得する。範囲・縮尺・視点によって累計取得量は変わる。水域が密な範囲では、端末側での計算時間とメモリ使用量は大きくなる。

### 最高詳細の三角形から LOD を作る地域試作

以前の地域試作では、槍ヶ岳周辺の DEM10B・レベル 14 から不規則な三角形を作り、同じ形状から QEM で面を段階的に減らした。生成処理は現在 `tools/terrain-rs/` に移した。低レベル用の標高配列を平均化してから再構築する方式とは別の比較試作で、全国の既存データは変更していない。QEM の原典は [Garland・Heckbert の論文](https://www.cs.cmu.edu/~garland/quadrics/) を参照。

最高詳細は標高格子に対する近似誤差 10 m、保存時の標高刻み 5 m で作る。地域内のタイルを結合してから削減するため、内部の元タイル境界は固定しない。外周・穴の境界と、周囲 250 m でも極大・極小になる標高差 40 m 以上の候補を固定する。境界を保った辺の縮約だけを許可し、面の裏返りや非多様体を防ぐ。端点の一方へ縮めるため、保存された低レベルの頂点は高レベルの頂点の部分集合になる。

各段階の目標は面数の半減だが、最高詳細の頂点と面中心に対する標高差も制限する。上限は既存のレベル別許容値を使う。これは標本点での上限であり、連続した面全体や元 DEM に対する厳密な誤差上限ではない。QEM の評価値だけで標高精度を保証する扱いにはしない。

```powershell
build/terrain-venv/Scripts/python.exe tools/terrain/verify_qem_prototype.py
```

出力済みの `build/terrain-qem-final/lod.sqlite3` を上書きしない。再生成するときは `--output` で別の保存先を指定する。SQLite はレベルごとの頂点・三角形の接続を gzip バイナリで持つ地域検証用の形式。全国配布用のタイル構成はまだ確定していない。

QEM の単体テストでは、段階的な削減、境界・穴・最高点の保持、平面の再現、最高詳細に対する標本点の誤差制限、不正な面の除外を確認する。保存データは全レベルで外周の辺・面積・向き・標本点の被覆・誤差を照合する。ブラウザーではレベル変更、旧方式との比較、三角形表示、視点の引き継ぎを確認する。


### 配信用タイルをまたぐ全国 QEM メッシュ

全国 QEM の生成処理は `tools/terrain-rs/` の Rust CLI に移した。元 DEM の展開、不規則 TIN、極値の保持、海岸線の簡略化と分割、QEM、区画の接続、SQLite 保存、進捗保存、全体検証を一つの実行ファイルで行う。Python の子プロセスは使わない。SQLite は実行ファイルに同梱し、海岸線の処理には GEOS 3.14 の C API を直接使う。

最高詳細の DEM10B からレベル 14 を作り、子メッシュを結合して 13 → 4 を生成する。処理区画のズームは `max(2, level - 2)`。一つのメッシュが複数の配信用タイルをまたぎ、配信用の境界では面を切らない。低レベルの座標も最高詳細の格子の角を基準とし、平均化した標高配列には戻さない。

元 DEM と既存の Python 出力を保ち、新しい全国データは `build/terrain-national-rust.sqlite3` に出力する。旧版の保存済み 372 区画は混在させず、Rust 版で生成し直す。保存形式は既存の YMP4 と同じで、ブラウザー側の復元処理をそのまま使える。

`build.ps1` は通常の Cargo、または `build/rust-tools/` のローカル環境を使う。GEOS の DLL と依存 DLL は `build/rust-native/` に置く。別の場所を使う場合は `TERRAIN_GEOS_DIR` を指定する。ビルド済みの生成器は Python のインストールに依存しない。HTML を配信する既存の Python サーバーと、過去の比較データを読むツールは残している。

区画ごとにトランザクションを確定し、同じコマンドで保存済みの区画を飛ばして再開する。元データと海岸線の大きさ・更新日時が変わった場合や、別の生成器の出力には追記しない。開始時に空き容量が 5 GiB 未満、実行中に 2 GiB 未満なら停止する。並列数の上限はレベル 14〜11 が指定値、10〜8 が 2、7〜4 が 1。

進捗は出力と同じ場所の `.progress.json` に保存する。`completedLevels`、処理中のレベルの区画数、経過秒数、WAL を含む SQLite のサイズ、空き容量を記録する。失敗時には `failed` と原因を保存する。各レベルの共有辺をそろえ、全 11 レベルの SQLite・頂点・面の向き・標高誤差・共有辺の確認が通ったときだけ `generationComplete` を真にする。途中のデータを完成済みとして配布しない。

QEM は投影面の裏返りや穴の閉塞を避け、境界と選んだ極値を保持する。削減結果の標本点での誤差や復元結果が不正なら入力形状を保持する。標高誤差は入力の頂点・面中心で測った段階誤差の累積で、海岸線の移動と境界調整を除く。元 DEM の連続面全体に対する厳密な上限ではない。

海岸線は島と穴を一つの被覆として簡略化する。接する穴を持つ輪郭で GEOS の三角形化が失敗するときは、保存する座標の精度以下での調整、輪郭の分割、Rust の Earcut を試す。別方式の結果は元の輪郭との差分面積と面の重複を検査し、確認できなければ停止する。内陸の DEM 欠損を陸地で埋めない。

## ハイトマップと法線 PNG の地域比較

ポリゴン方式を残したまま、槍ヶ岳周辺の標高を PNG に保存する別の試作を追加した。次のコマンドで変換し、専用サーバーを起動する。

```powershell
build/terrain-venv/Scripts/python.exe tools/terrain/heightmap_export.py
build/terrain-venv/Scripts/python.exe tools/terrain/heightmap_levels.py
build/terrain-venv/Scripts/python.exe tools/terrain/heightmap_server.py --port 61440
```

`http://127.0.0.1:61440/heightmap` で開く。元データは `build/terrain-yari-preview-source.sqlite3`、出力先は `build/terrain-heightmap-yari/`。元のポリゴン生成器と SQLite は変更しない。PNG への変換は比較用の Python スクリプトで行い、ブラウザー側で格子を作って標高テクスチャを参照する。

標高は 4096×4096 点で、R・G に 16 bit 値、B に有効な標高かどうかを保存する。高さは `R + 256*G + heightOffset` m。既存の 5 m 単位の標高に対する PNG 変換の追加誤差は 0 m。元の DEM に対する測定誤差や量子化誤差がなくなるわけではない。PNG は色補正とアルファの乗算を無効にして GPU に読み込む。

法線は東・北方向を R・G に保存し、上向き成分をシェーダーで復元する。1024×1024 と 2048×2048 を切り替えられる。標高と法線の解像度、描画格子の間隔は独立している。法線 PNG、標高から GPU で計算する法線、三角形の面の陰影を同じ視点で比較できる。法線 PNG の解像度を初めて切り替えたときだけ追加取得し、陰影方式の切り替えでは取得し直さない。

実測の PNG 本体は標高 4,273,327 bytes、法線 1024 四方 1,946,809 bytes、法線 2048 四方 7,350,629 bytes。既定の合計は 6,220,136 bytes で、同範囲のポリゴン L14 の 10,854,736 bytes より約 43% 小さい。圧縮済み標高の元形式 YMD1 は 2,816,412 bytes なので、PNG 自体が最も小さいわけではない。

この試作では約 30 km 四方を一括取得する。自動 LOD は視点距離に応じて地域全体の描画格子を切り替える簡易版で、距離ごとの細分化・段階的な形状補間・全国の逐次取得は未実装。格子の切り替えで形状が跳ねる場合がある。照明の方向と強さ、移動・拡大縮小・方角・傾きを操作できる。地形が落とす影、水域、山名、全国用の保存・配布形式はこの比較の対象外。端末での速度と GPU メモリー使用量は別途確認が必要。

検証は `python -m unittest discover -s tools/terrain -p test_heightmap_export.py` と `node tools/terrain/test_heightmap_viewer.cjs`。標高と欠損の PNG 往復、法線の寸法、描画、法線・格子・解像度の切り替え、マウス操作を確かめる。


PNG 試作の L14〜L4 は `heightmap_levels.py` で生成する。`levels/<レベル>/` に標高と大小 2 種類の法線 PNG、`levels.json` に全レベルの容量と元の L14 に対する最大復元誤差を保存する。標高は各レベルを元の L14 から直接面積平均して 1 m 単位に丸め、法線も L14 の向きを求めてから直接平均する。低いレベルの高さを順に削減して誤差を積み重ねる方式ではない。PNG の量子化誤差と、解像度を下げて失う地形の誤差は区別する。

同じ約 30 km 四方について、標高は L14 の 4096 四方から L4 の 4 四方まで減る。これは地域分を切り出した寸法で、全国データの 1 タイルを 4 四方にする仕様ではない。低いレベルでも陰影を比較できるよう、標準の法線 PNG は最低 128 四方、詳細版は最低 256 四方を保つ。データレベルと描画格子の間隔は別々に選べる。標準法線を使った全 11 レベルの合計は 11,535,959 bytes。詳細版の法線も含めた保存量は `levels.json` の `totalAllPNGBytes` を参照する。

ビューワーの「データレベル」で同じ視点のまま L14〜L4 を切り替えられる。`/heightmap?level=12` のように指定しても開ける。選択中のレベルの容量と、実際に取得した PNG の累計を別々に表示する。全レベルの描画、視点の保持、最大復元誤差の計算、元データから直接平均することと地域の大きさを保つことをテストした。ポリゴン方式と、従来の単一レベル PNG は残している。


法線 PNG は標高レベルごとの大小 2 種類に加え、2048・1024・512・256・128・64・32・16・8・4 四方の共用データを `normals/<寸法>.png` に生成する。すべて元の L14 の法線から直接平均する。`levels.json` の `normalVariants` に寸法・容量・URL を保存する。ビューワーは共用データを使い、法線の解像度を標高レベルと独立して保持する。同じ PNG は全標高レベルで使い回し、再取得しない。取得累計と、現在選択中の標高・法線の容量を別々に表示する。従来のレベル別 PNG とポリゴン方式は残す。


同じ比較画面の「形状の方式」で、ハイトマップとポリゴン L9・L10 を切り替えられる。`/heightmap?geometry=polygon9&level=9` でポリゴン L9 から開く。ポリゴンは `build/terrain-yari-local.sqlite3` の圧縮 BLOB を中継し、ブラウザーで復元する。頂点と面は変更せず、既存のポリゴン SQLite と生成器も保持する。両方式で視点・光源・法線 PNG・照明計算を共用し、同じ地上位置から同じ法線を参照する。比較する地域の外側は描画しない。地形が落とす影はこの比較には含まない。

ハイトマップ側のデータレベルと、法線の解像度は切り替え後も保持する。例えばハイトマップ L12 とポリゴン L10 を往復して比較できる。ポリゴンでは格子の間隔設定は使わない。形状・法線・GPU 計算用の補助標高の容量を分けて表示し、現在使うデータの合計と実際の取得累計も区別する。ポリゴンと法線 PNG は取得・復元済みのものを再利用する。ポリゴン＋法線 PNG の表示では、不要な標高 PNG を取得しない。GPU で標高から法線を計算する場合は補助標高を取得し、その容量も合計へ加える。

`node tools/terrain/test_heightmap_polygon_compare.cjs` で、L9・L10 の面数と容量、法線適用による表示変化、視点・照明・法線解像度の保持、ハイトマップ側の比較レベルの保持、データの再利用を確認する。ポリゴンは L9 が 59,456 三角形・393,387 bytes、L10 が 118,878 三角形・804,971 bytes。法線 PNG の容量は両方式で同じ。


## 地形圧縮方式の比較

槍ヶ岳周辺の同じ範囲で、法線の ASTC、ポリゴンの meshoptimizer、標高の YMD1・LERC・差分圧縮を比較する。既存の SQLite・PNG・生成器は残す。圧縮と誤差の計測は Rust、サーバーはファイルの中継、復元と描画はブラウザーで行う。

```powershell
build/terrain-venv/Scripts/python.exe tools/terrain/setup_codec_tools.py
tools/terrain-rs/build.ps1 -Codecs -Test
tools/terrain-rs/build.ps1 -Codecs
tools/terrain-rs/run-codecs.ps1 --part all
build/terrain-venv/Scripts/python.exe tools/terrain/heightmap_server.py --port 61440
```

生成前に上記の PNG 試作と地域ポリゴンを用意する。出力は `build/terrain-codec-comparison/`。`--part normals`・`mesh`・`heights` で個別に再生成できる。`build.ps1 -Codecs` は比較用バイナリだけをビルドし、全国生成用の実行ファイルを置き換えない。

- 比較画面: `http://127.0.0.1:61440/heightmap?geometry=polygon9&level=9&meshCodec=meshopt-f32-zstd&normalCodec=astc4-zstd`
- 容量・誤差・復元時間の一覧: `http://127.0.0.1:61440/codec-report`
- 計測 JSON: `http://127.0.0.1:61440/codecs/report`

比較画面ではポリゴン圧縮、標高圧縮、法線圧縮を切り替える。視点・光源・法線解像度を保ち、現在選択したファイル容量と実際の累計取得量を別に表示する。階層差分は親のファイルを含めた必要量で比べる。ブラウザー用デコーダーの初回取得量は、地形データの容量に含めない。

法線は 2048 四方〜4 四方の 10 解像度それぞれに、ASTC 4×4・6×6・8×8 の計 30 種類を生成する。線形色の RA に XY を格納し、KTX2 と KTX2＋Zstd を保存する。元の XY から復元した法線との角度誤差を測る。ASTC 非対応の GPU では事前復号 PNG で画質を確認し、その旨を画面に表示する。この場合の取得累計には PNG も加わる。ASTC の GPU 直接参照は対応端末で別途確認が必要。

ポリゴンは L4〜L14 の全 11 レベルを生成する。`meshopt-f32` は従来ビューワーが GPU に渡す Float32 頂点をビット単位で保持し、面の接続・向きも照合する。`meshopt` は追加で 0.5 m 単位へ丸めるため、細い面がつぶれたり反転したりする場合がある。件数を一覧と比較画面に表示する。両方に Zstd の有無を用意する。階層差分は共通の頂点群と面の削除・追加を保存する実験で、頂点分割だけを保存する厳密な Progressive Mesh ではない。

標高も L4〜L14 の全レベルについて、YMD1＋XZ（1 m・5 m）、YMD1＋gzip、LERC（最大誤差 0・1・2.5・5 m）、2 次元差分＋Zstd、親レベルの双線形補間からの残差＋Zstd の 9 種類を生成する。欠損位置を保持する。追加誤差の比較元は各レベルの PNG であり、元の DEM に対する誤差や LOD の縮小誤差とは別。可逆な方式は各 PNG の標高に一致することを確かめる。

### 槍ヶ岳周辺の実測値

容量はファイル本体の 10 進 MB。SQLite の空きページや配布用アーカイブの管理情報は含まない。

この地域では、頂点を保持する meshoptimizer 圧縮でも容量を減らせた。ASTC は 4×4 を画質比較の候補とし、6×6・8×8 は陰影の劣化を確認して判断する。Zstd の追加効果は法線では小さく、6×6・8×8 はヘッダー分だけ増えた。LERC と階層差分は今回の容量では有利にならなかった。全国の地形や実機で同じ結果になる保証はないため、全国の配布形式はまだ変更しない。

復元時間はメモリー内で 3 回測った中央値。ASTC の処理時間には外部プロセス起動と PNG 入出力が含まれるため、メッシュ・標高の計測と直接比較しない。階層形式は親を含めた時間も記録する。画面の FPS はこの PC の比較用描画の値で、スマートフォンの性能を表す値ではない。

比較用ツールは Arm astcenc 5.7.0、meshopt crate 0.7.0（meshoptimizer 1.3.0）、LERC 4.2.0、ブラウザーの fzstd 0.1.1 を使う。セットアップ時に配布物の SHA-256 または SHA-512 を照合し、ライセンスと出典を `build/terrain-codec-tools/` に保存する。KTX2 は単一レベルの ASTC コンテナーを Rust で作り、ペイロードの一致をテストする。

検証は Rust の比較用テスト 10 件と、`node tools/terrain/test_terrain_codecs.cjs`。全生成ファイルの復元・誤差・面の接続を Rust で照合し、ブラウザーでは L9・L10 の全メッシュ方式、法線の全圧縮方式、L10 の標高全方式について、描画・視点の保持・欠損・標高誤差を確認する。元の PNG とポリゴン比較のテストも残す。

`node tools/terrain/test_terrain_codecs_large.cjs` では L14 の YMD1＋XZ・LERC 可逆・階層残差を復元し、4096 四方の全画素と欠損位置が PNG に一致することも確認する。

「推奨設定にする」で、ポリゴン L10、頂点可逆 meshoptimizer＋Zstd、法線 1024 四方の ASTC 4×4＋Zstd、補助標高 YMD1＋XZ（1 m 単位）をまとめて選ぶ。陰影を法線テクスチャに戻し、視点と光源、ハイトマップ側の比較レベルは保持する。ASTC 非対応 GPU の画質確認には従来どおり事前復号 PNG を使う。


### LOD ごとのポリゴン法線との比較

```powershell
tools/terrain-rs/build.ps1 -Codecs
tools/terrain-rs/run-codecs.ps1 --part mesh-normals
```

`build/terrain-codec-comparison/mesh-normals/` に、槍ヶ岳周辺のポリゴン L4〜L14 それぞれから作った法線を保存する。各レベルに 2048 四方〜4 四方の 10 解像度の PNG と ASTC 4×4・6×6・8×8 の KTX2／KTX2＋Zstd を用意する。処理が完了したレベルは `report.json` に記録し、中断後の再実行では再利用する。元の SQLite と共通法線は変更しない。入力や生成方法を変更する場合は `--output` に別の出力先を指定して生成する。

各三角形の面積を重みにして頂点法線を求め、同じ位置の境界頂点を共有してから三角形の中で補間する。地上座標に対応する 2048 四方の画像に保存し、ほかの解像度はその画像から補間する。ポリゴンを覆わない画像の縁は隣の法線で埋めるが、ポリゴン自体は追加しない。座標系は従来と同じ東・北・上で、接線空間の法線マップではない。各 LOD の形状の傾斜を表し、詳細標高の凹凸を追加で焼き込まない。

比較画面の「形状の方式」で全 11 レベルのポリゴンを選び、「法線の生成元」で「詳細標高（全 LOD 共通）」と「表示 LOD のポリゴン形状」を切り替える。視点・光源・法線解像度・圧縮形式は保持する。法線の容量は選択中の画像の実サイズで更新し、LOD を変えると対応する法線も切り替わる。ハイトマップ表示時は従来の詳細標高の法線を使う。

`/heightmap?geometry=polygon9&meshCodec=meshopt-f32-zstd&normalSource=mesh&normalCodec=astc4-zstd` で L9 の形状に対応した法線から開ける。生成に使う形状は追加の 0.5 m 量子化を行う前の地域ポリゴンなので、比較には頂点可逆の方式を使う。もともとの LOD の形状誤差を修正する処理ではない。低い LOD では陰影も単純になる。

`node tools/terrain/test_mesh_normals.cjs` で、全レベルの選択と法線容量、同じ視点での表示差、PNG／ASTC の切り替え、取得済みデータの再利用を確認する。

法線の参照位置は共通の地域範囲と地上座標から求め、画像の実寸に合わせてテクセル中心へ変換する。LOD ごとの格子寸法で貼り付け位置が変わらないようにする。ポリゴンの描画範囲も同じ地上範囲で切り取る。


### 詳細法線の LOD への焼き込み

前項のポリゴン形状のみの法線は、比較用の「ポリゴン形状のみ」として残す。「詳細法線を表示 LOD に焼き込み」は、最も詳細な標高から求めた従来の法線を、各 LOD の滑らかな頂点法線を基準にした接線座標へ変換したもの。詳細法線の細かな陰影を保持する。

```powershell
tools/terrain-rs/build.ps1 -Codecs
tools/terrain-rs/run-codecs.ps1 --part baked-normals
```

出力は `build/terrain-codec-comparison/baked-normals/`。ポリゴン L4〜L14 の各 10 解像度について PNG と ASTC の比較データを保存する。元の共通法線とポリゴン形状のみの法線は変更しない。`normalSource=baked` で焼き込み方式から開ける。推奨設定ボタンもこの方式を選ぶ。

焼き込みと描画の両方で、Float32 の描画頂点から面積重み付きの頂点法線を求め、重複する境界頂点を共有する。頂点法線を三角形の中で補間し、東方向を接平面へ投影した接線と、それに直交する方向を使う。同じ基準で詳細法線を変換・復元する。標準の MikkTSpace とは異なる、この地域比較用の接線基準である。

基準面の向きと詳細法線の向きが大きく異なる部分も保存するため、符号付き XYZ を RGB に格納する。ASTC も RGB を保存し、従来の XY／RA と正の Z の再構成は使わない。基準の頂点法線はブラウザーで計算するため、追加の法線画像や頂点法線ファイルを取得する必要はない。GPU には追加の頂点法線バッファを用意する。

PNG に焼き込んだ法線を地上座標へ戻したときの角度誤差を `report.json` に記録する。この誤差は同じ解像度の共通法線との比較で、GPU の補間や ASTC の圧縮誤差とは別。低い解像度では基準面の変化と画像補間によるずれが出る場合がある。

従来の共通法線は地上座標の向きを直接保存しているため、正しく復元した焼き込み方式は近い陰影になる。焼き込みによってポリゴンの輪郭や標高が詳細になるわけではない。陰影だけを置き換える比較であり、地形が落とす影は含まない。

`node tools/terrain/test_baked_normals.cjs` で、L9 の共通法線と焼き込み法線の画素差が「形状のみ」の差より小さいこと、全 LOD の復元と容量、PNG／各 ASTC の表示、視点の保持を確かめる。

比較画面の「現在の設定」は、使用中の形状・法線の方式と解像度、圧縮形式、容量、光源、視点を一行で表示する。「コピー」で全文をコピーでき、欄のクリックでも全選択できる。使わない法線画像の設定は省き、ASTC 非対応時の PNG による代替表示も記載する。


### 標高の ASTC 比較

```powershell
tools/terrain-rs/build.ps1 -Codecs
tools/terrain-rs/run-codecs.ps1 --part height-astc
```

`build/terrain-codec-comparison/height-astc/` に L14〜L4 の各 2 種類、計 22 種類を保存する。各レベルの元 PNG から、256 四方ごとに最低標高と標高差を求め、1 成分の UNORM8 へ正規化して ASTC 8×8・12×12 に圧縮する。両方式とも Zstd を加える。R・G に分割した標高をそのまま圧縮する方式ではない。

ASTC のタイルは 264 四方で、256 四方の本体の外に 4 点ずつ余白を置く。最低標高・標高差・寸法と ASTC 本体を比較用パケット YHA1 に格納し、欠損情報は別の可逆な Zstd データとして同梱する。GPU ではタイルを 2D 配列テクスチャ、最低標高と標高差を RG32F の管理テクスチャとして参照する。欠損がなければ GPU のマスクは使わず、ある場合は 1 画素 1 bit のマスクを R8 に詰めて参照する。

比較画面の「標高形式」で選ぶ。`/heightmap?geometry=height&level=14&heightCodec=height-astc12` で L14 の 12×12 から開ける。ASTC 対応 GPU では圧縮したまま標高を参照する。未対応 GPU、または配列レイヤー数の上限を超える環境では、事前復号した PNG と管理値から標高を復元して R32F で描画する。代替表示の実際の転送量には PNG も加える。選択中の容量は比較用パケットの容量とし、代替 PNG は含めない。画面と一行の設定欄には代替表示の有無と標高誤差を記載する。

槍ヶ岳周辺 L14 のファイル本体は、8×8 が 3,861,089 bytes、12×12 が 1,674,841 bytes。各レベルの元 PNG に対する追加最大誤差は約 24.84 m／36.20 m、RMSE は約 1.88 m／2.65 m、95% の画素の誤差は約 3.90 m／5.29 m。可逆な YMD1＋XZ の 2,821,867 bytes と比べると、8×8 は大きく、12×12 は小さい。低い LOD では 1 タイルの地上範囲と標高差が大きくなり、誤差も大きくなる。既定の配布方式には変更しない。

`/codec-report` にレベル別の容量・GPU の ASTC 本体・最大誤差・RMSE・P95・境界の誤差段差・最高標高の差を表示する。誤差の比較元は同じ LOD の PNG で、元の DEM の測定誤差、元データの量子化、LOD の縮小誤差とは別。正規化だけの誤差は `report.json` の `normalizedOnly` に記録する。最高地点の移動距離は、比較元の最高標高が複数画素にある場合、最初の最高画素を基準にした値である。

格子の境界では、両側の区画が同じ地上サンプルを同じタイルから参照するため、同じ頂点に別々の標高を割り当てない。ただし、隣り合う標高サンプルの圧縮誤差が異なれば、傾斜や段差の見え方は変わる。L14 の境界誤差の段差・最大は 8×8 が約 15.29 m、12×12 が約 24.53 m。この指標は亀裂の幅ではない。

`node tools/terrain/test_height_astc.cjs` で全 22 種類の標高誤差・欠損・境界指標と描画を確認する。ASTC 非対応の PC でも、復号済みテクセルを通常の配列テクスチャに入れ、GPU 参照と R32F 参照の描画を比較する。境界をまたぐ欠損も置いてビットマスクを確かめる。この検証はタイル参照シェーダーの確認で、ASTC ブロックのハードウェア復号を確認したものではない。Android / iOS 実機での確認は別途必要。


### JPEG XL の検討

```powershell
build/terrain-venv/Scripts/python.exe tools/terrain/setup_codec_tools.py
tools/terrain-rs/build.ps1 -Codecs
tools/terrain-rs/run-codecs.ps1 --part jxl
```

公式の libjxl 0.12.0 の Windows 静的バイナリを固定 SHA-256 で確認して使う。計測の処理は Rust、符号化・復号は公式 CLI の cjxl／djxl。出力は `build/terrain-codec-comparison/jpeg-xl/`、結果は `/codec-report` の JPEG XL の表に表示する。既存の表示形式・配布形式は変更しない。

標高は代表レベル L14・L12・L10・L9 について、16 bit の単一グレースケールとして圧縮する。1 m 単位の可逆、10 m 単位へ丸めたあと可逆、正規化して非可逆 d=0.1・0.5・1 の計 20 通りを測る。L14 は 256 四方に分割した可逆と d=0.5 も測る。最低標高・スケール・可逆な欠損マスクを比較用パケット YJH1 に保存し、容量にはこれらの管理情報も含める。

法線は 1024 四方の共通法線と焼き込み L9・L10 を対象に、可逆と d=0.1・0.5・1 の計 12 通りを測る。全体で 34 通り。線形色の指定を符号化と復号の両方に与え、標高の値や法線の成分が表示用の色補正で変わらないようにする。d=0 は復元画素を入力と照合する。d は知覚的な距離の指標で、標高や法線の誤差上限を保証する値ではない。

同じ槍ヶ岳周辺 L14 の標高を 256 四方に分割した場合、可逆 JPEG XL は 1,827,495 bytes・追加誤差 0 m、d=0.5 は 1,057,025 bytes・追加最大誤差約 21.38 m・RMSE 約 1.69 m。既存の YMD1＋XZ は 2,821,867 bytes・追加誤差 0 m、ASTC 12×12＋Zstd は 1,674,841 bytes・追加最大誤差約 36.20 m・RMSE 約 2.65 m。地域一括の JPEG XL は可逆 1,904,090 bytes、d=0.5 は 325,038 bytes・追加最大誤差約 45.90 m だが、地域一括とタイル分割を同じ配信単位として比較しない。

焼き込み L9 の 1024 四方法線は、JPEG XL 可逆が 2,082,436 bytes、d=0.5 が 645,049 bytes・追加角度誤差 P95 約 6.66°。同じ法線の ASTC 4×4＋Zstd は 1,022,715 bytes・P95 約 5.17°。JPEG XL の復元結果を RGBA8 で GPU に送る場合は約 4.19 MB、ASTC 4×4 の GPU 本体は約 1.05 MB になる。ファイル容量と GPU メモリーを分けて判断する。

JPEG XL は配信・保存用の有力な候補だが、GPU では通常のテクスチャへ復元して使う。現在のアプリの対象は Android API 26 以降・iOS 15 以降なので、OS 標準の画像処理への依存を避け、共通デコーダーで数値と色空間を管理する構成を検討する。Rust の実装候補は [jxl-rs](https://github.com/libjxl/jxl-rs)。アプリへの導入・バイナリ容量・実機の復元速度・ピークメモリーはこの検討では確認していない。

復元時間は CLI の起動とファイル読み取りを含む 3 回の平均。出力画像の書き出しは除く。タイル版は区画ごとの CLI 起動を含む合計なので、アプリ内の連続復元の速度とは異なる。既存のメモリー内復元時間とも直接比較しない。

参考: [JPEG 委員会の JPEG XL](https://jpeg.org/jpegxl/index.html)、[libjxl と公式ツール](https://github.com/libjxl/libjxl)、[Android の標準対応形式](https://developer.android.com/media/platform/supported-formats)。

法線向けの追加比較では、共通・焼き込み L9・焼き込み L10 の 1024 四方を d=0、0.1、0.2、0.25、0.3、0.4、0.5、1 で計測する。JPEG XL と同じ元法線の ASTC の容量・角度誤差も比較ページに並べる。焼き込み L9 の d=0.3 は 877,043 bytes、追加角度誤差 P95 約 4.69°、最大約 20.85°。ASTC 4×4＋Zstd の 1,022,715 bytes・P95 約 5.17°より小さく、P95 も低かった。d=0.1 は 1,488,532 bytes・P95 約 1.96°。この比較は槍ヶ岳周辺の試料で、全国への容量比の適用や実機での陰影品質は未確認。可逆は元の PNG の画素を保持するが、元法線の生成・量子化誤差は残る。

### 全国 JPEG XL の生成

ポリゴン方式はコードを残し、2026-10-18 の指示で生成 DB・圧縮コピー・ポリゴンを埋め込んだ HTML・ポリゴン用の比較データを削除した。旧ポリゴン専用ビューワーは停止している。標高の元 DB、DEM、海岸線・水域・河川・登山道・県境のデータは保持する。

全国版は Rust の `national_jxl.rs` で、`build/terrain-lod.sqlite3` の L14〜L4 全 149,699 タイルを変換する。タイルは全レベルとも 256×256 画素。標高は整数メートルの 16 bit グレースケール JPEG XL 可逆とタイル最低標高、欠損は Zstd のビットマスク。元 DB にある量子化・レベル縮小の誤差は維持する。法線は線形 RGB の XYZ、JPEG XL d=0.3。これはポリゴン用の接空間法線ではなく、東・北・上の地理座標の法線である。

L14 の法線は隣接タイルを含む標高の中央差分で計算する。欠損の隣では中央の標高で補い、架空の崖を避ける。低レベルは子タイルの圧縮前の 8 bit XYZ 法線を 2×2 で平均・正規化して生成する。JPEG XL の非可逆誤差を親へ積み重ねないが、各段の 8 bit 丸めはある。海岸の有効範囲は標高の欠損マスクで判別する。

```powershell
& tools/terrain-rs/build.ps1 -Codecs
& tools/terrain-rs/run-codecs.ps1 --part national-jxl --root build/terrain-lod.sqlite3 --output build/terrain-jxl-national
```

出力 DB は `build/terrain-jxl-national/terrain-jxl.sqlite3`。`tiles` に z・x・y、標高 JPEG XL、最低標高、欠損マスク、法線 JPEG XL、法線の角度誤差を保存し、`metadata` に生成設定を保存する。既存 manifest の配布仕様へはまだ組み込んでいない。復号時は色補正をかけず線形データとして取り出す。

4 並列で生成し、各タイルの標高を復号して全画素を照合する。法線も復号して角度誤差を測定する。32 タイルごとにトランザクションで確定し、`progress.json` にレベル別の件数・標高／法線／マスクの容量を保存する。再実行は確定済みを飛ばす。重複起動をロックで拒否する。強制終了後のロックはプロセスが停止したことを確認してから除く。正常終了時は SQLite の整合性を検査し、中間法線を削除して VACUUM する。途中の DB 容量は中間法線を含むため、配布容量ではない。

小地域の全 11 レベル・19 タイルで、標高の可逆照合、法線の復号、再開時の重複防止、中間データ削除、DB 整合性を確認した。全国版の完了・容量は `progress.json` の state が complete になってから確認する。今回の生成に 15 分ごとの自動確認は使わない。

### JPEG XL の圧縮設定を画面で比較する

全国生成は 2026-10-18 の指示で停止し、確定済みタイルを保持している。再開は圧縮設定を決めてから行う。

`http://127.0.0.1:61440/heightmap?level=11` の「JPEG XL 動的比較」で、標高 d と法線 d を別々に指定し、「サーバーで圧縮して表示」を押す。0 は可逆、大きいほど圧縮を強める。現在の標高レベルと法線解像度で処理する。「元 PNG と比較」で元データと切り替える。視点・方角・傾き・照明は保持する。レベルや解像度を変えた場合は改めて圧縮する。

この比較では例外として、Python の比較サーバーから公式 cjxl／djxl を呼び出し、リクエストごとにエンコードとデコードを行う。処理は 256 四方のタイル単位、effort は 7。ブラウザーには復号後の標高 f32 と法線 PNG を渡す。画面の JPEG XL 保存容量と、表示用の転送量は異なる。標高の非可逆設定ではタイルごとに標高範囲を 16 bit へ正規化する。可逆設定は整数メートルの画素を照合する。法線は既存の共通法線 RG・上向き Z 復元方式を使う。全国生成の XYZ 法線とは格納方式が異なるため、容量をそのまま全国へ掛け合わせない。

保存先は `build/terrain-jxl-dynamic/`。各処理の保存容量は、タイル管理値を含む比較用パケットの実サイズ。標高パケットは YJD1（標高 JPEG XL と zlib の欠損マスク）、法線は YJN1（法線 JPEG XL）で、全国版 SQLite の容量とは区別する。圧縮前の PNG に対する標高の最大誤差・RMSE、法線角度の P95・最大値を表示する。処理時間は CLI 起動・画像の読み書きを含む。L14 はタイル数が多く時間がかかる。比較要求は同時に 1 件だけ受け付ける。

圧縮比較画面の「槍ヶ岳」「筑波山」ボタンで地域を切り替えられる。筑波山は `?region=tsukuba` でも指定できる。標高レベル・法線解像度・圧縮設定・陰影の設定を引き継ぎ、新しい地域の PNG を表示する。「サーバーで圧縮して表示」を押すと、選んだ地域のデータを動的に処理する。筑波山には比較用 ASTC などを生成していないため、PNG と動的 JPEG XL を選択できる。

筑波山の比較データは `python tools/terrain/heightmap_region.py` で保存済みの全国 DEM から生成する。L14 の 16×16 タイルを対象にし、L4〜L14 の標高 PNG と共通法線を `build/terrain-heightmap-tsukuba/` へ保存する。全国 JPEG XL の生成は再開しない。

### 全国表示で法線と縮小陰影を比較する

全国比較の「地形レベル」で L4・L5・L6・L7 を選べる。法線・縮小陰影は共通のまま、選択したレベルの標高を読み込む。位置・拡大率・方角・傾き・太陽位置・陰影方式・強さ・コントラストを保持し、地形レベル変更だけでは陰影画像を再生成しない。L4 に戻しても取得済みの標高は再取得しない。

全国比較の範囲では L4 が 448 四方、L5 が 896 四方、L6 が 1792 四方、L7 が 3584 四方。標高は f32＋gzip で配信し、ブラウザーで HTTP 展開後の f32 を読み込む。GPU には現在のレベルの標高だけを置く。L4／L5／L6／L7 の三角形数は 25,088／100,352／401,408／1,605,632。データと描画の切替・設定保持は `test_national_geometry.cjs` で確認する。

全国比較の「表示レベル」は、地形だけでなく法線・縮小陰影も L4〜L7 で切り替える。以前の地形レベル指定は標高だけを変えたため、全国縮尺では見た目の差が小さかった。現在は標高・法線・縮小陰影とも、L4 が 448 四方、L5 が 896 四方、L6 が 1792 四方、L7 が 3584 四方になる。法線のみ 1 段詳細にする選択肢も残す。輪郭は共通の詳細マスクを使う。

各表示レベルの法線・陰影は、L14 全タイルから求めた法線の合計・有効点数・照明値の合計を使って生成する。法線は平均後に正規化し、陰影は照明計算後に平均する。PNG を引き伸ばして高レベルに見せる処理は行わない。太陽位置別の縮小陰影も全表示レベルを生成し、切替時は生成済みの該当レベルを読む。旧形式の太陽位置キャッシュは、新形式のレベル一覧が無い場合に作り直す。

全国比較では海岸線を表示しない。DEM の有効範囲で陸地を切り抜かず、欠損部分を水平面と同じ明るさで埋める。表示範囲の外も同じ背景色にし、青い海面や輪郭を描かない。有効範囲マスクは欠損処理だけに使う。

地域別 JPEG XL 比較では、標高と法線それぞれに「Modular」「自動（従来）」を選べる。画面の初期値は両方 Modular。Modular は cjxl に `--modular=1` を指定する。d の指定は方式ごとに画質と容量の関係が異なるため、同じ d の容量だけで比較せず、表示と標高・法線の誤差も確認する。可逆設定の全画素照合、非可逆設定の符号化・復号、標高と法線の方式の個別指定を確認している。全国生成の設定は変更せず、停止したままにする。

地域別 JPEG XL の初期値は「自動（従来）」へ戻した。Modular の指定を続けて比較することもできる。「境界対策（試験）」では、16 画素の余白を含むタイルを符号化し、重複範囲の復号値を重み付きでつなぐ。標高は地域内で共通の最低標高とスケールを使う。画面にはタイル境界における標高の追加誤差の段差を表示する。地形そのものの標高差を差し引いた指標である。

境界対策は容量が増えるうえ、試料によっては最大誤差も増えるため初期値では無効。槍ヶ岳 L11・法線 512 四方・標高と法線 d=0.5 の試料では、自動の従来方式は標高 38,364 bytes・法線 176,509 bytes、境界の追加誤差段差最大約 41.55 m・法線 P95 約 9.07°。余白と重ね合わせありでは 40,906 bytes・205,805 bytes、約 40.34 m・約 9.05°で、改善は小さかった。Modular の従来方式の法線 P95 は約 11.10°。同じ d が同じ誤差を意味するわけではない。格子模様の解消は未確認で、この試験方式を全国生成には適用しない。

余白付きの比較用パケットは YJD2／YJN2。ヘッダーに余白幅を保持する。各タイルの JPEG XL は周囲の余白を含み、復号時は余白の外縁を重み 0、中心部を重み 1 とする線形の重ね合わせで復元する。画面の保存容量には余白を含むファイル全体を数える。可逆時は余白付きでも全画素を照合している。

地域比較の「各レベルの実タイル 2×2」を有効にすると、L4〜L14 の各レベルで隣接する 256×256 画素の実タイルを 4 枚表示する。URL は `http://127.0.0.1:61440/heightmap?tiles=2&level=14`。槍ヶ岳・筑波山とも `heightmap_tile_preview.py` で元の標高 DB から生成する。レベルを変えると地理的な表示範囲も変わり、視点を範囲に合わせ直す。画像を拡大してタイル数を増やす処理はしない。

標高は常に 2×2 タイル。法線は同じ範囲の 1 段詳細な標高から生成し、512 四方（2×2）と 1024 四方（4×4）を比較できる。L14 は元データの上限なので L14 から 512 四方を生成する。境界線の選択で標高は赤、法線は青の線を重ねられる。JPEG XL の動的圧縮もこの実タイルを使い、保存容量とタイル数を表示する。全 11 レベルの切替と複数タイルの可逆圧縮は `test_heightmap_native_tiles.cjs` で確認する。

地域比較の「陰影」で「共通の凹凸テクスチャ」を選ぶと、地形別の法線マップを使わず、標高から求める傾きに共通の高さ模様を重ねる。`/heightmap?tiles=2&level=14&normal=pattern` から確認できる。256 四方の周期的な高さ模様を端末内で生成するため、追加の配信データは無く、ミップマップ込みの GPU 容量は約 85 KB。模様の大きさと強さを調整でき、緩斜面・遠景では弱める。模様は地上位置に固定し、タイルごとには貼り直さない。実際の尾根や谷の細部を復元するものではない。

「法線マップ」と切り替えても視点と光源を保持する。共通模様を初期選択した場合は法線画像を取得しない。法線マップへ戻すと必要な画像を読み込む。`test_heightmap_pattern.cjs` で画像取得・切替・視点と光源の保持・レベル変更を確認する。

標高形式と法線形式の JPEG XL は、圧縮前でも選択できる。現在のレベル・解像度の結果が無ければサーバーで圧縮して表示する。JPEG XL 表示中にレベルを変えると、新しいレベルでも圧縮し直す。実タイル表示と筑波山では PNG と JPEG XL が対象で、ほかの形式は該当範囲の比較データが未生成のため選べない。形式の直接選択と PNG への復帰は `test_heightmap_codec_selection.cjs` で確認する。

全国のハイトマップのみを L7〜L12・JPEG XL d=0.2 で生成する場合は、`tools/terrain-rs/run-codecs.ps1 --part national-height-jxl --root build/terrain-lod.sqlite3 --output build/terrain-height-jxl-national-L7-L12-d02` を使う。PowerShell 7 で実行する。既存の標高＋法線方式とは別出力で、全国 11,304 タイルを対象にする。自動方式・effort 7・256 四方・タイルごとの標高最小値と 16 bit スケールを使う。d はメートル単位の誤差上限ではない。

出力 `terrain-height-jxl.sqlite3` は標高 JPEG XL、最小標高、スケール、Zstd 欠損マスク、復号標高の誤差を保持する。法線や海岸線は含めず、海岸線非表示をメタデータに記録する。全タイルで復号寸法と誤差を計測し、レベル別の最大誤差・RMSE・容量・件数を `progress.json` に出す。32 タイルごとに確定し、同じ設定で再開すると保存済みを飛ばす。完了時はレベルごとの元データ件数と DB 整合性を確認して空きページを除去する。

### JST 日時で太陽位置を指定する

全国比較と地域別比較の「太陽の指定」は「日時（JST）」が初期値。「日時」、前後 1 時間、現在のボタンで変更できる。「方角・高さを手動指定」に戻すと従来の操作も使える。`?sunDateTime=2026-03-20T06:00` で日時、`?sunMode=manual` で手動モードを指定できる。

JST を UTC に変換し、均時差・赤緯・各地点の緯度経度から太陽方向を求める。全国でも地点ごとに違う太陽方向になる。地平線下では直射光を使わず、薄明は表示用の近似で弱める。大気屈折・周囲の山による太陽の遮蔽は未実装。法線・共通模様は即時反映し、縮小陰影は「この太陽位置で陰影画像を再生成」で日時別に作る。再生成前は画像の元日時・光源を表示する。

`solar-position.js` と `solar_position.py` が位置計算、`solar-controls.js` が共通の操作欄。Rust の `national_shading.rs` は日時から求めた赤緯・時角を受け取り、各詳細標高点で照明を計算してから縮小する。API は `{"datetime":"2026-03-20T06:00"}` を受け付け、JST 固定で扱う。既存の方角・高度指定 API とキャッシュは維持する。

単体確認は `test_solar_position.cjs` と `test_solar_position.py`、Web 表示は `test_solar_display.cjs`。調査メモに参照式、精度・省略した条件、確認範囲を記録している。

### 河川・湖・沼の表示

全国比較と地域別比較に「河川」「湖・沼」を追加した。河川中心線と幅のある河川水面は「河川」、湖沼・池・貯水池などの面は「湖・沼」で切り替える。保存済みの OSM ベクターを使い、島の穴を保持する。北海道の大部分の河川は参照パックで未収録。出典と ODbL は画面フッターから開ける。

```powershell
# 初回は参照パックを読み取って、生のベクターと来歴を保存する
build/terrain-venv/Scripts/python.exe tools/terrain/inland_vectors.py --source D:/GitHub/yamamuki/app/src/main/assets/offline/terrain.zip
# 以後は作業フォルダーに保存済みの入力だけで再生成できる
build/terrain-venv/Scripts/python.exe tools/terrain/inland_vectors.py
build/terrain-venv/Scripts/python.exe -m unittest discover -s tools/terrain -p test_inland_vectors.py
```

`build/terrain-inland-vectors/` に入力ベクターの SQLite、元の manifest・GeoJSON・来歴・ライセンスと、全国／地域別の INL1 パケットを保存する。サーバーではベクターを加工せず中継する。WebGL でベクターを一時マスクに描き、地形面へ重ねるため、3D 表示でも地形と水面の深度差による縞が出ない。これは描画用の一時処理で、配信データはベクター。湖の水位を一定にする物理的な水面処理は入れていない。

全国は z10、地域別は範囲に応じて z10〜z12 の素材を使う。当初は全国の拡大時に詳細データを追加していなかったが、東京湾の表示修正で、次節の範囲別取得へ変更した。JPEG XL の全国標高 DB とは独立している。表示確認は `test_inland_display.cjs`。容量・描画上の制約・出典は調査メモにも記録する。

### 拡大時の水域の詳細化

東京湾の表示崩れに対応し、海域・河川・湖沼を表示範囲ごとに取得する。幅 400 km 以下で z12、1200 km 以下で z11、広域は z10。地形 LOD と独立して選び、GPU 上では表示範囲付近のタイルを 2048 四方のマスクへ描く。全国全体を描いたマスクをそのまま引き伸ばす処理は使わない。

初回は `inland_vectors.py --source ... --import-only` で参照パックの `sea/` も保存する。SQLite には生の RIV1 / WAT1 を置く。サーバーの `/water-tiles` は BLOB の中継だけを行い、復号と三角形化はブラウザーで行う。海岸の切り抜きも詳細海域に合わせる。

東京湾の確認は `/national-shading?lat=35.5&lon=139.8&span=180&sunMode=manual`。`span` は表示幅の指定値 km。`test_tokyo_water.cjs` で地形 L4 / L7 と傾き 0° / 55°、湾内と埋立地、全国へ戻したときの切替を確認する。中継の範囲・生データ保持は `test_water_tile_relay.py`。修正前後の画像と制約は調査メモに記録する。
