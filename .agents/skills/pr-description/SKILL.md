# PR の件名と本文を作る

作業ブランチのコミットをもとに、PR の件名と本文を作る。書き方のルールは [AGENTS.md](../../../AGENTS.md) の「コミットメッセージ」と「ブランチと PR」に従う。

## 1. コミットと差分を集める

```bash
git fetch origin main
git log --reverse --format='--- %h%n%B' origin/main..HEAD   # コミットのタイトルと本文
git diff --stat origin/main...HEAD                          # 変わったファイル
```

- base は通常 `main`。別のブランチに向けた PR なら、そのブランチに置き換える。
- まだ push していないコミットやコミットしていない変更があれば、先にそれを伝える。コミットしていない変更は件名と本文に含めない。

## 2. 件名

- コミットが 1 つなら、そのタイトルをそのまま使う。
- 複数なら、PR 全体で何がどう変わるかを 1 文にまとめる。
  - プレフィックスは、利用者から見て一番大きい変更の種類から選ぶ（`feat` > `fix` > `perf` > `refactor` > その他）。
  - 互換性を壊すコミットが 1 つでもあれば、`feat!:` のように `!` を付ける。
- PR 番号は書かない（スカッシュマージのときに GitHub が付ける）。

## 3. 本文

`.github/pull_request_template.md` の見出しに沿って書く。テンプレートのコメント（`<!-- -->`）は消し、内容で置き換える。

- **何を変えたか**: 利用者から見た変化を先に、実装の補足をあとに、箇条書きで書く。関連する Issue があれば `Closes #番号` を書く。アプリ側の Issue なら `shohei0205/yamamuki#番号` と書く（番号はコミットや会話で確認できたものだけ）。
- **対象**: 変わったファイルの場所でチェックを付ける。
  - 抽出条件や `manifest.json` の形式など、データの生成に関わるもの → データの生成
  - Releases への公開や、それを動かす GitHub Actions → 配布
  - それ以外（確認用の CI・ドキュメント・設定ファイルなど）→ その他
- **確認方法**: 各コミットの「検証:」をまとめる。同じ確認は最後のコミット時点の結果だけを残す。成功・失敗・未実施・環境上実行できなかった確認を区別し、確認していないことを書き足さない。

## 4. マージ時のコミット

コミットが 2 つ以上あるときは、本文の最後に次の見出しと、マージ画面の欄ごとに分けた 2 つのコードブロックを足す。マージするときにそのまま貼れるようにする。

````markdown
## マージ時のコミット

**Commit message**（GitHub が入れたものと同じなら、書き換えなくてよい）

```text
<PR の件名> (#<PR 番号>)
```

**Extended description**（欄の中身を消して貼る）

```text
- <変更 1>
- <変更 2>

検証:
- <結果>

Co-authored-by: <各コミットにある作成者>
```
````

- AGENTS.md の「コミットメッセージ」のルール（本文・検証・作成者）に合わせる。
- 「Commit message」のブロックは、PR の件名と同じにし、末尾に `(#番号)` を付ける。GitHub もこの欄に同じものを入れるので、ふだんは書き換えなくてよい。欄を書き換えたときに `(#番号)` が消えないよう、ブロックにも番号を入れておく。
  - 番号は、PR を作ったあとに確かめたものだけを書く。PR を作る前に本文を作るときは、PR を作ったあとで本文を直して番号を入れる。
- 「Extended description」のブロックにはタイトルを入れない。入れると「Commit message」と 2 重になる。
- 箇条書きは、各コミットの本文をもとに、**最終的な差分**に残っている変更だけを書く。途中で取り消した変更や、レビューで直しただけの変更は、1 つの変更としてまとめるか省く。
- 「検証:」は、最後のコミット時点の結果を使う。
- `Co-authored-by:` などの末尾の行は、各コミットにあるものを重複なく並べる。セッション URL など、ツールが付けた行もそのまま残す。自分で作らない。
- コミットが 1 つだけなら、この節は足さない（そのコミットのメッセージがそのまま使われる）。

## 5. PR に反映する

- 新しい PR は、ユーザーが作成を指示したときだけ、作った件名と本文で作る（AGENTS.md の「ブランチと PR」）。指示がなければ、件名と本文を見せるところで止める。PR を作る前に内容を確認したいと言われている場合も、先に見せる。
- すでに PR があるなら、今の本文と比べて、変わるところを先に見せる。人が書き足した部分（レビューの経緯、注意書きなど）は残す。
- 件名と本文を GitHub に書き込む手段（`gh pr edit`、GitHub の MCP ツールなど）は、使える環境のものを使う。
