# 階層 B スプライン曲面の地域比較

## 概要

富士山・槍ヶ岳・筑波山の Web メルカトル上 32 km 四方を、三角形一覧を持たない曲面として保存する試作。既存の TIN と全国データは変更しない。比較画面は http://127.0.0.1:61467/ 。左は従来の元標高メッシュ、右は選択した曲面を同じカメラで表示する。現在のBスプライン表示は曲面からポリゴンを生成する。交点探索の説明と検証結果は旧方式の記録として残す。

NURBS の重みをすべて 1 とした B スプラインを使う。今回の実装は、一様な3次テンソル積 B スプラインの階層補正であり、LR B スプラインや THB スプラインの正式な実装ではない。通常の NURBS の2次元制御格子を、必要な場所だけ細かくする方法を調べる最初の試作である。

## 曲面の定義と生成

高さを `h(x,y) = Σ_l Σ_i,j c[l,i,j] B3(x/s_l-i) B3(y/s_l-j)` で表す。各階層の区間数は 8・16・32・64・128・256・512。区間長は 4,000・2,000・1,000・500・250・125・62.5 m。メルカトルの距離なので、地表の距離は緯度により短くなる。

基底は各軸で4区間の有限な範囲にだけ影響する3次 cardinal B スプライン。区間内の重みは `[(1-t)^3, 3t^3-6t²+4, -3t^3+3t²+3t+1, t³]/6`。係数の和は、通常の内部節点をまたいで C2 連続になる。保存する係数は地表の標高サンプルではなく、曲面の制御値である。

1. 既存 `terrain-lod.sqlite3` の YMD1 標高を読み、各地域の中心を既存比較 DB から取得する。三角形配置は読み込まない。
2. 最初の粗い格子のサンプルを、SciPy の `spline_filter(order=3, mode='mirror')` で制御係数へ変換する。周囲16区間を計算用に用意する。
3. 次の階層では、元標高とそれまでの曲面との差をサンプルし、その残差を同じ方法で係数へ変換する。
4. 残差の絶対値を5×5近傍で評価し、`max(0.5, 1000/n)` m 以下の領域の補正係数をゼロにする。領域に基底の影響範囲が届かない係数も保存しない。ゼロの係数との境界でも基底の滑らかさは変わらない。
5. 階層ごとに、元標高との RMSE・最大差を評価する。62.5 m 格子と、独立したランダム8,192点を使う。全 DEM 点での最大誤差保証ではない。最細階層の評価格子は生成サンプル位置と一致するため、ランダム点の誤差も確認する。

これは誤差上限を制約とした最小二乗近似ではない。節点を増やす場所の選択、粗い階層への LPF、山頂保持、誤差上限の保証は今後の比較対象。スプラインの滑らかさだけでは、サンプリングによる折り返しやオーバーシュートまで防げない。

## SQLite と転送

出力は `build/bspline-surface-prototype-v3/spline.sqlite3`。旧試作の出力も保持する。

- `regions(name, info)` は地域の共通原点・範囲など。
- `layers(region,n,info,indices,coefficients)` は地域と階層を主キーとする。三角形インデックスはない。
- `indices` は非ゼロ係数の位置を行優先で並べた little endian uint32 の列。対応する `coefficients` は little endian float32 の列。それぞれ zlib level 6 で圧縮する。これは比較用であり、既存 TFC の形式は変更しない。
- 正方形配列の幅は `n+1+2*16`。制御点の原点はタイル左上から16区間外側。`info` に単層・累積の係数数と BLOB サイズを記録する。
- 表示側が選択した階層までを復元すると、その曲面が得られる。独立保存・親予測差分・量子化の容量比較は [係数圧縮比較](BSPLINE_CODEC_COMPARISON.md) に記録した。

`GET /api/spline?region=fuji&n=128` は、階層の合計を細かい一様 B スプライン基底へ変換して返す。元 DEM の転送ではない。返却 JSON は `info,size,halo,span,heightBounds,gradientBounds,coefficients`。係数は little endian float32 を base64 化し、HTTP は gzip 圧縮する。画面の「保存 BLOB 合計」はこの JSON の転送サイズとは異なる。

GPU 用への基底変換は、細かい節点位置で階層の合計を評価し、同じ3次基底の係数へ変換する。計算用の余白による領域内への影響を含め、生成時とテストで元の階層曲面との違いを照合する。この試作の照合差は 0.02 m 未満を必須とする。端末では R32F テクスチャに曲面係数を置く。三角形や元の標高画像は右側の曲面表示に必要ない。

## 描画

画面を覆う補助三角形1枚から、画素ごとに視線を作る。領域の箱との交差範囲で `視線の高さ - h(x,y)` の根を探索する。地表を三角形へ分割する処理はない。

3次基底の微分は隣接する制御係数差の凸結合なので、その差の最大値から勾配の上界を得られる。区間ごとの上界と視線の向きで安全な歩幅を決め、次の区間を越えないように制限する。高さ差だけでは交点としない。解析微分によるNewton補正を使い、視線上の補正距離が小さい場合、または係数の2階差分から区間内の単調性を確認できる場合に、補正後の残差を検証する。符号が変わった場合は20回の二分探索で補正する。ほぼ接する区間や探索が停滞した区間では、視線上の曲面を6次Bernstein多項式へ変換し、凸包による根の除外とde Casteljauの二分割で手前の根を分離する。探索は最大2,048回。上限到達は `splineDebug=1` で紫色に表示できる。法線は曲面の解析微分、深度は求めた交点を使う。

「ワイヤー」は曲面の区間を表示し、三角形の辺は表示しない。「近似描画の分割数」と「曲面の法線」は従来描画にだけ使い、B スプラインでは無効になる。比較元メッシュの z と B スプラインの区間長は独立している。断面グラフの青線も選択中の B スプラインから評価する。

## 起動と検証

```powershell
./build/terrain-venv/Scripts/python.exe -X utf8 tools/terrain/bspline_surface.py generate --output build/bspline-surface-new
./build/terrain-venv/Scripts/python.exe -X utf8 tools/terrain/bspline_surface.py serve --output build/bspline-surface-prototype-v3 --port 61467
./build/terrain-venv/Scripts/python.exe -X utf8 tools/terrain/test_bspline_surface.py
node tools/terrain/test_bspline_surface.cjs
```

比較サーバーの `/api/info` と `/api/data` は既存の61465から取得する。右側の B スプラインは新しい DB のみから取得する。既存サーバーを止めない。非表示起動の PID・ログは出力ディレクトリの `server.launch.json` と `server.*.log` に保存している。

2026-10-25 の検証では Python 4テスト成功。平面の保持、節点での勾配、局所的な係数の影響範囲、階層から一様基底への変換、保存した21曲面の復元を確認した。Chrome では3地域×3区間長の9条件、低い視点を含む9条件、旧曲面・三角形描画への切り替えを確認した。確認した低い視点では探索上限に達した画素は0。

実際の GPU の高さ・勾配216値を CPU の倍精度参照と照合し、高さ差の最大は約0.00152 m、勾配差の最大は約0.0000282。記録と画像は `build/bspline-surface-prototype-v3/browser-check/`。既存 LPF 比較も9条件の回帰テストを通した。

RTX 5060 Ti、Chrome、1,200×800 の左右比較で、槍ヶ岳の n=128/512、傾き1.1/0.3ラジアンを各10フレーム計測した。描画と1画素読み戻しの平均は約0.92～1.25 ms。この測り方は画面の提示を含む FPS ではなく、モバイル GPU の性能も示さない。

全国化、混合 LOD・タイル境界接合、滑らかな LOD 切り替え、メモリー上限、スマホでの速度は未検証。既存 TIN の配布形式をこの試作へ置き換える判断はまだしない。


## 交わらない視線を面として描く不具合（2026-10-26）

槍ヶ岳・250 m区間で縦の平面が見えるとの報告を受け、交点判定を修正した。旧処理は高さ差0.15 m未満で交点としたため、地表から5 cm上を平行に通る視線でも、近クリップの開始距離1 mを交点として出力した。高さ差が小さくても、視線と曲面が交わるとは限らない。

現在は視線上の距離と曲面の微分で収束を確認し、補正後の高さ残差0.0005 m未満を確認する。局所曲率の上界で単調性を保証できない大きなNewton補正は採用しない。接線に近い場合などは区間内の6次多項式の根を分離する。分離後の交点を実際の曲面へ最大4回補正する。最終交点も領域・探索範囲内にあるか検証し、高さ残差は0.002 mを基本に座標・標高・勾配に応じたfloat32の丸め幅を加えて確認する。この残差の条件だけで交点を新しく認定することはない。

高さの評価では、近傍の共通高さを引いて係数差を加算してから戻すようにした。勾配も係数差から計算し、標高の大きい平坦部での丸め誤差を抑える。曲面係数や保存データの形式・生成結果は変更していない。

GPU再発テスト `test_bspline_intersection.cjs` は7条件で成功。地表の上下5 cm・上1 mmを平行に通る視線、ほぼ水平だが交わらない視線は非交差となった。通常の平面、かすめる交点、斜面の交点も距離を照合した。実データは3地域×250/62.5 m×3傾斜×2距離の36条件で探索上限到達0・WebGLエラー0。GPUの高さと勾配の照合とPython 4テストも成功した。画像の利用者の正確なカメラ座標は取得しておらず、同じ画素配置を再現した結果ではない。

記録は出力先の `intersection-check.json`、`browser-check/*-n*-ray-check.json`、槍ヶ岳250 mの接近画像は `wall-fixed-yari/`。ブラウザーで実行済みの古いシェーダーは残るため、画面の再読み込みで更新する。

交点の確認を追加した後のRTX 5060 Ti・1,200×800での描画と1画素読み戻しは、同じ4条件で最終確認は約2.67～3.35 msだった。以前の約0.92～1.25 msから増えている。提示FPSやモバイル性能の値ではない。


### 区間境界での高さの跳び

さらに槍ヶ岳250 mの区間境界近傍で、CPUでは連続なのにGPUでは高さが最大約152.093 m異なる座標を再現した。余白のオフセットを含めた座標から整数の区間番号と `fract` による区間内座標を別々に求める構成で、境界の直前・直後の評価が整合していなかった。

余白を加える前の正規化座標から整数部を一度だけ求め、区間内座標はその同じ整数部を引いて算出する。余白は整数のテクスチャ番地にだけ足す。曲面評価と6次多項式の区間化の両方でそろえた。これにより、同じ座標のCPUとの差はテスト許容値内になった。保存している曲面そのものに152 mの段差があったわけではない。

各地域・250/62.5 mで、区間境界の前後0.0005～0.003 mを含む972個のGPU出力を照合した。高さ差の最大は約0.00152 m、勾配差の最大は約0.0000452。実地形の36視点では探索上限到達・交点の最終検証失敗・WebGLエラーがすべて0。槍ヶ岳250 mの接近画像でも、区間境界に出ていた偽の面とその箇所の大きな欠けの解消を確認した。


## 曲面をポリゴン化する描画へ変更（2026-10-26）

現在の61467の「階層Bスプライン」は、Bスプラインから描画用ポリゴンを生成する。地表との交点探索は使わない。保存DB・曲面の係数は従来のままで、再生成は不要。旧Bスプラインの交点探索コードは `createRay` として検証用に残し、画面のBスプライン表示からは呼ばない。別の選択肢「直接交差（レイキャスト）」は従来からある三角形パッチのClough–Tocher比較用である。

各曲面区間に、分割数dの格子と2d²枚の三角形を配置する。格子とuint16の三角形インデックスの小さなテンプレートを1個だけGPUへ送り、n²区間をインスタンス描画する。各区間の位置は `gl_InstanceID` から計算する。頂点シェーダーで元のBスプラインを評価して高さを求め、通常のラスタライズと深度処理で地表を描く。画素ごとの根の探索や手書きの交点深度はない。隣の区間と共通のXYでは同じ曲面を評価する。

「曲面の分割」は1・2・4・8・16から選択する。描画用データが過大にならないよう、既存比較と同じ400万三角形の上限を設けた。`2n²d²` が上限を超える場合はdを半分ずつ下げ、指定値と実際の分割数をステータスに併記する。例えば250 m区間・4分割は524,288面、62.5 m区間で4分割を指定すると実際は2分割の2,097,152面。カメラの向きによって分割数を変更する実装ではない。

陰影は「曲面の法線で陰影」のONで元曲面の解析微分を画素ごとに評価し、OFFで生成した三角形の面法線を使う。ワイヤーは実際の生成三角形の辺を表示する。格納容量・元曲面の誤差は変わらないが、ポリゴン化による形状の近似誤差は分割数に依存する。画面の曲面RMSE・最大差は、その近似誤差を含まない。

検証は、3地域の3品質での9表示条件、250/62.5 m区間での接近・傾斜・回転36視点、1/2/4/8分割、面法線・解析法線・ワイヤーの切り替えを確認した。GPUの曲面評価972値と、実際の頂点シェーダーからtransform feedbackで取り出した324点をCPU参照と照合した。生成頂点の高さ差最大は約0.00174 m、XY差最大は約0.00146 m。WebGLエラーなし。記録と画像は `build/bspline-surface-prototype-v3/polygon-browser-check/`。

RTX 5060 Ti・Chrome・1,200×800の左右比較で、槍ヶ岳の250/62.5 m区間と傾斜1.1/0.3/0.05ラジアンを各10フレーム計測し、描画と1画素読み戻しの平均は約0.94～1.39 msだった。旧レイキャストの最終確認は約2.67～3.35 ms。これは表示FPSやモバイル端末の性能を示す値ではない。水平に近い視線でも根の探索を繰り返す処理はなくなったが、描く面数や画面の覆われ方によって負荷は変わる。

係数の保存方法を比較する表は http://127.0.0.1:61471/ 。表示中の曲面や元の SQLite を変更せず、全 11 方式を比較した。[係数圧縮の技術メモ](BSPLINE_CODEC_COMPARISON.md) に実測と復号方式をまとめた。
