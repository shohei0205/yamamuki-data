# 制御点から GPU で自然近傍曲面を生成する試作

2026-10-28。比較 URL: http://127.0.0.1:61485/control-gpu?region=fuji&quality=25&resolution=auto

## 目的と処理

CPU で細分割した頂点・三角形を転送する処理を避ける。WebGPU へ制御点、元の Voronoi セル、候補検索用四分木、全域 C¹ の頂点勾配を渡す。左は元の Sibson、右は全域 C¹ 勾配調整。XYZ は共通。

Compute shader が両曲面の高さと前後 1 m の差分勾配を計算し、GPU 専用キャッシュへ保存する。Vertex shader は頂点 ID から格子内の三角形を生成する。CPU の頂点・index バッファー、標高画像の転送はない。描画には三角形を使う。カメラ操作ではキャッシュを再利用し、地域・品質・評価密度の変更時だけ曲面を再生成する。

GPU キャッシュは配布データではなく実行時の一時データ。自動密度は投影サイズに応じて 128～512 分割、手動では 1024 まで。現在は 8 km 四方の比較試作であり、全国のタイル選択・接合・常駐量制限は未統合。

## 入力形式

先頭 uint32 は JSON ヘッダーのバイト数。ヘッダーは 4 バイト境界まで空白で埋める。以降はヘッダーに記載した件数順の配列。

- 制御点 32 B: XY float32（km）、Z float32（m）、セル先頭 uint32、勾配 XY float32（m/m）、セル頂点数 uint32、フラグ uint32。
- Voronoi セル頂点 8 B: 制御点からの相対 XY float32（km）。必要点に絞っても、元の全点集合で計算したセルを保持する。
- 四分木節点 32 B: 子 4 個の uint32 と葉の参照先頭・件数等 4 個の uint32。葉の子番号は 0xffffffff。
- 候補参照: uint32 の制御点番号。

候補は矩形と交差する Delaunay 外接円から保守的に収集する。境界に 1 cm の余裕を加える。候補が多ければ細分化し、上限を超えた候補を切り捨てない。無効な計算は紫色で明示する。

## 実測と検証

RTX 5060 Ti / Chrome。この PC の GPU 時間であり、スマートフォンや画面全体の FPS の保証ではない。

富士山 25 m、512 分割では入力約 0.113 MiB（876 制御点と補助情報）、CPU メッシュ転送 0 B。両曲面の GPU キャッシュ合計約 8.03 MiB。GPU 曲面生成約 0.9 ms、左右描画約 0.26 ms。旧画面と比較する場合、旧 16 km 四方に対し本試作は 8 km 四方であることに注意する。

富士山・槍ヶ岳・筑波山の 25/50 m、128/512 分割および富士山 25 m の 1024 分割、計 13 条件を確認。全キャッシュで無効点 0。各条件 2048 点の CPU 基準との比較では高さ最大差 0.000348 m、勾配成分最大差 0.000323。候補索引は各条件 512 点で真の自然近傍候補を包含することを別途確認。自動密度 512→128→512 と右ドラッグも確認。

検証時だけ GPU キャッシュを読み戻す。通常表示では読み戻さない。テストは test_sibson_gpu_controls.py、test_sibson_gpu_controls.cjs、verify_sibson_gpu_controls.py。結果は build/sibson-weighted-v1/gpu-controls/benchmark.json と verification.json。

## 全国表示への適用

全国の全タイルを同じ分割数で常駐させない。可視範囲・投影面積に応じた評価密度、遠方の低品質タイル、GPU キャッシュの容量制限と破棄、近傍タイルとの接合を組み合わせる。今回確認できたのは CPU での密なメッシュ組立・転送を除去できることと、GPU 補間の数値一致である。

### LODと常駐

最粗タイルから四分木で降りる。可視範囲は標高0～4000 mの箱とカメラの視錐台の交差を、同次座標の半空間で判定する。距離による画面上の誤差がスライダー指定のピクセル値を超える場合に子へ進む。固定品質も選べる。表示用分割数は投影サイズを基に8～128とし、合計約200万三角形を上回る場合は表示格子を減らす。制御点の削減は行わない。

最粗レベルは常駐。読み込み済みの子は維持し、未読の子の範囲だけ親を切り出して表示する。取得済みのタイルはズーム往復でも再利用し、常駐領域不足時に描画中・取得対象以外の古いものから破棄する。入力の一時GPUバッファーはCompute完了後に破棄する。CPUからの定常更新はカメラ・タイル範囲・隣接番号だけ。

GPU標高・勾配キャッシュの確保量は128 MiB固定。可変長の領域割当と解放領域の併合を行う。画面上の使用量はこの中で有効なタイルが使う部分であり、GPUが確保している物理バッファー自体は128 MiB。メタデータ・入力一時バッファー・MSAA・深度バッファーは別枠。CPUに細分割後の頂点や三角形インデックスは存在しない。

### 境界

同品質の点集合は既存の共通曲面から切り出したもの。入力には250 mの余白を含む。GPU描画時に隣接する可視タイルだけを参照し、余白内でsmoothstepの重みを正規化して高さと勾配を混合する。勾配には重みの微分も含める。異なる分割幅の共有辺では、細かい側の辺の頂点を粗い側の辺の端点間に置き、T字接続の隙間を防ぐ。境界の一部だけ別レベルに接するケースも、実際に接する辺の区間で判定する。CPUで接合メッシュを作る処理はない。

地域外周は鏡像制御点で延長して有限のVoronoiセルを作る。内部タイルで候補探索が保守的に拾う外周点の無限セルは、近傍の半平面から十分広い作業枠内で構成する。既存制御点や元SQLiteは変更しない。制御点をタイル中心の相対座標にしてGPUのfloat32誤差を抑える。

### 検証

`test_sibson_gpu_variable.py` は3地域×7レベルでパケットの補間値を元モデルと比較する。`test_sibson_gpu_variable.cjs` は同条件の表示、各GPUキャッシュの全点の有限性、自動LOD、傾けた混合LOD、描画時間、標高画像・CPUメッシュ転送がないことを確認する。`verify_sibson_gpu_variable.py` は試験時に読み戻したGPU値と独立した倍精度パケット評価を比較する。

GPU境界検証は、描画シェーダーと同じ `stitched` 関数をComputeから呼び、細かい側の頂点と粗い側の描画辺上の高さ・勾配を比較する。3地域の混合LODで合計13,481点、そのうち異品質2,278点を確認し、高さ・勾配とも差0だった。これは検査した辺上の描画頂点の一致であり、曲面全体のDEM精度や地域外の接合を保証するものではない。通常表示はGPU結果をCPUへ読み戻さない。

RTX 5060 Ti / Chrome 1500×1000では、全体表示40タイルの定常GPU描画中央値は約0.39 ms。傾斜時137～148タイル、約198万三角形では約1.18～1.25 ms。GPU時間はフレーム全体やスマートフォンの性能とは区別する。結果は `build/sibson-gpu-variable-v1/browser-results.json`、スクリーンショット、`gpu-verification.json` に保存する。

タイル一覧の更新では目標タイルと分岐する祖先を索引化し、毎タイルの全目標走査を避ける。隣接一覧も総当たりせず、2 km単位の64×64所有者索引から各タイルの周囲だけを調べる。これにより最詳細固定で数千タイルを扱うときにも、一覧・接合メタデータの更新が二重ループで増えないようにした。重い固定レベル全域とズーム往復の追加試験は `test_sibson_gpu_variable_full.cjs`。

大量の固定レベルを読み込む間は、取得ごとの再描画を最大4回/秒にまとめる。操作によるカメラ更新はこの制限を受けない。補間・取得・キャッシュへの保存は描画更新の間も進む。
GPUと倍精度パケット評価の標高差は3地域・7レベルの試験で最大約0.000279 m。パケットと元モデルの比較は最大約0.000239 mだった（地域外周の鏡像境界条件を除く）。

疎な同一円周上の点では、外接円からの候補が細分割しても減らず、探索木だけが膨らむ例があった。全ての子の候補集合が同じでGPU上限256点以下なら葉として止める。128 km版は通常32候補・深さ8を目安とし、256点を超える場合だけさらに細分化する。候補の切捨てはしない。富士山12.5 mの(55,43)は旧補助パケット約219 MBから9,684 B、(32,58)は約119 MBから3,920 B、25 mの(16,30)は約79 MBから4,776 Bになり、元の補間値を維持した。旧パケットは保持し、1 MiBを超える旧版は配信せず `x-y-fast.bin` を生成・再利用する。SQLiteや制御点を変える処理ではない。

最詳細12.5 m固定・span 145 km・富士山で、可視の3,712タイルを読み込み、499,712三角形を表示した。初回のパケット準備を含むこの試験は124.0秒、キャッシュ有効領域は51.06 MiB。試験後のズームイン・右ドラッグ・ズームアウトでもエラーなし、キャッシュは128 MiB以内だった。全4,096タイルを常に描くのではなく、視錐台外を除いた数である。

## 2026-10-28 視点変更時に既読タイルが粗くなる問題

旧処理は兄弟の1枚でも未読だと、読み込み済みの詳細な兄弟もまとめて親に戻していた。新処理は未読部分だけ親キャッシュで埋める。親キャッシュを使う場合も表示範囲は未読部分に限定し、詳細タイルとの重なりを作らない。同じ親だけで埋めた領域はまとめ、不要な描画呼出しを増やさない。

各描画項目は元のキャッシュに加え `drawBounds` と `drawN` を持つ。GPUの `Tile.core` は切り出した描画領域、`Tile.field` は元キャッシュの評価領域、`Tile.data.y` は元キャッシュの分割数、`Tile.misc.y` は描画分割数。両者を分離し、親のキャッシュを再生成せず一部分だけ描画する。GPU側の境界接合も描画側の分割幅を使う。

同タイルのキャッシュが複数あるときは最も細かいものを参照し、必要な密度以上のキャッシュがあれば低密度版を再取得・再生成しない。描画密度自体には引き続き予算を適用する。約200万三角形への調整は分割数の大きい順ではなく、画面上の大きさに対して過密なものから減らし、手前の大きな地形を優先する。

`test_sibson_gpu_variable_selection.mjs` は兄弟3枚が既読・1枚が未読のとき、既読3枚を維持して親は未読部分だけに使うこと、被覆面積と高密度キャッシュの再利用を確認する。`test_sibson_gpu_variable_partial.cjs` は実際に1枚のHTTP応答を遅延させ、同じ状態の描画と、報告された富士山の視点からの回転を検証する。

## 2026-10-28 目標レベルへの直接切り替え

表示のために途中の全祖先レベルを取得する処理を廃止。初回の800 m常駐タイルと、可視範囲で最終的に選ばれたタイルだけを取得する。800 m以外は画面中心に近い目標を優先し、品質の粗い順には並べない。差分SQLiteをサーバーが復元する際の内部参照はこれとは別であり、途中の品質を描画する必要はない。

目標の粗いレベルが未読の間も、既読の詳細な子タイルを表示に利用する。目標が届けば直接置き換える。より詳細な目標を待つ場合は既読の祖先で未読部分だけ埋める。目標選択に含まれない枝には、粗い代替タイルを出さない。

`test_sibson_gpu_variable_direct.cjs` は報告された槍ヶ岳の視点で、800→12.5 mの取得レベルがこの2種類だけであること、12.5→400 mの400 m応答を止めても詳細表示を維持すること、応答後に直接400 mへ変わり、12.5 mへ戻すと再取得しないことを確認する。

## 2026-10-28 自動LODで既読の1段細レベルを優先

自動LODの目標タイルに対し、直接の子（1段細かい品質）のキャッシュがあれば、目標自体も既読であっても子を優先する。未読の子の領域だけ目標タイルで埋める。目標より2段以上先のキャッシュをこの理由で選ぶことはない。固定品質指定では従来どおり指定品質にする。

この優先表示のために子を新規取得することはない。可視の子が全て既読なら、その領域の目標品質を改めて取得する必要もない。キャッシュは従来のLRUと128 MiB枠で管理する。子を選ぶ場合も描画用格子の間隔は元の目標の予算を引き継ぎ、データ品質の再利用と描画の細分割数を区別する。
