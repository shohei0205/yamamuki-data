# 山頂・尾根・谷を保持する曲面の比較

2026-10-26。少数の Gaussian 曲面では槍ヶ岳の形が失われたため、山頂と稜線を残す別案を試作した。全国データへの採用は未決定。既存の比較画面と生成物は残している。

## 表示

http://127.0.0.1:61469/?region=yari&quality=fine

富士山・槍ヶ岳・筑波山の各 32 km 四方を、粗い・標準・細かいの 3 段階で比較する。「山頂へ接近」で中心付近の保護点を注視し、「尾根・谷線」で尾根候補を橙、谷候補を水色、保護点を黄色にする。左右比較の左は従来の元標高 TIN。曲面の分割と滑らかな陰影も切り替えられる。RBF と B スプラインの選択肢も保持する。

## 生成と保存

`tools/terrain/ridge_surface.py` が `build/terrain-lod.sqlite3` を読み、`build/ridge-surface-prototype-v4/ridge.sqlite3` を生成する。基準地域は `build/lpf-curve-smooth-prototype/comparison.sqlite3`。125 m 間隔の 257×257 標高格子から、D8 流路と逆地形の流路を求めて谷・尾根候補にする。実際の地形分類を保証する線ではない。

候補線は平面位置と高さの双方で簡略化し、交点と山頂候補を固定する。候補線を辺に含む平面三角形分割を作り、候補線を横断しない凸な隣接面を四角形にまとめる。残りは三角形。普通の山腹には標高差が大きい点を追加する。

`surfaces(region, quality, info, model)` は WITHOUT ROWID。主キーは地域と品質。model は JSON を zlib level 6 で圧縮した比較用 BLOB。vertices は地域中心からの平面 XY と標高、faces は 3 または 4 頂点のインデックス、creases は辺の両端と種別（0: 外周、1: 尾根、2: 谷）、corners は保護点のインデックス。座標は float32 に量子化してから保存する。配布形式として確定したものではない。

## 曲面と描画

通常部の高さは Catmull–Clark に似た重み、尾根・谷上の新しい高さは 4 点補間で求める。骨格と山頂の既存点は固定する。XY は元頂点・辺中点・面重心による固定の平面分割とし、面の反転を防ぐ。高さの重みには傾いた平面を再現する補正を加える。通常の 3 次元 Catmull–Clark、NURBS、解析的に連続性を保証した曲面ではない。

骨格を挟む面は位置を共有し、法線は別に求める。サーバーは保存された制御網だけから細分割の重みを作る。ブラウザーはその重みと制御高さを GPU で評価して頂点を生成し、キャッシュして描く。移動・回転だけでは頂点を再生成しない。描画時に元 DEM を参照しない。レイキャストは使わない。

保存 BLOB と表示用の派生配列は別物。現在はサーバーが重み・インデックス等を作って送信するため、通信量と表示用メモリーは BLOB より大きい。槍ヶ岳・細かい・4 分割では 149,400 三角形、派生配列 16,276,168 bytes。独立した曲面を数十枚置くだけで山を再現できたという結果ではない。

## 三角形メッシュの約半分の容量へ増量（2026-10-26）

`--half-budget` で容量を基準に制御網を増やす実験を追加した。比較元は同じ 32 km 四方・z14 の元標高三角形メッシュ。曲面の係数は比較元に含めず、ローカル XYZ（float32 値）と三角形インデックスだけを JSON＋zlib level 6 で保存した容量を測る。曲面側も同じ条件で、制御点・制御面・骨格・保護点をすべて含める。最終配布形式や SQLite ファイル全体の容量比ではない。

比較元の圧縮量は富士山 557,701 bytes、槍ヶ岳 3,009,892 bytes、筑波山 607,683 bytes。各地域ごとにその半分を目標に、流路の抽出しきい値・骨格の簡略化・山腹の追加点数を調整する。制御高さを適合させた後の実サイズと比率を画面に表示する。同じ制御点数ではなく、同じ保存量の比率で比較する実験。

新データは `build/ridge-surface-half-budget-v2/ridge.sqlite3`、比較画面は http://127.0.0.1:61470/?region=yari&quality=half 。以前の 3 品質も選択でき、元データは変更しない。生成は `python tools/terrain/ridge_surface.py generate --half-budget --output build/ridge-surface-half-budget-v2`、配信は同じ引数で `generate` を `serve` に変え `--port 61470` を加える。

制御点が 12,000 点を超える場合、適合計算は 1 回細分割した位置で行い、評価は 2 回細分割する。それ以外は従来と同じ 2 回適合・3 回評価。参照の分割回数を画面に表示するため、表の誤差を比較するときはこの違いを考慮する。大容量版の描画は概算 100 万三角形を目安に分割回数を抑え、指定と実際の回数を表示する。保存制御点は間引かない。

骨格辺の種別判定は、従来の全線総当たりから STRtree の最近傍検索へ変更した。同距離は元の並びの先頭を選ぶ。同距離を含む照合テストを追加している。

制約辺上の既存点は、中点から半辺長の球内を cKDTree で探してから正確な距離・区間判定を行う。候補インデックスを整列して同距離の選択順を維持する。全点照合との一致をテストする。保存済み地域は `--resume` で読み飛ばせる。容量調整の再開には `--initial-scale` も指定できる。

大量の山腹点を追加する場合は 128 点までの分散した候補をまとめて追加する設定を加えた。完成した富士山・筑波山は従来の 16 点単位、槍ヶ岳の再開時は 128 点単位。各行の settings に実際の条件を保存する。いずれも点を追加するたびの厳密な最急降下ではなく、まとまった点を追加した後に誤差を再評価する試作用の生成処理である。

| fuji | 12,478 | 285,214 | 557,701 | 51.1% | 5.47 | 42.76 |

容量調整では目標の半分に対する ±10% を目安に停止し、最後の高さ適合後に実サイズを再計測する。最終 3 地域とも比較元の 45～55% に収まった。表の誤差は 2 回細分割・125 m 格子の参考値で、細かな凹凸までの最大差保証ではない。

増量版の確認結果: 3 地域すべて Chrome で表示・分割数切替・陰影・骨格線・旧描画方式との切替に成功。GPU と CPU の高さ・勾配照合、保護点の高さ、共有位置の隙間 0、反転面 0、カメラ操作で再生成なしを確認した。集計は `build/ridge-surface-half-budget-v2/verification.json`。Python は空間検索との照合を含む 6 テストに成功。既存 RBF 12 条件、B スプライン 9 条件の回帰テストも成功した。槍ヶ岳の 4 分割指定は面数の目安により実際は 2 分割で、592,396 三角形・表示用導出配列 64,692,772 bytes。目視では従来より稜線と斜面の細部が増えたが、骨格に沿う折れは残っている。

比較元の容量表示は選択中の z6～z14 に追従する。`/api/mesh-sizes?region=fuji` が各レベルの元標高メッシュを独立した XYZ＋三角形 JSON＋zlib6 として測る。地域ごとにキャッシュし、表示用ステンシルや曲面係数は含めない。曲面データの生成予算は従来どおり z14 基準で、表示の容量比だけを現在の比較元に合わせる。Chrome で z14→z10→z6→z14 の往復を確認し、富士山の比較元は 557,701→18,601→265→557,701 bytes に切り替わった。

初回読み込みでは比較元メッシュを先に表示し、曲面の準備中も空白にしない。容量の取得は曲面の表示と分離し、失敗しても地形を描く。`test_ridge_loading.cjs` で曲面応答の待機・容量 API の 500 応答・再取得を再現し、表示継続と z10 の容量復帰を確認する。槍ヶ岳の表示、既存 RBF・B スプラインの回帰テストも実施した。

## 尾根・谷の折れを弱める表示（2026-10-26）

すべての推定骨格を鋭い折れとして固定すると、尾根と谷の面が人工的に角張るため、表示時の細分割に折れの強さを追加した。0 は滑らか、0.25 は弱く残す（初期値）、1 は従来の鋭い折れ。外周と山頂の保護点は固定する。骨格上のその他の頂点と辺中点の高さは、通常部の曲面用の重みと従来の骨格用の重みを混合し、平面を再現する補正を行う。XY の分割は同じで、三角形の投影形状を崩さない。

0/0.25 では骨格をまたいで法線を共有する。これは見かけの陰影だけをぼかす操作ではなく、高さの曲面補間も変える。一方、解析的な C1 連続性を保証した曲面という意味ではない。1 の場合は従来の法線分離を使う。保存された制御網と容量は共通で、元データの再生成は不要。曲面の準備は切替時に行い、読み込み中も比較元や既存の描画を残す。表示される RMSE と最大差は保存時の鋭い曲面の参考評価で、柔らかい表示の測定値ではない。

単体テストで傾斜平面の再現、固定山頂の維持、尾根中点の折れが 0→0.25→1 と強くなることを確認する。試験 API は `sharpness=0.25`、画面の設定名は「尾根・谷の折れ」。

折れの調整追加後は単体テスト 8 件に成功。増量版 3 地域で弱い折れの GPU 表示を確認し、中心付近の保護山頂の高さの差は 0、WebGL エラーは 0。槍ヶ岳では弱い折れ→従来→弱い折れの切替も確認した。画像は `build/ridge-surface-half-budget-v2/yari-soft.png` と `yari-sharp.png`。
