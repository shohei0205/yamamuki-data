# B スプライン係数の差分圧縮比較

2026-10-26。富士山・槍ヶ岳・筑波山の既存データを使い、保存方式だけを比較した。元の SQLite と表示用データは変更していない。画面は http://127.0.0.1:61471/ 。区間長を選び、3 地域合計と地域別の容量を確認できる。

## 現行方式と比較条件

入力は `build/bspline-surface-prototype-v3/spline.sqlite3`。現行も粗い曲面との差を補う階層残差であり、差分保存をしていないわけではない。残差が密な領域では位置番号もほぼ全係数に必要になる。複数階層の重複と位置情報を減らせるか調べた。

各地域 32 km 四方。区間数 n は 8・16・32・64・128・256・512、区間長は 4,000～62.5 m。各 BLOB は同じ zlib level 6。SQLite の管理領域、説明用 JSON、HTTP ヘッダー、実装コードは容量に含めない。「全階層」は選択した細かさまでの保存量。「復元に必要」はコールド読み込みで必要な親を含む量。親が既にキャッシュされていれば追加取得量は小さくなる。

独立版と新しい親差分版の対象は、現行ビューアーが GPU へ渡す float32 の一様基底係数。各段の `flatten(layers)` を保存対象にする。元の階層表現との基底変換誤差を新たに増やすものではないが、元の階層和そのものとビット単位で同じという意味ではない。

## 比較方式

- 現行: 疎な位置 uint32 と階層残差 float32 を別々に zlib 圧縮する。
- 位置差分＋バイト整列: 位置番号の差を unsigned LEB128 にし、float32 の同じ桁のバイトをまとめてから圧縮する。係数と位置は完全可逆。
- 係数 XOR: 階層残差の隣り合う float32 のビット列を XOR し、整列して圧縮する。こちらも完全可逆。
- 独立 float32: 選択段の曲面を細かい基底に展開し、曲面へ影響する `(n+5)×(n+5)` 係数だけを保存する。位置番号と親は不要。表示領域内の現行 GPU 係数と一致する。
- 親係数 XOR: 細かい位置に最も近い親の係数ビットを参照し、XOR を保存する。
- 親の節点挿入＋XOR: 親の 3 次 B スプラインを細かい基底へ変換し、予測値と実際の float32 の XOR を保存する。
- 25 cm 量子化: 展開後の制御係数を 0.25 m 刻みの int32 にする。標高画素の量子化ではない。独立保存と親の節点挿入予測との差分を比較する。
- ZigZag: 符号付き整数を `0,-1,1,-2,2,...` に対応する小さな unsigned 整数へ変換し、バイト整列して圧縮する。独立と親差分の両方を測った。
- 独立段併用: n=8・64・256 は独立した量子化係数、その他は直前段からの整数予測差分＋ZigZag。最大 2 回の親参照、合計最大 3 段で復元できる。

## 親予測と復元

1 軸の 3 次 cardinal B スプラインの節点挿入では、偶数の新係数を `(c[i-1]+6c[i]+c[i+1])/8`、奇数を `(c[i]+c[i+1])/2` で予測する。2 軸のテンソル積として計算する。保存配列の先頭は領域の 2 区間外側。子の添字 j に対する親の中心添字は `j//2+1`。

量子化整数版は int64 の分子を 2 軸まとめて計算し、`floor((numerator+32)/64)` で一度だけ丸める。親と差分を足すと、その段で独立量子化した係数へ完全に戻る。したがって量子化誤差は階層数に応じて累積しない。値域は今回の標高に対し int32 の範囲内であることを復号一致で確認した。

float32 予測版は float64 の指定順演算で予測後、float32 へ丸め、XOR を戻す。可逆にするにはエンコーダーとデコーダーで丸めと演算順を一致させる必要がある。今回の Python 間の一致は検証したが、モバイルでの相互運用は未検証。整数予測にはこの浮動小数点の一致条件がない。

## 量子化の精度

係数を最も近い 0.25 m へ丸めるため、係数誤差は最大 0.125 m。B スプラインの基底は表示領域内で非負、重みの和が 1 なので、現行 GPU 係数が表す曲面に対する追加標高差も最大 0.125 m に抑えられる。これは元 DEM に対する誤差ではなく、法線の誤差上限でもない。各モデルのランダム 2,048 点でも照合し、量子化した全方式の最大実測追加差は約 0.107 m だった。

## 判断

可逆のままなら、位置差分とバイト整列が小さな変更で効く。保存全体を減らすなら親の節点挿入予測＋XOR も有効だが、全階層を読む必要がある。独立 float32 はその段だけの取得量が小さい。

25 cm の係数量子化を許す場合は、整数予測差分＋ZigZag に独立段を挟む方式が候補になる。250 m 区間までの保存量は独立保存 101.8 KiB に対し 86.6 KiB、最細区間まででは 1,194.7 KiB に対し 1,013.3 KiB。約 15% 小さくしつつ親参照を最大 2 回に抑えられる。表示までの取得量は独立保存より増えるため、保存量とコールド読み込みのどちらを優先するかで選ぶ。現行表示への採用はまだ行っていない。

## SQLite と検証

比較出力は `build/bspline-codec-comparison-v2/codecs.sqlite3`。`encodings(region,n,method,info,positions,coefficients)`、WITHOUT ROWID。info に親の n、実際の codec、単段と累積の容量、依存込みの取得量を記録する。独立段併用も、メタデータで独立か親差分かを判定する。曲面の領域・次元・係数原点は今回の固定条件から決定する試作で、配布用の完全な形式定義ではない。

3 地域×7 段×11 方式の 231 件を、保存した SQLite と復号済みの親から再構築して照合した。可逆係数はビット一致、量子化係数は整数一致。位置番号・バイト整列・ZigZag の往復、傾いた平面を保つ親予測、保存した全親チェーンの 6 テストに成功。復号中の時間には照合と曲面評価が含まれるため、ランタイムの速度ベンチマークとは扱わない。

```powershell
./build/terrain-venv/Scripts/python.exe -X utf8 tools/terrain/compare_spline_codec.py --output build/bspline-codec-comparison-v3
./build/terrain-venv/Scripts/python.exe -X utf8 tools/terrain/test_compare_spline_codec.py
```

新しい出力先を指定すると 11 方式を再生成できる。旧比較データと既存ビューアーは保持する。比較表は自己完結した HTML で、API や元標高へアクセスせず開ける。
