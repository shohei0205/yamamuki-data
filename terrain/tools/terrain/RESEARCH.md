最終更新: 2026-10-18。Issue #90 に関連する調査とローカル試作の記録。

このメモを今後の調査でも更新する。方式の比較、生成条件、容量、誤差、採用判断が変わったら、該当する節と更新履歴を直す。現在の方針を先に置き、取り下げた方式は比較結果として残す。生成中・完了・未確認を区別し、見積もりを実測値へ置き換えたときは条件も残す。定期実行による更新は行わず、このタスクで新しい結果が得られたときに更新する。

最新の指示は、全国のハイトマップを L7〜L12、JPEG XL d=0.2、法線マップなしで生成すること。生成時の指定は海岸線非表示。全国 11,304 タイルの生成と検証は完了した。その後の指示で、比較ビューワーには DEM 由来の海域ベクターを追加した。Android / iOS の製品機能への組み込み、公開、配布 manifest への接続は未実施。

### 最新データの形式と再生成

256×256 画素のタイルごとに、最低標高と標高差から 16 bit の単一グレースケールを作る。スケールは `max(標高差, 1) / 65535`。復号後の標高は `height_min + decoded * height_scale` で求める。欠損は可逆なビットマスクとして別に Zstd 圧縮する。RGB に標高を分割した画像を非可逆圧縮する方式ではない。

JPEG XL は自動方式、d=0.2、effort 7、線形グレースケール。d はメートル単位の誤差上限ではない。今回の結果では最大追加誤差が L7 で約 61.30 m、L12 で約 31.97 m あるため、低い d でも地形用途としての許容範囲を別途判断する。

SQLite の `tiles` は z/x/y、最低標高、スケール、標高 JPEG XL、欠損マスク、最大誤差、二乗誤差の合計、有効点数を保持する。`metadata` に生成条件と `renderCoastline=false` を記録する。海岸線のベクトルや法線画像は入っていない。この設定を記録することと、アプリ側で海岸の輪郭を描かない処理を実装することは別である。

Rust 実装は `tools/terrain-rs/src/national_height_jxl.rs`。PowerShell 7 で実行する。

```powershell
tools/terrain-rs/build.ps1 -Codecs -Test
tools/terrain-rs/build.ps1 -Codecs
tools/terrain-rs/run-codecs.ps1 --part national-height-jxl --root build/terrain-lod.sqlite3 --output build/terrain-height-jxl-national-L7-L12-d02
```

32 タイルごとに DB を確定し、同じ条件で再実行すると保存済みタイルを飛ばす。設定が違う既存出力への追記と重複起動は拒否する。完了時に件数・DB 整合性を確認し、VACUUM する。異常終了後のロック削除は、生成プロセスの停止を確認してから行う。

## 元データの取得と保持

国土地理院の `dem_png` を使用する。今回の方針は 10 m メッシュで、1 m・5 m メッシュは取得対象にしない。元データの説明は [地理院標高タイル](https://maps.gsi.go.jp/development/demtile.html) を参照する。このリンクは参照先の記録であり、このメモ作成時に利用条件を再確認したという意味ではない。

取得には [tdlmn](https://github.com/gsi-cyberjapan/tdlmn) を調べ、標高目録が使えない場合への対応として `https://cyberjapandata.gsi.go.jp/xyz/std/mokuroku.csv.gz` の L14 座標を標高取得の候補にした。std と DEM の提供範囲は同一ではなく、DEM の存在や完全な網羅を保証する目録ではない。std の MD5・サイズを DEM の検証値に流用しない。

404 は元目録の SHA-256 とともに保存し、同じ目録での再開時に再問い合わせを避ける。429 や一時障害とは分けて扱う。PNG の寸法・形式・CRC・展開を確認し、取得した DEM 自体の SHA-256 を記録する。詳しい取得手順と保存先は README の取得節に残している。

変換元の `build/terrain-lod.sqlite3` は 1,510,574,080 bytes。保存済み L14 は 109,506 タイル。最新の全国変換はこの DB の既存レベルを読み、ネットワークから再取得していない。低レベルの値は元 DB の縮小・量子化を引き継ぐため、「全レベルが詳細 DEM の情報をそのまま保持する」とは扱わない。

バックアップ先はユーザーの指示で `D:\GDIData` に変更した。現在のバックアップの完全性はこのメモ作成時には再検査していない。元 DEM と標高 DB を消さない。

## 表示方式を変えて分かったこと

最初は山頂間の尾根・鞍部を把握するため、DEM から稜線を抽出した。山頂の位置と標高だけから実際の稜線は復元できず、線の抽出・簡略化では接続が途切れる場合があった。連続した山並みを確認するため、ワイヤーフレーム、陰影付き面、格子なし表示へ試作を広げた。

透視投影、マウスでの移動・回転・傾き・拡大、滑らかな陰影、山頂名、隠れる地点の除外、地形が落とす影も試した。これらは複数世代の試作であり、現在の比較ページに全機能が統合されているわけではない。

### ポリゴンと LOD

規則的な四角形分割では、低 LOD の輪郭や陰影に格子状の形が出た。最高詳細の三角形から QEM で削減する方式、境界を越えて処理する方式、手前と遠方で詳細度を変える方式を試した。タイル境界の接続、海岸の輪郭、細い面、平滑化によるのっぺりした表示も課題になった。

削減の検証に失敗した区画で細かい面を保持する処理は、新方式を評価するため外すよう指示があった。過去の容量にはこの保持処理や生成条件の影響があるため、別条件の表をそのまま比較しない。L9・L10 付近ではポリゴンの容量と品質が有利に見える地域試料があったが、全国・全縮尺での優位は確定していない。

生成器は Python から Rust へ移した。ポリゴン生成物は削除済みで、再比較には再生成が必要。現在の採用方針はハイトマップである。

### ハイトマップと法線

ハイトマップは規則的な配列なので圧縮とタイル配信を扱いやすい。形状の詳細度は標高の解像度に依存する。法線だけを高精細にしても、外形や遮蔽に使う地形は細かくならない。

詳細 DEM から作る共通法線、表示 LOD のポリゴンだけから作る法線、詳細法線を LOD の接線空間へ焼き込む方式を比較した。表示形状だけの法線は失われた細部を補えない。焼き込みは詳細法線を表示形状に合わせて復元する比較方法だが、低解像度での補間誤差や基準面との向きの差を評価する必要がある。

法線解像度は標高と独立して選べる。4×4 まで縮小した比較も作った。低い表示レベルで法線を細かくすることは陰影の保持に有効だが、配信量と GPU メモリーが増える。最新の全国データには法線を含めない。

## 圧縮方式の比較

容量、CPU 復号時間、GPU メモリー、実地形に対する誤差を分けて比較する。地域一括の画像と 256 四方のタイルでは圧縮条件が違い、同じ形式名だけでは比較できない。

| 方式 | 試作で確認したこと | 現在の扱い |
|---|---|---|
| PNG | 標高を可逆に保持でき、比較元として使える | 比較画面の基準 |
| YMD1＋XZ / gzip | 標高の丸め・差分・圧縮を試作した | 比較コードを保持 |
| 2 次元差分＋Zstd、階層差分 | 格子の相関や親レベルを使って圧縮した | 比較コードを保持 |
| LERC | 追加誤差なし、およびメートル単位の許容誤差を指定して比較した | 候補として保持 |
| ASTC | 圧縮のまま GPU 参照する標高・法線を試作した | 実機検証は別途必要 |
| meshoptimizer＋Zstd | ポリゴンの頂点・接続を圧縮した | コードのみ保持 |
| JPEG XL | 可逆と非可逆、タイル分割、自動と Modular を比較した | 最新の全国標高に採用 |

JPEG XR という指定は途中で JPEG XL の意味だと確認した。現在の試作・全国生成は JPEG XL であり、JPEG XR を採用した結果ではない。

### 同一地域の標高での参考値

過去の槍ヶ岳周辺 L14 の試料。全国 L7〜L12 の最新生成とは入力範囲・d が違うため、全国容量の実測として扱わない。

| 方式 | bytes | 最大追加誤差 m | RMSE m |
|---|---:|---:|---:|
| 256 四方の可逆 JPEG XL | 1,827,495 | 0 | 0 |
| 256 四方の JPEG XL d=0.5 | 1,057,025 | 21.38 | 1.69 |
| YMD1＋XZ | 2,821,867 | 0 | 0 |
| ASTC 12×12＋Zstd | 1,674,841 | 36.20 | 2.65 |

同じ試料でも地域一括 JPEG XL d=0.5 は 325,038 bytes・最大追加誤差約 45.90 m となった。小さくなった分だけ良い方式と判断せず、タイル取得・再利用の単位と誤差をそろえる。

JPEG XL はファイルが小さくても GPU では通常の画素配列へ展開する。ASTC の GPU 上の容量と JPEG XL のファイル容量は別の指標である。PC の Web プレビューではサーバー上の cjxl／djxl を使っているため、Android / iOS の端末内復号性能を確認したことにはならない。

### JPEG XL のノイズと境界

高圧縮ではブロック状のノイズが見えた。Modular も試したが、ユーザーの目視ではタイル状の格子が目立ち、全体として自動の方が高品質だった。現在の初期値と最新全国生成は自動方式。Modular の同じ d が自動と同じ品質を意味するわけではない。

境界対策として、16 画素の余白、重複範囲の重み付き結合、共通の標高スケールを試した。槍ヶ岳 L11・法線 512 四方・標高と法線 d=0.5 の試料で、自動の標高境界追加誤差の段差は約 41.55 m から約 40.34 m へ下がったが、容量と最大誤差は増えた。改善は小さく、格子ノイズの解消は未確認。試験機能として残し、最新の全国生成には適用していない。

タイル境界を見るため、各 L4〜L14 の実データを 2×2 タイルにした比較を追加した。小画像を引き伸ばす処理ではなく、各レベルの隣接タイルを使う。この表示ではレベルによって地理的な範囲が変わる。標高は赤、法線は青の境界線を重ねられる。

## 全国縮尺の陰影と共通テクスチャ

全国を高い LOD の全ポリゴンで描くと重くなる。一方、粗い標高だけで陰影を作ると山並みが平らに見えるため、形状と陰影の解像度を分離して比較した。

全国比較では、詳細 DEM の法線を平均して使う方式と、詳細 DEM で照明を計算してから縮小した陰影画像を切り替えられる。後者は小さな尾根・谷の明暗を縮小画像に残せるが、太陽位置に依存する。法線は光源変更に追従できるが、平均した向きだけでは細かな陰影が消える。全国の比較画像は L14 から各表示レベルへ生成し、低解像度画像を拡大して詳細に見せる処理はしない。

全国比較の L4〜L7 は法線・陰影とも 448、896、1792、3584 四方。法線と縮小陰影、光源の方角と高さを比較できる。縮小陰影の別光源はサーバーで再生成する。海岸線は別途解決する方針で、全国比較でも輪郭表示を外している。

共通テクスチャ方式は、標高から得た斜面の向きへ、端末内で生成する 256 四方の高さ模様を重ねる。地形ごとの法線画像は不要で、追加の配信データは 0 B、ミップマップ込みの GPU 容量は約 85 KB。模様の大きさと強さを調整でき、緩斜面・遠景では弱める。

共通模様は見た目の細かさを補う試作であり、実際の尾根・谷を復元しない。法線マップと同じ視点・光源で切り替えられる。最新の全国データに法線が無いことは、この模様を製品の表示方式として確定したことを意味しない。

## その他の表示データ

河川、海・湖・池などの水域、登山道、県境は、地形とは独立して切り替える要望がある。複数 LOD の線・面と地形を組み合わせる試作を進めた。水域だけの表示も検討・試作した。最新の標高のみの DB にはこれらのレイヤーは同梱していない。

海岸の輪郭は低 LOD の DEM マスクだけだと四角く荒れるため、国土地理院最適化ベクトルタイルの海域から輪郭を作る方式も試した。標高のみの全国生成時には海岸線を描画しない方針だった。その後、別リポジトリの DEM 由来ベクターを参考に、比較ビューワーへ海域表示を追加した。元のベクトルデータは削除しない。

利用条件・出典表記・再配布条件は、DEM、国土地理院ベクトル、OSM ごとに整理が必要。既存のアプリの OSM 表記は維持する。このメモは再配布の許諾確認を完了した記録ではない。

## 別リポジトリの海域・河川ベクター実装

2026-10-18 にユーザー指定の `D:\GitHub\yamamuki` の作業ツリーを参照した。HEAD は `07fb031e8e360335a1140807c36656fd348fe592`。README などには未コミットの変更があるため、参照内容をすべてこのコミットの確定仕様とは扱わない。参照先のファイルや生成物は変更していない。

### レイヤーと保存形式

| 対象 | 保存先 | 形式・由来 |
|---|---|---|
| 河川中心線 | `rivers/{z}/{x}/{y}.riv` | RIV1。OSM の線形データ |
| 湖・池・貯水池・幅のある河川 | `water/{z}/{x}/{y}.wat` | WAT1。OSM の面データ |
| 海域 | `sea/{z}/{x}/{y}.wat` | WAT1。陰影地形と同じ DEM の有効・欠損境界から生成 |

タイル座標は Web Mercator、タイル内座標は 0〜4096 の uint16。RIV1 はマジック 4 bytes、uint32 線数、各線の uint32 頂点数と uint16 x/y 列で構成する。WAT1 はマジック、uint32 面数、各面の種別・リング数、各リングの頂点数と x/y 列を持つ。いずれもリトルエンディアン。WAT1 は先頭リングを外周、残りを島などの穴として保持し、閉じる始点は重複保存しない。海域か内水面かは保存ディレクトリでも区別する。

これらは標高を持たない 2D ベクターで、参照先では ZIP 内の DEFLATE で保存している。現在のハイトマップ用 SQLite にそのまま同梱済みという意味ではない。

### タイル境界と表示量

河川は z10・z11・z12 の 3 段階。512 px 換算の簡略化許容差は 2・1・0.3 px。線全体を簡略化してからタイルで切り、隣接タイルの境界交点を一致させる。表示範囲が広いときは長い川を優先する。同名かつ端点が接続する区間をまとめた総延長を使い、z10 は 20 km 以上、z11 は 5 km 以上、z12 は全区間を対象とする。離れた同名河川はまとめない。これは描画優先度の推定で、法的な河川区分ではない。元 GeoJSON 自体の簡略化や未収録地域は残る。参照先 README には北海道の大部分の河川が未収録とある。

内水面も全体を簡略化してからタイルで切り、重複面は同種ごとに統合する。湖・河川の島や穴を保持し、Android は EVEN_ODD、iOS は eoFill で描画する。

海域は隣接 DEM を含む 272 四方の標高配列から、有効点と欠損点への距離の差を計算し、ContourPy でゼロ境界の面を抽出する。外周と穴を対応付け、簡略化後にタイルへ切り出す。海岸専用 PNG や外部の海岸線ベクターを使う方式ではない。DEM の欠損を海と見なす前提があるため、データ不足と海域の区別は適用先でも確認が必要。

### Android / iOS での利用

Android は `TerrainData.kt` で ZIP から、iOS は `RiverStore.swift` で同梱 Terrain フォルダーから表示範囲のタイルを読む。両 OS に RIV1 / WAT1 のデコーダーがあり、復号した河川と水面をそれぞれ約 8 MiB 上限のキャッシュに置く。観測地点を基準に投影したパスを再利用し、画面外のバッチを除外する。河川はタイル内でも空間的に分けてまとめる。

地形画像と水面・河川は別レイヤー。参照先では地形または河川が ON のとき海・湖を表示し、両方 OFF なら消す。こちらの海岸線非表示という現在の指示へ、その表示条件をそのまま移さない。

### 今回の試作で参考にする点

- 標高 JPEG XL と、水面・河川ベクターを独立して保持し、地形なしの水域表示やレイヤー別更新を可能にする。
- RIV1 / WAT1 の単純な座標形式、簡略化してから切る順序、穴の保持、バッチ化とキャッシュを参考にする。

### 参照方式を使った海域表示の実装

2026-10-18 の追加指示で、全国比較と地域別比較に「海域ベクター」を追加した。初期値は ON。OFF にして従来表示と比較でき、視点・光源・地形レベルは保持する。参照先と同じく DEM の有効・欠損境界から符号付き距離場を作り、ContourPy の OuterOffset で外周と穴を抽出する。簡略化・量子化した WAT1 と、穴を避けた描画用三角形 SEA1 を保存する。WebGL では海を標高約 0 m の独立した青い面で描く。

## 日時による太陽位置のシミュレーション

2026-10-18 に全国・地域の比較ビューワーへ日時指定を追加した。初期値は現在の JST。入力は分単位で、JST（UTC+9）から UTC の瞬間に変換する。端末のローカルタイムゾーンには依存しない。「−1 時間」「＋1 時間」「現在」と日時欄で操作し、従来の手動方角・高度指定にも戻せる。

日本の標準時は共通でも、実際の太陽時は経度で異なる。均時差と太陽赤緯を日時から求め、経度を含む時角と緯度から東・北・上の太陽方向を計算する。経度 1° の差は約 4 分の太陽時差に相当する。全国を一つの方向で照らさず、各描画地点で方向を求めるため、日本の東西で同じ JST の日の出・日の入りが異なることを反映できる。

計算は [NOAA の計算法の説明](https://gml.noaa.gov/grad/solcalc/calcdetails.html) と [太陽位置の式](https://gml.noaa.gov/grad/solcalc/solareqns.PDF) を参照した。実装は `solar-position.js` と `solar_position.py`。均時差・赤緯にはユリウス世紀から求める式を使う。大気屈折、地形による太陽の遮蔽、観測者の標高による地平線の変化、気象は含めない。幾何学的な太陽高度が 0° 以下なら直射光を切る。薄明の明るさは表示用の近似で、物理的な照度計算ではない。

法線マップと共通模様の陰影は日時変更を即時反映する。縮小陰影画像は指定日時で Rust 生成器を動かして再生成する。日時別キャッシュは `build/terrain-national-sun/tYYYYMMDDTHHmm/`。詳細 DEM の各点で太陽方向を求め、照明を計算してから縮小する。手動光源の既存キャッシュと分け、画像が古い日時・光源のままなら画面に明示する。新しい日時での全国生成には数分かかり、日時を変えるたびに自動で全国データを生成する処理は入れていない。

確認した内容は以下のとおり。

- [NREL の参照例](https://docs.nlr.gov/docs/fy08osti/34302.pdf) の 2003-10-17 19:30:30 UTC、緯度 39.742476°・経度 −105.1786°で、方位・高度を 0.1° の許容差で照合した。参照値は屈折を含むため、この照合を全条件での精度保証とは扱わない。
- 春分ごろの JST 6:00、同じ緯度 35°の経度 130°では太陽が地平線下、145°では地平線上になることを確認した。夏至・冬至の高度差、夜間、うるう日を含む日時の入力検査も行う。
- `test_solar_position.cjs`、`test_solar_position.py`、`test_solar_display.cjs` で位置計算、JST、日時別キャッシュキー、生成コマンド、画面変化、視点保持、手動切替、夜間を確認した。Rust テストは追加分を含め 27 件成功。
- Rust の縮小陰影は東西 2 タイルの実 DEM でも生成し、西の直射光が 0、東が 0 より大きいことを確認した。この日時で全国の陰影画像を生成済みという意味ではない。

太陽シミュレーションは表示の機能であり、完成済み L7〜L12 の標高 JPEG XL DB は変更しない。

## 河川・湖沼の表示

2026-10-18 に全国表示と地域別比較へ「河川」「湖・沼」の切替を追加した。河川は中心線と幅のある河川の面、湖沼は湖・沼・池・貯水池などの水面を表示する。OSM の水面として収録された形状が対象であり、湿地の植生や季節ごとの水位を再現するものではない。海域・河川・湖沼は個別に ON/OFF でき、レベル・光源・JPEG XL 圧縮形式を変えても表示設定を保つ。

参照先 `D:\GitHub\yamamuki\app\src\main\assets\offline\terrain.zip` の保存済み RIV1 / WAT1 を読み、ネットワークへ再取得は行っていない。入力パックの SHA-256 を確認・記録し、参照先は変更していない。参照パックの河川は `complete=false` で、北海道の大部分が未収録という制約を引き継ぐ。

入力は河川 7,106 タイル、水面 8,441 タイルの計 15,547 タイル。`build/terrain-inland-vectors/source.sqlite3` に生のベクターを保存し、元 manifest、NOTICE、ODbL、河川・水面 GeoJSON と来歴ファイルも保持する。画面のフッターに OSM の出典とライセンスへのリンクを置いた。国土地理院 DEM の海域と OSM の水面は別の素材である。

生成コードは `inland_vectors.py`、表示は `inland-vectors.js`。全国と地域別の計 45 範囲を用意した。通常の地域比較は地形 LOD によらず同じ範囲のベクターを使う。実タイル 2×2 の比較は表示する地理的範囲に合わせて切り出す。地域幅が 50 km 以下なら z12、200 km 以下なら z11、それより広ければ z10 を選ぶ。全国比較は z10 の同じベクターを共用する。この初期方式では全国画面のズーム操作だけで詳細化しなかった。後述の東京湾の修正で、表示範囲に応じた z10〜z12 の取得へ変更した。

WAT1 の外周と穴を復元し、穴を避けて三角形化する。河川線と水面の描画用座標を正規化した INL1 パケットにまとめ、サーバーは保存済みデータを中継する。全国パケットは 6,341,804 bytes、筑波山の実タイル L10 範囲は 429,919 bytes、槍ヶ岳の通常比較範囲は 124,793 bytes。これらは試作用の未圧縮パケットで、配布形式の最終容量ではない。標高 JPEG XL の全国 DB は変更しない。

当初の水面三角形を 3D 空間へ直接重ねる描画では、地形との高さの差で縞が出た。現在はベクターを GPU 上の一時的な 2048 四方のマスクへ描き、地形のフラグメントで河川・湖沼の色を重ねる。保存・転送はベクターで、マスク画像を配信する方式ではない。ミップマップ込みのマスクは約 22.4 MB の GPU メモリーを使う。海面と違い、湖面を実際の一定標高へ水平化する処理はなく、表示中の DEM 面に沿う。当初は全国全体を固定解像度で描いていたため、拡大時に格子状に見えた。東京湾の確認後は表示範囲を覆う局所的なマスクに描き直す方式へ修正した。

`test_inland_vectors.py` の 2 件で、RIV1 の復号・不正データ、範囲での切り出し、WAT1 の島の穴が三角形で覆われないことを確認した。全 45 パケットの寸法・頂点範囲・有限値を検査した。`test_inland_display.cjs` では全国と筑波山の描画、河川・湖沼の個別切替、視点保持、地形 LOD と JPEG XL の変更、WebGL エラーなしを確認した。Android / iOS の本アプリへの移植は未実施。

### Progressive Mesh の検討（2026-10-19）

検討の結論: 同じ一辺の複数品質を「粗い基底メッシュ＋追加情報」にまとめる候補として有効。ただし圧縮後サイズの削減率とスマホでの復元時間は未測定で、採用はまだ決めない。今回、生成器・データ形式・表示処理は変更しない。

一次資料:
- Progressive Meshes（Hoppe, SIGGRAPH 1996）: https://hhoppe.com/proj/pm/
- Efficient Implementation of Progressive Meshes（1998）: https://hhoppe.com/proj/efficientpm/
- View-dependent Refinement of Progressive Meshes（1997）: https://hhoppe.com/proj/vdrpm/
- Smooth View-dependent Level-of-detail Control and Its Application to Terrain Rendering（1998）: https://hhoppe.com/proj/svdlod/

標準PMは詳細メッシュを辺縮約し、逆操作の頂点分割を記録する。基底と復元列で段階配信でき、同一タイル内を視点に応じて部分詳細化するVDPM、切替時の形状変化を補間するgeomorphへ拡張できる。地形に対するブロック単位の構築も研究されている。これらは保存形式とCPUでの復元の技術であり、特殊なGPU描画命令を前提としない。Android/iOS向けの案はRustによる共通復元器、Web比較はWASMまたはWorkerで復元し、通常の頂点・インデックスバッファを渡す構成とする。実端末性能の確認は別途必要。

現在のRust Builder::insertはBowyer–Watsonのcavityに含まれる面を削除し、境界辺から新頂点への扇形を追加する。頂点配列は追加順だが、Meshの出力には面の更新履歴は残らない。この更新は標準PMのvertex splitと同一ではない。現方式を生かすなら「挿入履歴付きTIN」と呼び分け、新頂点の座標・属性、削除面、追加面（または境界頂点列）を記録する。復元側にDelaunay探索をさせず、事前計算済みの接続変更だけ適用する。地形の削減誤差を再評価する別の簡略化アルゴリズムを導入せず、元DEMとの最大標高誤差を生成側で直接測定できる利点がある。

比較すべき3方式:
1. 共有頂点＋品質別の完全インデックス。復元が単純で高速。品質が2～3段階・数千頂点なら、圧縮後に履歴方式より小さくなる可能性もある。
2. 挿入履歴付きTIN。既存の挿入処理へ記録を追加し、基底から追加分だけ配信する。局所的な面削除・追加の記録が増えるため、小容量になるとは限らない。
3. 標準PM。辺縮約の逆操作を保存する。実績ある設計だが、今の生成器への記録追加だけでは実装できず、縮約生成・属性保持・誤差測定を追加する必要がある。

試作案: 一辺16 km内の品質だけを対象とし、基底＋2段階の拡張BLOBをSQLiteの別行へ保存する。128/512/2048頂点などは比較用の上限候補で、レベルの正式な決定値ではない。各段階へ実測最大標高誤差・頂点数・面数・圧縮バイト数を付ける。挿入によるDelaunay再接続後の誤差が単調減少するとは仮定せず、各公開段階を実測する。段階ごとのチェックポイントを置き、任意段階へ毎回最初から大量の履歴を再生することを避ける。基底と追加BLOBは独立圧縮し、基底表示時に詳細BLOBを読まない。差分の座標・頂点番号は整数量子化・可変長整数を候補とする。標準PMの圧縮率を独自TIN履歴の圧縮率として流用しない。

タイル境界は先に共通の頂点・標高列を確定し、内部だけを段階的に追加する。両隣で別々の品質を選んでも同じ境界を使う。境界頂点も最大頂点数に含め、境界だけで予算超過するケースを検出する。固定境界を詳細にしすぎると粗い段階の負荷が下がらないので、境界点数と境界誤差も測定する。一辺16 kmと8 kmのようにタイルサイズ自体が変わる切替は別の空間階層であり、PMだけでは自動接続しない。親子間の境界整合も別途検証する。

頂点法線も共有するなら、同じ頂点の値が品質ごとに変わらない定義が必要。現行の頂点密度依存フィルターは品質別に法線が変わるので、そのまま1配列へ統合できない。固定したDEM法線を共有する案と、品質別法線差分を持つ案を比較する。メッシュ形状に依存する法線差分・焼付補正は、対象の形状段階と対応付ける。形状切替だけでは陰影の連続性は保証されない。

描画時は毎フレーム履歴を復元せず、必要品質が変わったときにバックグラウンドで処理し、GPU更新をまとめる。基底だけを表示する際に最大品質分のCPU隣接情報やGPUバッファを確保しない。粗い方への切替は少数段階のキャッシュかチェックポイント復元を使い、不要データを退避する。タイル全体の品質切替を先に検証し、面単位のVDPMやgeomorphは必要性を測定してから追加する。

検証項目: 富士山・槍ヶ岳・平野での基底容量／追加容量／全段階容量、独立LOD保存と共有頂点インデックス保存との圧縮後比較、初回表示と品質切替の時間、CPU/GPUピークメモリー、各段階の最大標高誤差、境界の隙間、陰影の変化。16 kmの比較元は32 kmの保存済みDEMから取り直し、クリップ後のメッシュへ追加順を後付けしない。現在の地域全体生成→タイルクリップ方式では、実際のタイルごとの挿入履歴を復元できないため、共有境界を初期頂点とするタイル単位生成が必要。


### Geometry Clipmaps の確認（2026-10-19）

参照: Losasso・Hoppe「Geometry Clipmaps: Terrain Rendering Using Nested Regular Grids」（2004）https://hhoppe.com/proj/geomclipmap/ 、著者公開論文 https://hhoppe.com/geomclipmap.pdf 、Asirvatham・Hoppe「Terrain Rendering Using GPU-Based Geometry Clipmaps」（GPU Gems 2, 2005）https://hhoppe.com/proj/gpugcm/ および https://hhoppe.com/gpugcm.pdf 。

Progressive Meshとは別の地形LOD方式。視点の周囲へ同じ頂点数の正規格子を重ね、外側ほど標本間隔を2倍にする。最内周以外は内側を抜いた帯だけ描く。視点移動では循環バッファの新しく入る帯だけを更新し、境界付近は粗い標高へのモーフと接続用メッシュでつなぐ。単なるタイル別LODではなく、視点中心の有限キャッシュ・差分更新・境界遷移を一体で扱う。高度が高い場合は細かすぎる段階を無効にする。

GPU版ではXY格子とインデックスを固定し、標高を頂点シェーダーから読むテクスチャへ分離する。規則的なブロックのバッファを位置・倍率だけ変えて再利用する。CPUは主に保存データのデコードとアップロードを担当する。現在の比較画面のハイトマップも頂点シェーダーのtexelFetchで高さを取得しているので、「GPUで高さを読む」だけでは新方式にならない。差は、地域・タイルごとに独立した格子バッファを常駐させるのではなく、視点中心の一定量の格子と循環する標高キャッシュを使うことにある。

今回への評価（設計上の推論、実測前）: ドラッグ・回転の負荷安定性、端末メモリー上限、手前と遠景の品質遷移を優先する比較候補として、PM試作より先に試す価値がある。地形の起伏に応じて頂点数を節約するTINとは異なり、平野にも一定の格子を使う。ポリゴン数は増える場合があるが、データ構造とバッファが規則的なため、描画の速さは頂点数だけでは比較できない。全国保存量が小さくなるかは別に測定する。

保存形式と描画キャッシュを分ける。SQLite内のハイトマップ・画像圧縮は従来のものを利用できる可能性がある。取得した画像タイルをデコードし、必要な標高配列をクリップマップの窓へ転送する。論文の圧縮率は画像ピラミッド・残差圧縮・品質条件に依存するため、現在のJPEG XLデータへそのまま当てはめない。粗い段階からの予測値＋詳細残差という保存方式は別の比較候補。論文のノイズによる細部合成は本アプリの地形再現へは採用しない。

L16_1等は配布データの一辺と品質を示す識別子として残す。クリップマップの描画段階は格子間隔とキャッシュ窓サイズで定め、配布タイルとの対応を別に持つ。法線は標高からGPU計算する案と高解像度の保存法線を使う案の両方が考えられ、クリップマップ化のために法線画像を必ず配布する必要はない。粗い形状では山のシルエット・標高精度が失われるので、陰影のみで補う判断をしない。

試作案: 既存TIN・ハイトマップ比較を残し、共有格子＋GPU標高読み取り＋2倍間隔の帯＋境界モーフを別モードへ追加する。初期は標高データの追加生成をせず、既存データで描画構造の差を確認する。データ取得・画像デコード・GPU転送は更新予算を持たせ、細部が未取得なら粗い段階で覆う。フレーム時間、GPU転送量、ピークメモリー、移動中の欠落、真上と水平視点の品質、山頂シルエットと標高誤差を比較する。Android/iOSでの実機性能はまだ未検証。今回の作業は調査と記録のみで、生成器・データ・表示実装は変更していない。
