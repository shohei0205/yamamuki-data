# Rust ネイティブ地形ビューワー

全国地形 SQLite を直接読み取り、Windows と macOS で表示する検証用アプリ。Web 版はそのまま残しています。Rust / eframe 0.31 / wgpu 24 / egui / rusqlite を使用し、Windows の標準は DirectX 12、macOS は Metal です。比較試験では `WGPU_BACKEND` 環境変数でバックエンドを明示できます。GPU 名とバックエンドを起動ログへ記録します。HTTP サーバー、ブラウザー、WASM は不要です。

## 起動

Windows では `run.bat` をダブルクリックすると標準の全国 SQLite で起動します。SQLite ファイルを `run.bat` にドラッグ＆ドロップして別のデータを開くこともできます。実行ファイルがない場合は PowerShell 7 で初回ビルドします。

PowerShell からは terrain ディレクトリで次を実行します。

```powershell
./tools/terrain-viewer/run.ps1
# 別の SQLite を指定
./tools/terrain-viewer/run.ps1 -Database C:/path/to/terrain.sqlite3
# ソースを変更したあとの再ビルド
./tools/terrain-viewer/run.ps1 -Build
```

標準のデータは `build/terrain-national-xyz-20261024/terrain.sqlite3`。実行ファイルは `build/terrain-viewer-target/release/terrain-viewer.exe` に出力します。通常の Rust がない環境では、既存の terrain 用ローカル Rust / LLVM MinGW を使います。SQLite、生成処理、Web 配信サーバーには変更を加えません。

macOS では Rust と Xcode Command Line Tools を用意し、同じ terrain ディレクトリから実行します。

```sh
sh tools/terrain-viewer/run.sh /absolute/path/to/terrain.sqlite3
```

macOS 専用のソース分岐は不要です。ただし現時点の実機確認は Windows のみで、macOS のビルド・表示は未確認です。別の OS 向け実行ファイルをコピーするのではなく、それぞれの OS でビルドします。署名・公証・インストーラー作成は行っていません。

## 操作と表示

- 左ドラッグ: カメラの向きに合わせて平行移動。
- ホイール: 拡大縮小。
- 右ドラッグ: 方角・傾きを変更。
- 全国・富士山・槍ヶ岳・筑波山のボタンで視点を移動。
- 自動 LOD の上限、または固定の z6〜z14 を指定。自動LOD品質は0.5～4倍のスライダーで調整し、標準は2倍。
- Loop 曲面の最大分割数をなし・2・4・8から選択。画面上の大きさに応じて面ごとに分割し、画面内200万面とGPU生成メモリを別に制限する。
- 形状保持を 0〜1 で調整。0 は Loop の形、1 は元の平面を分割した形。変更時は GPU の計算処理で位置と法線を更新し、SQLite の読み込みや CPU の接続表生成を行わない。
- 滑らかな陰影の ON/OFF、陰影の強さを切り替え。
- 設定パネルは折りたたみ可能。元の面数、描画面数、描画頂点数、適用分割数、組み立て時間、GPU 保持量を表示。

LOD 切り替え中は直前の表示メッシュを維持し、新しいメッシュが完成してから交換します。ズーム距離や移動距離によって強制的に z6 へ戻しません。

全国 z6 の 22 タイルは起動直後に読み込み、CPU・GPU の両方で保持します。通常のキャッシュ整理や地域切り替えでも追い出しません。初回読み込み中や地域切り替え時の表示にも使い、表示済みメッシュがある場合も、そのメッシュが描かれていない範囲だけを補完します。キャッシュはプロセス内だけで、終了時に解放します。

## 処理の分担

`data.rs` が SQLite を読み取り専用で開き、YMV4 の親頂点参照を再帰的に復元します。三角形は YMT3 の本体部分を TFC2 から復元します。親参照と TFC2 のコーデックは `../terrain-rs/src/` の既存 Rust 実装を共有し、別の形式や圧縮処理は導入しません。XY は世界幅 2^28 の整数格子からメートルへ変換し、標高は既存の地上 25 cm・海底 50 cm の規約に従います。

専用スレッドがタイル選択・デコード・接合・元メッシュの辺と所有面の情報作成を担当します。Loop の分割後の頂点・面・接続リストは GPU で生成します。操作中は前の地形を描画し続け、新しい結果が完成してから交換します。視点要求は最新のものにまとめ、移動中も 100 ms を目安に送ります。処理中の要求は一つまでとし、移動だけなら途中で完成した結果も表示してから最新視点へ追従します。地域・レベル・曲面分割などの設定を変えた場合は世代を更新し、前の設定の結果を表示しません。GPU の作成と描画は GUI スレッドで行います。作業スレッドからは元メッシュと制御用の連続配列だけを転送します。GPU が分割後の接続情報を作るため、CPU で分割数に応じて増える配列を作りません。大きな GPU バッファの初回転送による停止時間は残り得ます。

`selection.rs` は画角・画面上の推定誤差・面数からタイルを選択します。自動は「自動LOD品質」0.5～4倍で調整し、目標誤差は3 px÷品質倍率です。標準を従来の1倍（3 px）から2倍（1.5 px）へ変更しています。元データ35万面・192タイルを上限とし、隣接レベル差は 2 段を目安に、予算がある場合は粗い側を詳細化します。差をそろえるために細かい側を粗くすることはありません。予算や元データの都合で差を縮められない境界は、既存の混在接合で処理します。曲面分割数を変えても元データの LOD は変えません。固定では指定レベルを維持し、50 万面・256 タイルを超える場合はカメラを近づけて範囲を狭めます。

`geometry.rs` は同レベルでは同じ XY の頂点・同じ面を共有します。混在 LOD ではタイルの本来の範囲で面を切り、隣接する粗細の境界頂点列をそろえ、詳細側の境界高さで再分割します。部分的な隣接も区間単位で扱います。接合時の切断面には、保存メッシュの最小角 10° の保証は適用しません。追加の標高データや接合用 SQLite は不要です。

Loop の分割後の三角形、辺上と面内の追加頂点、接続面リスト、曲面上の位置は Compute Shader で生成します。元のメッシュの辺番号と整数の重心座標から頂点番号を決め、隣接面で同じ辺の点を共有します。GPU 上で面リストを作り、前の段の接続を参照して 2→4→8 分割と進めます。CPU へ頂点数や座標を読み戻す処理は通常の描画にはありません。CPU はタイルの復元・接合と、元メッシュの辺・所有面の情報だけを用意します。

`render.rs` の GPU 計算シェーダーが、元の平面を分割した位置と Loop の位置を形状保持に応じて混ぜ、変形後の三角形から頂点法線を計算します。DEM 頂点法線や追加の曲面ヒントは読みません。分割結果は GPU に保持し、形状保持が変わらないドラッグ・回転中は再計算しません。地形・カメラ・描画設定が同じ場合は地形を再描画しません。GPU コマンドは egui の画面描画と同じバッファで送ります。ただしメッシュが変わったときの分割生成は、描画に先行する GPU コマンドとして一度実行します。

wgpu 24 はハル／ドメインシェーダーによるハードウェアテッセレーションを公開していないため、Windows と Mac で共通に使える Compute Shader を採用しています。

描画シーンは最大 6 個・GPU 約 384 MiB を目安に保持し、選択タイルと分割数が同じ場合に再利用します。作業スレッドの組み立て済みキャッシュは最大 6 個・192 MiB、復元済み頂点キャッシュは 256 MiB が整理開始の目安です。表示中のシーンと全国 z6 は上限より優先して保持するため、厳密なメモリ上限ではありません。シーンごとに座標原点を持ち、描画時にカメラとの差分を渡して、全国座標を f32 で直接持つことによる精度低下を避けます。

日本語フォントは OS のフォントから読みます（Windows: Meiryo、macOS: ヒラギノ角ゴシック）。フォントファイル自体は再配布しません。

## 2026-10-25 の操作と描画の修正

上下ドラッグで地形が逆方向へ動いていたため、左右と同じくマウスに追従する向きに修正しました。カメラの方角を変えても同じ操作になることを単体テストで確認しています。

富士山・Loop 4 分割・約 187 万描画面で、高速化前後の地形描画領域は画素単位で一致しました。GPU の保持データは同条件で約 167 MiB から約 109 MiB へ削減。初期の「約 60 fps」は GUI 更新時刻の平均から算出しており、滑らかさの判断には不十分でした。計測を地形の画面描画コールバックに変更し、重複する GUI 更新や同じ画像の再表示を数えないように修正しました。NVIDIA GeForce RTX 5060 Ti で同じメッシュを回転した 120 フレームでは、Vulkan は平均約 16.7 ms でも p95 が約 33.4 ms、DirectX 12 は平均約 16.7 ms・p95 約 16.8 ms でした。この実測から Windows の標準を DirectX 12 に変更しています。

地形画面の右上に FPS と描画間隔の p95 を重ねて表示します。設定パネルを折りたたんでも表示します。FPS は直近 1 秒の変更された地形の描画回数です。停止中の同じ画像はカウントせず、操作停止後は「停止中」と表示します。これは画面描画コマンドの記録時刻による計測であり、ディスプレイが実際に走査・提示したフレーム数ではありません。`--benchmark-output` は選択済みメッシュの回転試験で、新しい LOD の読み込みを伴う操作全体の保証ではありません。

```powershell

./build/terrain-viewer-target/release/terrain-viewer.exe build/terrain-national-xyz-20261024/terrain.sqlite3 --region fuji --divisions 4 --benchmark-output build/native-performance.json
```

## 連続操作中の LOD と HTML 版の色合わせ

連続ドラッグで LOD が更新されなかった原因は、入力のたびに更新期限を延ばす待ち方と、移動のたびに完了結果を古いものとして捨てる判定でした。期限を延ばさないスケジューラーへ変更し、移動中も同じ設定世代の完了メッシュを反映します。処理中に届いた視点は一つに集約して次に送るため、未処理の要求が積み重なることはありません。地域・レベル・曲面分割・表示サイズの変更は前の世代と区別します。

淡い色の原因は、HTML 版で画面用の RGB として出力していた色を、egui が線形 RGB として受け取り、もう一度明るく変換していたことでした。地形の描画先を sRGB テクスチャへ変更し、シェーダーの最終 RGB を線形値へ変換して渡します。色・照明・標高色の式は HTML 版と共通に保ち、背景も同じ RGB (.90, .945, .98) に合わせます。比較条件をそろえてもメッシュや法線の違いによる陰影差は残ります。

```powershell
# 4秒間の連続移動で、移動中の要求・適用回数を保存する
./build/terrain-viewer-target/release/terrain-viewer.exe build/terrain-national-xyz-20261024/terrain.sqlite3 --region fuji --divisions 4 --drag-test-output build/continuous-lod.json
# 高さ0の試験用SQLiteを別ファイルへ作り、地表色と背景色を画素で照合する
./build/terrain-venv/Scripts/python.exe -X utf8 tools/terrain-viewer/test_color.py --source build/terrain-national-xyz-20261024/terrain.sqlite3 --binary build/terrain-viewer-target/release/terrain-viewer.exe --output build/native-color-check
```

色の試験は既存の試験 SQLite を上書きしません。再実行時は別の出力フォルダーを指定します。元の全国 SQLite は読み取り専用で扱います。

## GPU 曲面分割の検証

`build.ps1 -Test` では、シェーダー検証に加えて実際の GPU を使う照合テストを実行します。平面と山型のテストメッシュを 1・2・4・8 分割し、GPU の座標と面を読み戻して、旧 CPU Loop の位置（誤差 1 mm 以内）と面の接続を比較します。したがってテスト実行にも GPU が必要です。`loop_reference.rs` の CPU 分割はこの照合専用で、通常のビューワーには組み込みません。

Windows / DirectX 12 で 25 テストに成功。全国 SQLite の富士山では約 187 万描画面・939,530 頂点で、CPU 版と GPU 版の地形画像差は最大 2 階調、99% の画素では差なしでした。CPU の準備時間は同条件で約 0.51→0.10 秒でした。GPU 生成時間や画面への提示までを含む値ではありません。槍ヶ岳の表示と筑波山の連続 LOD 更新も確認しています。Mac の実機確認は未実施です。

## z6 による不足範囲の補完

表示済みのメッシュを先に描いてステンシルへ印を付け、印のない画素だけに常駐 z6 を描きます。粗い z6 が詳細地形より高くても、その詳細地形を上書きしません。表示全体を z6 へ置き換える処理とは別です。補完用の z6 は追加の読み込み・曲面分割・タイル接合を行わず、常駐 GPU バッファを使用します。地域原点が異なるため、主表示と補完用には別のカメラ定数バッファを渡します。

`test_underlay.py` は新しい LOD を取得せずに4倍ズームアウトした状態を作り、同じカメラ・同じ表示メッシュで補完なし／ありの画像を比較します。空白が減ることと、表示済み地形の内部の色が維持されることを確認します。

```powershell
./build/terrain-venv/Scripts/python.exe -X utf8 tools/terrain-viewer/test_underlay.py --source build/terrain-national-xyz-20261024/terrain.sqlite3 --binary build/terrain-viewer-target/release/terrain-viewer.exe --output build/native-underlay-check
```

## ズームイン時の LOD 巻き戻り対策

隣接差の調整で細かい領域の上位タイルをまとめて置き換えていたため、ズームインで中心が3段階粗くなることがありました。調整は予算内で粗い側を詳細化する方向だけとし、細かい側の強制削減を廃止しました。元データ35万面・192タイルの予算は維持します。

また、ズームアウト時の古い視点に対して完成した結果が、ズームイン後の詳細表示を置き換えないようにします。新しい視点が保留されていて、現在より広い範囲を対象とする結果が中心のデータレベルまたは同レベルでの分割数を下げる場合は表示へ反映しません。移動中でも詳細を改善する結果は引き続き反映します。

`examples/lod_sweep.rs` は全国 SQLite の3地域について、傾き・方角・距離を変えた1,044条件を調べます。修正前の中心LOD低下は4件、修正後は0件でした。旧方式の一律な曲面分割制限による分割数変化は、比較用の診断項目として出力します。

## 画面上の大きさに応じた曲面分割

「Loop曲面（GPU・最大）」は一律の分割数ではなく上限です。接合後の元の三角形ごとに、画面上の最長辺が約24 px以下になるよう1・2・4・8分割から選びます。画面外は1分割とし、手前の大きな面を細かく、遠方の小さな面を粗く描きます。視錐台を横切る三角形も数えます。元の形状を基準にした推定で、隠面除去後の画素数ではありません。

隣接面が共有する辺の分割数は細かい側にそろえます。粗い側は辺に沿う部分だけ接続用の面を作るため、面の内部全体を同じ密度にする必要はありません。CPUは1～8分割の小さな接続テンプレートと面ごとの画面サイズを決め、実際の共有頂点番号・三角形リスト・Loop座標・法線はGPUで生成します。各面の重心座標を最大分割の共通格子へ対応付け、同じ辺に二重の点やT字接続を作りません。

画面内の描画面数は接続用の面も含めて200万面を上限とし、超える場合は24 pxの目標を緩めます。元の面だけで超える場合は1分割を維持します。データLODの選択条件は変えません。全体で一律に分割数を下げる方式とは異なります。

生成メモリは別に、各段と描画出力を含めて384 MiB・単一バッファ128 MiBを上限とします。Loop座標は隣接面との連続性のため最大密度の共有格子で計算するため、描画に使わない格子点の分もメモリに含みます。メモリ不足の場合は最大分割数を下げて理由を表示します。キャッシュやフレームバッファを含むGPU総使用量の保証ではありません。

同じタイルの組み合わせでも視点ごとに画面サイズを再計算します。GPUキャッシュは元のタイル・最大分割数・各面の分割数が同じ場合に限って使います。下部に指定と実際の最大分割数、画面内の推定面数、1/2/4/8分割それぞれの元面数、メモリ制限の有無を表示します。連続操作中は完成した要求の視点に基づく表示です。

自動LOD品質のスライダーは右ほど早く詳細レベルへ切り替えます。1倍は従来と同じ判定、2倍は同じ画面上の誤差に対しておよそ1段細かいレベルを要求します。最大レベル・面数・タイル数の上限に達した場合はそれ以上細かくなりません。固定レベルではスライダーを無効にし、値を変えても選択結果へ影響しません。設定変更は読み込み要求に反映され、地域ボタンで移動しても品質倍率を維持します。
