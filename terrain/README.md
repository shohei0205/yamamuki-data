# 地形データの生成と表示の試作

国土地理院の標高データから地形を生成し、圧縮方式・表示品質・データ量を比較するためのコード。アプリへの組み込みと Releases / Pages への公開処理は未実装。

## 現在の方式

- 全国分は L7〜L12、JPEG XL distance=0.2 のハイトマップ。法線マップは付けない。
- 生成済み SQLite は 11,304 タイル、208,162,816 バイト。データ本体の合計は 189,770,484 バイト。
- 海域と河川・湖沼は保存済み WAT1 / RIV1 ベクターを別に取得する。海域は三角形を直接描画し、地形の切り抜きには補助マスクを使う。河川・湖沼は補助マスクを通して描画する。
- 河川は水面ポリゴンの形状で表示し、川幅を持たない中心線は描かない。画面上で約 0.5 描画ピクセル未満になる水面を近似判定で除く。
- 海岸と河川・湖沼は、それぞれ自動／z10／z11／z12 を選択できる。河川は北海道などに未収録範囲がある。

検証経緯と制約は [調査メモ](tools/terrain/RESEARCH.md)、過去の実行手順は [試作の作業記録](tools/terrain/README.md) にまとめている。作業記録には元の作業環境のパスや、終了した方式の記述も含まれる。

## 配置

地形関連のコードと作業ファイルは `terrain/` 以下に置く。この文書のコマンドは、リポジトリ直下から `cd terrain` した後に実行する。`tools/` と `build/` はいずれも `terrain/` からの相対パス。

| 場所 | 内容 |
|---|---|
| `tools/terrain/` | 標高取得、変換、比較用 HTML / JavaScript、中継サーバー、テスト |
| `tools/terrain-rs/` | Rust の地形・LOD・JPEG XL 生成器と圧縮比較 |
| `build/` | ローカルの元データ・生成物・外部ツール。Git 対象外 |

生成済みデータと実行ファイル、Python 仮想環境はローカルの `terrain/build/` に移動済みで、このブランチには含めていない。元データの取り直しや全国生成を始める前に、必要な保存済みファイルを用意する。

## ローカルの準備と表示

Python 3 と、使う処理に応じた依存パッケージが必要。

```powershell
cd terrain
python -m venv build/terrain-venv
build/terrain-venv/Scripts/python.exe -m pip install -r tools/terrain/requirements.txt
build/terrain-venv/Scripts/python.exe -m pip install -r tools/terrain/requirements-overlays.txt
build/terrain-venv/Scripts/python.exe tools/terrain/heightmap_server.py --port 61440
```

比較用の PNG / JPEG XL、SQLite、海域・水域データを `build/` に用意した後、`http://127.0.0.1:61440/heightmap` と `http://127.0.0.1:61440/national-shading` で確認する。ファイルがない状態では比較画面は動かない。JPEG XL の動的圧縮には別途エンコーダー／デコーダーが必要で、導入は `tools/terrain/setup_codec_tools.py` を参照する。

Rust のビルドは `tools/terrain-rs/build.ps1`、実行は `tools/terrain-rs/run.ps1` を使う。GEOS を使うポリゴン生成と、JPEG XL の処理には対応する外部ライブラリが必要。利用可能なコマンドはビルド後に `tools/terrain-rs/run.ps1 --help` で確認できる。

## テスト

```powershell
build/terrain-venv/Scripts/python.exe -m unittest discover -s tools/terrain -p 'test_*.py'
```

ブラウザーのテストは Node.js、Playwright、Microsoft Edge と、生成済みの比較データおよび起動済みのローカルサーバーを必要とする。例：

```powershell
node tools/terrain/test_tokyo_water.cjs
```

過去の方式を対象とするテストは、その方式の生成物も必要。すべての比較データを再生成するテストではない。

## 全国ハイトマップをブラウズする

全国 L7〜L12・JPEG XL d=0.2・法線なしの再生成済みデータから、ブラウザー表示用キャッシュを作成する。以下は `terrain/` 内で実行する。

```powershell
build/terrain-venv/Scripts/python.exe tools/terrain/prepare_height_browser.py
build/terrain-venv/Scripts/python.exe tools/terrain/heightmap_server.py --port 61440
```

`http://127.0.0.1:61440/national-height` を開く。初期表示は全国 L7。移動・拡大に応じて L12 まで切り替え、レベルの手動指定もできる。左ドラッグで移動、マウス位置を中心にホイールで拡大縮小、右ドラッグで方角と傾きを変える。槍ヶ岳・富士山・筑波山への移動ボタンもある。高レベルの広域指定は、表示範囲を拡大するまでタイル数を制限する。

JPEG XL の 16 bit 標高をブラウザーで直接復号する代わりに、`djxl` で一度だけ復号した値を PNG の R・G に分けて保存する。標高値を 8 bit へ落とさず、元の最小標高・スケールと有効範囲マスクも使用する。サーバーは保存済みファイルを中継し、投影・陰影・LOD・キャッシュはブラウザーで処理する。法線マップは使わない。海・河川・湖沼は別データの表示レイヤーとして切り替えられる。表示用 PNG の転送量と、配布用 JPEG XL の容量は画面で区別して表示する。

キャッシュは `build/terrain-height-browser/` に置く。生成途中から再開でき、別の元 DB と混在させないため SHA-256 を確認する。ブラウザーのタイルキャッシュには上限を設け、未取得部分は親レベルで補う。中心の緯度経度を URL で指定する例は `/national-height?lat=35.3606&lon=138.7274&span=45`（表示範囲の基準 45 km）。

検証は `python -m unittest discover -s tools/terrain -p test_prepare_height_browser.py` と `node tools/terrain/test_national_height.cjs`。後者は全国、富士山 L9〜L12、北海道、傾き、移動と元 DB の SHA-256 を確認する。

移動の座標変換は `node tools/terrain/test_national_navigation.cjs` で、回転 4 方向・傾き 3 段階のドラッグ方向とズーム中心の保持を確認する。

全国ハイトマップでも海・河川・湖沼を個別に表示できる。海域はベクター面を直接描画し、地形の切り抜きと河川・湖沼は既存の補助マスクを使う。海岸と河川・湖沼のレベルは独立した自動／z10／z11／z12。川幅のない中心線は表示せず、水面ポリゴンが約 0.5 描画ピクセル未満になる部分を非表示にする。水域の元データには既知の未収録範囲がある。水域転送量も地形とは別に表示する。確認は `node tools/terrain/test_national_height_water.cjs`。

タイルの境界は隣接する標高画素を線形補間し、両側の境界頂点を同じ高さにする。角は最大 4 タイルを参照する。未取得の詳細タイルは共通の親標高で補い、補助の垂直面は使わない。補正は表示時だけで、保存済み JPEG XL と PNG は変更しない。検証は `node tools/terrain/test_height_boundaries.cjs` と `node tools/terrain/test_height_tile_seams.cjs`。

各マスの対角線は、元ハイトマップの中央標高をよりよく再現する向きを選ぶ。同程度なら勾配差と交互の向きで固定方向への偏りを抑える。陰影は周囲の標高の差から法線を計算して補間し、タイル境界では法線の勾配も共有する。保存する法線マップや地形データの再生成は不要。`node tools/terrain/test_height_mesh.cjs`、`node tools/terrain/test_height_boundaries.cjs`、`node tools/terrain/test_height_smooth_shading.cjs` で確認する。

「陰影の強さ」は 0〜8 倍で、法線の水平成分だけを強める。高さ倍率を上げたときのような明暗差を、地形形状を変えずに調整できる。既定は 1 倍。レベル切替・移動後も保持し、URL の `shading=4` でも指定できる。確認は `node tools/terrain/test_height_shading_strength.cjs`。

太陽は「日時（JST）」と手動の方角・高さを切り替えられる。日時の変更、前後 1 時間、現在時刻のボタンに対応し、各地点の緯度・経度から個別に光源を計算する。日本の東西の差を反映し、太陽が地平線下では直射光を消す。日時は URL の `sunDateTime=2026-06-21T12:00`、手動は `sunMode=manual` で指定できる。面の陰影を太陽位置に合わせる。「地形による影」を ON にすると、地形同士の遮蔽も計算する。

「滑らかな陰影」を OFF にすると三角形の面法線で描画する。レベル変更・移動でも状態を保持し、URL の `smooth=0` でも OFF にできる。形状の対角線選択と境界標高の共有はどちらの陰影でも有効。検証は `node tools/terrain/test_national_height_solar.cjs`。

地形をクリックすると、その地点の緯度経度と表示地形の標高をメニューに出す。クリックだけでは視点を変えず、「この地点から水平に見る」を選ぶと透視表示へ切り替える。ドラッグではメニューを開かない。地形のない海上や空は選べない。

水平表示は選択地点の地形高を基準に、目の高さ 1.7 m を加えたカメラを置く。初期の上下角は 0°。ドラッグで見回し、ホイールで画角を変える。「水平に戻す」で上下角を 0°にし、「俯瞰へ戻る」で切替前の位置・縮尺・方角・傾きを復元する。地形は最大 50 km 先まで表示する。高さ倍率は引き続き有効で、カメラの地形高も同じ倍率に合わせる。読み込みで詳細度が変わる場合は現在の描画面へ視点の高さを追従させる。

選択地点は地形の深度から求め、傾いた画面でも手前に見えている三角形上の標高を使う。元 DEM より細かい測量精度を保証する機能ではない。`node tools/terrain/test_ground_camera.cjs` と `node tools/terrain/test_ground_camera_display.cjs` で逆投影・地形標高・クリックとドラッグの区別・見回し・復帰・傾斜時の選択・海上の選択制限を検証する。

水平表示の「足元を下げる範囲」で、カメラ近くの表示地形を中心で 100 m 下げる。周囲へなだらかにつなぐため、面を除外する場合のような穴は開かない。既定は水平距離 100 m で、「下げない」から 1 km まで選べる。近くの斜面に視界を遮られる場合は範囲を広げる。カメラ標高と保存データは変えず、俯瞰表示には適用しない。距離には表示中心の緯度によるメルカトルの倍率を補正する。確認は `node tools/terrain/test_ground_foot_hide.cjs`。

地形レベルの自動切替は「自動（最大12）」〜「自動（最大7）」で上限を選べる。縮尺から求めたレベルが上限を超えると上限に留め、水平視点でも同じ上限を適用する。「全国」で縮小しても自動の上限を保つ。手動指定も引き続き利用できる。URL は最大 12 が `level=auto`、最大 9 の例が `level=auto-9`。確認は `node tools/terrain/test_height_auto_max.cjs`。

## PNGからAdaptive TINを生成する

Rustの独立コマンド `terrain-adaptive-tin` は、Garland & HeckbertのGreedy InsertionでPNG標高マップを不規則メッシュへ変換する。既存の全国データ生成や比較用SQLiteは変更しない。

```powershell
# terrain/ で実行
./tools/terrain-rs/build.ps1 -AdaptiveTin
./build/terrain-rust-target/release/terrain-adaptive-tin.exe --input build/height.png --output build/adaptive-mesh.json --max-vertices 20000 --max-error 5 --encoding gray --scale 0.25 --offset 0 --spacing 10
```

`--max-vertices` は4以上（既定10000）、`--max-error` は0以上（既定5）。PNGを数値として復号し、標高は `画素値 × scale + offset` で求める。既定のgrayは8/16ビット・1成分グレースケールPNG専用で、ガンマ補正や8ビットへの変換は行わない。GSIのRGB標高PNGは `--encoding gsi` で符号付き24ビット・単位0.01 mとして復号し、scaleとoffsetを追加適用する。欠損値・無限大・アルファ付き画像・パレット画像は受け付けない。欠損領域を埋めたり、海面と判断して変更したりはしない。

XYは画素中心の格子座標で、左上が(0,0)、右向きX・下向きY。正方画素を前提とし、出力時に両軸へ同じ `--spacing`（既定1）を掛ける。Delaunay条件もこの等方的な平面上で評価する。緯度経度への投影や、異なるタイル間の境界接続はこのコマンドの対象外。

出力JSONの `vertices` は `[x,y,z]` の配列、`triangles` は0始まりの頂点インデックス3個の配列。Float64の標高を保存し、追加の量子化は行わない。`maxError` は入力PNGの全格子点における現在の最大絶対標高誤差。PNG化する前のDEMや格子間の曲面全体に対する上限ではない。`toleranceReached` と `stopReason`（tolerance / maxVertices）で停止理由を区別する。頂点数上限を優先して停止すると許容誤差を超える場合がある。`triangleEvaluations` と `sampleEvaluations` は局所再評価の計数。JSONは確認・連携用の形式であり、圧縮済みSQLiteの容量とは直接比較しない。

最初は4隅と2面だけを作り、各三角形内で入力標高との最大誤差点を走査する。優先度付きキューの最大要素から1点ずつ挿入し、外接円に追加点を含む隣接領域をBowyer–Watson法で置き換える。変更領域の新しい三角形だけ誤差を再評価する。全点のDelaunay再構成や全域の誤差再計算は行わない。失効したキュー要素は遅延破棄し、一定以上に増えたら有効要素だけで再構築する。

向きと外接円の判定は、PNGの整数座標に対するi128演算で行う。寸法を各軸1048576以下に制限して中間値の範囲を守る。高さと誤差の計算はFloat64。三角形は走査線との交差区間だけを走査し、境界点の包含判定は整数演算で行う。同一外接円上の点では不要な変更を行わず、外周の辺上への挿入では面積ゼロの面を作らない。ハッシュ表の順序によらず同じ入力と設定から同じ頂点・面を出力する。

検証コマンド:

```powershell
./tools/terrain-rs/build.ps1 -AdaptiveTin -Test
./build/terrain-venv/Scripts/python.exe -m unittest discover -s tools/terrain -p test_adaptive_tin_cli.py
```

Rustの10件で平面、長方形、境界、同一円上の点、整数判定、大域最大誤差点の選択、局所再評価、32系列のランダム挿入、PNGの数値復号、停止条件を確認する。Pythonの3件では生成器を呼び、出力した各三角形を独立に走査して入力PNG全点の誤差と被覆を照合する。Pythonは検証専用で、生成処理はRustのみ。

## 全国Adaptive TINの6段階生成

`terrain-adaptive-national` は保存済み `build/terrain-lod.sqlite3` のL14標高から、20・50・100・250・500・1000 mの6候補を作る。L14の4×4タイルと右・下の共有境界標高を読み、1025×1025の1区画にまとめる。区画番号はWeb Mercatorのz12相当。対象は7886区画、計47316メッシュ。元標高は5 m単位で量子化された保存済みデータで、追加ダウンロードは行わない。

```powershell
# terrain/ で実行。生成中のプロセスがある場合は二重起動しない。
./tools/terrain-rs/build.ps1 -AdaptiveNational
./build/terrain-rust-target/release/terrain-adaptive-national.exe --source build/terrain-lod.sqlite3 --output build/terrain-adaptive-national.sqlite3 --workers 4

# 保存済み区画を飛ばして同じコマンドで再開できる。確認用の区画数制限は --limit 4。
./build/terrain-rust-target/release/terrain-adaptive-national.exe --source build/terrain-lod.sqlite3 --output build/terrain-adaptive-national.sqlite3 --verify
./tools/terrain-rs/build.ps1 -AdaptiveNational -Test
```

各区画は6候補を1トランザクションで確定し、完了区画を `blocks` に記録する。元データのパス・サイズ・更新時刻と生成条件が異なる場合は同じ出力へ再開しない。出力は既存データと別のSQLite。`terrain-adaptive-national.progress.json` に進捗と段階別の保存量・頂点数・面数を記録する。実行ログは `terrain-adaptive-national.log`、エラーは `.err`、非表示実行のPIDは `.pid` に保存する。これらはbuild/以下に置く。自動確認タスクは追加しない。

全国版は4隅・2面から開始した後、境界の標高列だけで決まる固定頂点を先に挿入する。その後に通常の最大誤差優先挿入を行う。同じ許容誤差の隣接区画で同じ境界頂点を選び、区画境界の高さと分割位置をそろえる。許容誤差が異なる区画間の接続は描画側の別課題で、この固定処理だけでは保証しない。最大頂点数は全格子点数として許容誤差への到達を優先する。ブラウザーでの曲面分割は保存データへ焼き込まない。

入力の欠損は作業用格子に限り0で埋め、元の有効域を別のビットマスクとして保存する。欠損を実際の海面や有効標高へ変更したという意味ではない。描画側は `blocks.valid_mask` を必ず参照する。海岸・河川ベクトルの生成・変更は行わない。

出力の `meshes` は主キー(x,y,tolerance)で、data・normal_data・vertices・triangles・max_errorを保存する。dataはzlib圧縮した「頂点数UInt32・索引数UInt32・画素XY/標高のFloat32列・UInt32索引列」（すべてリトルエンディアン）。標高は元の5 m単位値を保持する。XYは0〜1024の画素座標でYが下向き。normal_dataは1頂点2バイトの八面体法線をzlib圧縮したもの。法線のYは地形表示用に上向きで、頂点密度に応じた3回の分離ボックス平均から計算する。地域比較で使ったGaussianと完全に同じフィルターではない。メッシュと法線は同じ行へ保存するため、地域比較のYVN1ヘッダーは使わない。

`blocks.valid_mask` は行優先・1画素1ビット・下位ビットから、1が元データ有効で、zlib圧縮する。`boundaries` には各候補の4辺の分割位置と標高を保存し、完了時に隣接辺の一致を確認する。その他、6候補の保存、誤差上限、BLOBの長さ、座標・索引範囲、法線長、SQLiteの整合性を完了時に検証する。全区画の独立した再ラスタライズ検証を行うものではない。

### 全国ビューアーの同一レベル境界を修正（2026-10-20）

### L2固定でも残る継ぎ目への対応（2026-10-20）

従来の3次三角形ベジエ補間は共有辺の値を合わせても、辺を横切る勾配が連続にならず、境界付近の陰影法線を混ぜるだけでは形状の折れが残った。全国ビューアーの傾きヒント付き補間をHsieh–Clough–Tocher型の3分割3次曲面に変更した。頂点の標高と2成分の傾き、共有辺中央の法線方向の微分を共通に与え、内部3パッチも高さと1階微分が連続になるよう固定参照三角形の制約を解く。辺中央の接線方向微分は端点の標高と微分から決まるHermite値を使い、垂直成分は端点の傾きの平均から作る。係数変換は地形に依存しない固定行列。ブラウザーで計算し、保存データや通信量は増やさない。

陰影にはこの曲面の解析微分を使用する。曲面分割なしでは既存の共有頂点の法線平均を維持する。旧比較ビューアーのPN補間は既定動作を変えない。保存した傾きヒントは以前の補間方式に対して適合した値を再利用するため、新方式に対する誤差の再最適化・最大誤差保証は行っていない。連続曲面のC1接続と、描画用に有限分割した面そのものの微分連続性は区別する。

L2固定の富士山周辺では、可視候補188枚に対して従来の上限180枚が適用され、8枚分にL7が混ざる別の問題も確認した。視錐台で標高0～4,500 mの範囲を判定して候補を絞り、L2の枚数上限を分割数に応じたGPU容量見積もりから決めるようにした。可視範囲の詳細タイルが揃った場合はL7を描画しない。画面にも実際に描画しているレベルを表示する。広域で予算上限を超えた場合や読込途中には背景L7が残る。

### 比高連動の許容誤差を滑らかにする比較

### 比高連動を山頂・肩・尾根へ限定する比較

### 固定50mの基本メッシュへ最大1,024頂点を追加する比較

`dataset=ridge1024` は、まず32 km四方の4隅から固定誤差50 mを満たすまで生成する。この段階に頂点予算は設けず、実装上の最大値は元格子の全点数とする。次に基本メッシュの全頂点を保持し、山頂・肩・尾根を優先した許容誤差に対する標高誤差の比が最大の点から、最大1,024頂点を追加する。条件を先に満たせば停止する。Delaunay再分割で変更された領域の誤差を再評価する。画面には基本頂点数・基本最大誤差・追加頂点数・最終誤差条件の達成状況を分けて表示する。基本生成は最低4頂点。従来の固定50m比較は最低128頂点なので、完全に平坦な地域では点数が異なり得る。

### 比高と凸地形の重みで追加点を選ぶ比較

`dataset=priority1024`を追加。固定50 mの基本メッシュを全頂点保持し、最大1,024点を追加する。優先度は「標高誤差÷比高の5%基準（下限5 m・上限50 m）×山頂・肩・尾根の重み（1～4倍）」。比高と凸地形は既存の広域窓・平滑化で求める。Rustには基準誤差を重みで割ったマップを渡し、最大優先度が1以下なら停止する。追加マップは基礎メッシュの50 m条件とは独立しており、赤い点で実際の追加頂点を表示できる。既存の追加方式は残す。


単純な相対誤差では平野の小さい起伏が優先されたため、追加基準を`50×(1-w)+w×比高基準/(1+3w)`へ修正した。wは平滑化した凸地形の優先度（0～1）。山腹・平野は50 mを維持し、山頂・尾根ほど比高基準と最大4倍の重みを効かせる。

### 曲面4分割で三角形状の陰影が残る原因の調査

富士山L3の中心タイル（x=8,y=-9）の1,954面を調べた。XY上で最小角5度未満の三角形は0面。3Dでは元が1面、曲面4分割後は31,264面中8面で、鋭角化が広範囲に起きているわけではない。強さ1のHCT曲面は共有辺で高さ・勾配とも連続しており、CPU倍精度での最大差は高さ約1.1e-9 m・勾配約2.6e-11だった。

原因は二つに分かれる。分割した頂点の単位法線を線形補間する近似では、4分割時の拡散光成分の誤差（0～1）が、面ごとの最大誤差の95パーセンタイルで約0.257だった。8分割で約0.155、16分割で約0.085に減る。一方、法線を画素ごとに正確に計算しても三角形状の陰影は残る。粗いメッシュの頂点高さとDEM由来の傾きを同時に満たす曲面自体に、局所的な膨らみができるためである。曲面を16分割相当の点で評価すると、元の3頂点の高さ範囲を5 m超はみ出す面は94面、最大は約25.27 mだった。これは元DEMとの差を測った数値ではなく、頂点の高さ範囲からのはみ出しである。

陰影の比較用に「陰影補間」を追加した。従来の「分割頂点から補間」を初期値として残し、「曲面を画素ごとに評価」「頂点の傾きだけ補間（調査用）」へ切り替えられる。最後の方式では三角形状の模様が減るが、実際の曲面の傾きと陰影が一致しないため、形状と陰影の切り分け用とする。補間曲面の過大な傾き・膨らみを抑えることが次の検討点である。元メッシュとSQLiteは変更していない。

画素評価用の曲面係数は元の高さ・傾きからブラウザーで計算し、GPU上の浮動小数点テクスチャへ保持する。配布画像や保存データは増やさない。三角形ごとに係数を参照するため、描画用の共有頂点を複製しており、GPU常駐量は増える。元の頂点数と描画頂点数を画面で分けて表示する。3方式の切り替えでは形状・面数・必要データ量は変わらない。

再現URLは `http://127.0.0.1:61448/?region=fuji&level=3&divisions=4&smooth=1&shade=vertex`。末尾のshadeをanalytic・slopesへ変えると比較できる。係数・UV・形状維持の単体テストと、3地域×3分割数×3陰影方式の表示を確認した。曲面4分割の例では、既存方式との形状座標差はテスト上0、GPU用係数の勾配評価とCPU倍精度の差は約2.46e-7以下だった。


### 傾きの一次補間に残る三角形状の陰影を弱める

「頂点の傾きだけ補間」でも、三角形をまたぐと傾きの変化率が変わり、山腹に角張った模様が残った。「傾きの変化も滑らかに補間」（shade=slopesSmooth）を追加する。頂点ごとに一周の隣接点から傾き2成分の変化率を重み付き最小二乗で求め、各成分をHCTでC1補間する。隣接点の差と逆向きの変化率は0へ制限し、差分の3倍を超す外挿も抑える。タイル辺上の変化率は両側共通の0とし、独立したタイルの計算で境界がずれないようにする。

形状用の高さ補間は変えず、陰影の傾きだけを別の滑らかな場として計算する。元の頂点、曲面分割後の位置と三角形、必要なSQLite BLOBは変わらない。実際の曲面の勾配とは異なる陰影なので、曲面の形状そのものを修正した方式ではない。稜線の輪郭や形状自体の角張りはこの変更だけでは直らない。従来3方式も残す。

GPU用係数は1面あたり48から112浮動小数点数へ増やし、追加の傾き場の係数もブラウザー内で生成する。保存データ・配布データは増やさないが、GPU常駐量と画素ごとの計算量は増える。富士山L3の同一視点で、一次補間にあった山腹の角張りが弱まることを確認した。共有辺101点の値・変化率の最大差は単体テストで約7.3e-13・1.9e-15。線形の傾き場の再現、境界条件、既存形状と面参照が変わらないことも検証する。

比較URL：`http://127.0.0.1:61448/?region=fuji&level=3&divisions=4&smooth=1&shade=slopesSmooth`。

### 緩い斜面の陰影を強める

### 曲面分割による外挿の抑制

滑らか陰影 OFF・陰影 1 倍でも、局所 DEM の傾きを長い辺へ外挿した曲面には細長い凹凸が出た。「曲面の外挿を抑制」で、各頂点の傾きを全隣接辺の標高差に沿う向き・3 倍以内へ縮めてから HCT を構成する。保存データと元頂点は変えない。共有境界の傾きは共通の 0 とするため、境界付近の曲面は従来から変わる。チェックを外すと従来方式と比較できる（URL は `limitCurve=0`）。

外挿制限で縮めた傾きを陰影用の傾き場にも流用すると、陰影が不自然に平坦化した。形状用の傾きと陰影用の元ヒントを分離し、「傾きの変化も滑らかに補間」と「頂点の傾きだけ補間」では保存済みヒントを維持する。実際の曲面を照らす「曲面を画素ごとに評価」と「分割頂点から補間」は制限後の形状の傾きを使う。この変更は形状と陰影の完全な一致を保証するものではない。単体テストで外挿 ON/OFF 間の陰影係数の一致と形状の変化を確認し、筑波山の WebGL 表示で 4 方式の切り替えを確認した。

### 元メッシュで曲面の外挿誤差を減らす

### メッシュのワイヤーフレーム表示

「ワイヤーフレーム」を「なし」「元メッシュ」「分割後メッシュ」から選べる。元メッシュは曲面上に元の三角形の辺を重ね、分割後は補間で増えた三角形の辺も表示する。曲面分割なしでは両者は同じ。線は地形に隠れる部分や欠損域には表示しない。切り替えは描画だけで行い、データの再取得やメッシュの再生成は行わない。URL の `wire=source` / `wire=render` で指定できる。曲面分割時は既存の三角形内座標を使い、分割なしでは同じ頂点を参照する線のインデックスを GPU に保持するため、GPU 容量にはその分を含む。筑波山で分割なし・4 分割の切り替えと、通信量・形状が変わらないことを確認した。

曲面分割なしのワイヤーフレームは、面の微分を評価するシェーダーを線描画にも使う経路で黒塗りになったため、マスクと深度判定だけを行う線専用シェーダーへ分離した。分割なしの表示について、GL エラーの確認に加え、地形色の画素が残り画面が黒塗りになっていないこともテストする。

61448 も `terrain-regional-priority-levels-v4.sqlite3` に切り替えた。配信サーバーの省略時の入力は、v5、v4、従来版の順に、存在する最新のファイルを使う。v2 は保持し、`--input build/terrain-regional-priority-levels-v2.sqlite3` で比較できる。筑波山 L3・9 タイルの XY 最小角を計測したところ、従来版は 5 度未満 20 面中 16 面が境界に接し、v4 は 25 面中 19 面だった。最小角は両者とも約 0.199 度。曲面の辺の誤差を減らす処理では、鋭角な面を防げていない。境界の共有位置の一致と、境界付近の三角形の品質は別の課題として扱う。

### 共有境界付近の鋭角面を減らす

`refine_regional_quality.py --output build/terrain-regional-priority-levels-v5.sqlite3` で、v4 を元に 3 地域・L0～L7 のメッシュ品質を補修する。XY 平面上の最小角が 10 度未満の面について、外接円中心付近の標高格子点を追加する。境界を侵す場合は境界線分の中点を先に追加し、隣接タイルにも同じ座標を配る。平坦な正方形のように角度が十分な領域には追加しない。元の頂点位置・高さ・傾きヒントを保持し、Delaunay 分割を作り直す。

角度の補修には基本枠の空きから最大 1,024 点／タイルを使い、標高誤差の補修を含めて最大 2,048 点／タイルとする。基本上限 16,384 点と、比高優先の追加上限 1,024 点は超えない。誤差の補修後に角度を測り直すため、10 度以上を保証する処理ではない。標高誤差は各レベルの許容値を守り、従来から許容値を超えていたタイルは従来の最大誤差を超えないことを確認する。共有辺を追加分割した後の境界標高誤差も測り直す。

L3 の試作では 3 地域合計の 10 度未満の面が 471→125 面。筑波山の 9 タイルの形状・傾き・マスクは約 141→145 KiB。共有辺の座標・高さ・傾き一致、元頂点とヒントの保持、面の向き、面積、Delaunay 条件、頂点数予算、標高誤差を検証する。最小角は投影前の XY 平面上で測るため、画面を傾けたときの見かけの鋭角さとは異なる。

補修版を 61448 に反映し、61449 は v4 の比較用として残す。元の v2・v4 データは保持する。画面には「境界・鋭角面を補修」と表示し、選択レベルの鋭角面数を補修前後で表示する。

鋭角面の補修版 v5 は全 144 タイルを生成し、61448 に反映済み。10 度未満の面は全体で 4,278→586 面、5 度未満は 692→311 面。頂点数は 452,458→461,791（約 2.1% 増）。元の頂点・傾きヒントの保持、共有辺の位置・高さ・傾き一致、Delaunay 条件、面積・面の向き、頂点数予算、標高誤差の検証を通過した。61448 で 3 地域×全 8 レベル、曲面分割なし／4 分割、面陰影／滑らか陰影、ワイヤーフレームの切り替えを確認した。61449 は v4 の比較用として保持する。

曲面分割が「なし」のときは「曲面の強さ」と「曲面の外挿を抑制」を無効表示にする。強さ 0 のときも外挿制限を無効にする。v5 の筑波山 L3・4 分割で GPU 頂点を比較し、外挿制限と強さによって追加頂点の高さが変わることを確認した。「傾きの変化も滑らかに補間」は保存済みの傾き場を使うため、形状の変化を陰影へそのまま反映する方式ではない。

### 外挿制限による不自然な水平化を修正

旧制限は、辺方向の条件に合わない場合に頂点の傾き全体をゼロへ縮め、共有境界も一律にゼロへ固定していた。このため、曲面の実際の傾きで陰影を計算すると、不自然な平坦部や細かな凹凸が目立った。独立した傾き場による陰影ではこれが見えにくかった。

各辺方向の外挿量を制約する凸領域へ、元の傾きを最短射影する方式へ変更した。許容幅は辺の標高差、隣接頂点の比高、レベルの許容誤差から決める。一方向の補正で他方向まで一律に潰さず、曲がった地形に単調性も強制しない。共有境界は両側共通の保存済みヒントをそのまま使う。元メッシュと保存データは変更しない。

方向別の補正、平面と境界の傾き維持、外挿量の制約、元ヒント不変を単体テストした。表示では、実際の曲面を評価する陰影にも細かな凹凸が残る。独立した傾き場と実際の曲面の陰影が同一になる修正ではなく、完全解消とは扱わない。

### GPUでの曲面評価と強さのリアルタイム変更

全国メッシュビューワーに「曲面の計算：GPU（リアルタイム）／CPU（変更時に再生成）」を追加した。GPU 方式を標準とする。曲面分割が 2・4・8 のとき、ワーカーでは元の三角形ごとの HCT 係数と陰影用の係数を作り、GPU では全三角形で共通の分割パターンをインスタンス描画する。頂点シェーダーが曲面の高さと傾きを評価する。元の 3 頂点は既存の係数テクスチャの未使用領域に保存し、配布データの形式は変えない。

「曲面の強さ」はスライダーの `input` ごとに uniform を更新し、次の描画に反映する。メッシュの再生成・再取得・頂点データの再転送・ページ再読み込みは行わない。2・4・8 分割の切り替えでも共通パターンを切り替えるだけで、係数は再利用する。分割なしでは従来の元メッシュ描画を使い、曲面の設定は無効にする。外挿制限や GPU/CPU の切り替えは係数・メッシュの再生成が必要。CPU 比較方式では強さの操作完了時に再生成する。

筑波山 L3・4 分割について transform feedback で GPU 出力を読み、CPU の頂点位置と強さ 0・0.5・1 で比較した。最大差は約 0.000092 m。強さ 1 の頂点法線差は約 0.0000045。中間の強さでは CPU 側の境界法線の平均化があるため、法線の完全一致は保証しない。強さの操作中にワーカージョブ・通信・GPU バッファとテクスチャの再転送が増えないことをテストした。3 地域×3 分割数×4 陰影方式、ワイヤーフレームの切り替えも確認した。

槍ヶ岳 L3・8 分割の GPU 使用量表示は CPU 展開方式の約 237.5 MiB から約 39.5 MiB へ減った。ただし、描画する三角形数は同じで、これ自体が描画速度や曲面の品質の改善を保証するものではない。確認用 URL は `http://127.0.0.1:61448/?region=tsukuba&level=3&divisions=4&smooth=1&shade=slopesSmooth&engine=gpu`。

### 曲面全体の曲がりを抑える比較方式（2026-10-20）

### 元頂点の高さ・傾きを調整する比較方式（2026-10-20）

### 曲面方式4種類の比較（2026-10-20）

| 方式 | 実装と制約 |
|---|---|

### 盛り上がる山体と最大誤差を使う改良（2026-10-21）

前案は地域内の多くの小さな起伏も相対誤差で重くし、対象の山の頂点を減らしてしまった。改良案 `--landform-aware` では、従来の混合許容誤差を土台に残し、周辺より盛り上がる山体の部分だけを最大3.5倍重くする。250 mの標高場で6 kmのGaussian周辺平均と16 km範囲の比高を求め、正の盛り上がりを比高で正規化する。20～100 mの盛り上がりで重みを滑らかに増やし、最後に約1 kmで重みを平滑化する。表示範囲の外も28 km参照し、範囲端を偽の山として扱わない。山名による分岐や、平野への最低頂点数は設けない。

地域の平均誤差で選ぶと、孤立した山の残りの大きな誤差が平野で希釈される。そのためこの案は、地域間の選択にも正規化した最大誤差を使う。固定外周と欠損域を選択対象から除外する。固定外周の誤差を含む最大値では、追加点で減らせない誤差が地域選択を独占するため。地域内の追加ごとの更新は従来のRust TINの優先度キューを使う。地域間は32 km試験で512点、128 km本比較で2,048点追加するごとに選び直すため、全地域を合わせた厳密な1点単位のGreedyではない。
